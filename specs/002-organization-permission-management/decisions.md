# Decisions: 可配置组织树与分级权限管理

**Feature Branch**: `002-organization-permission-management`
**Created**: 2026-08-16

## ADR-001: Keycloak 通用组织树与平台权限中心分工

**Status**: Accepted
**Date**: 2026-08-16

### Context

V0.1 使用 Keycloak 完成人员认证，但组织只支持固定域、部门、团队三层，人员组织上下文来自手工用户属性，业务权限只支持六种固定角色及部门级范围。新需求要求任意深度组织树、一个主组织与多个协作组织、自定义角色、人员或组织授权、组织范围向下继承和受约束的委派管理。

关键决策是组织与人员由谁作为事实来源，以及业务权限应放在 Keycloak 还是平台。若两个系统都可独立修改相同主数据，会产生不可解释的冲突；若把全部业务权限塞进 Keycloak Token，则权限变更受 Token 生命周期影响，也难以表达业务资源范围。

### Options Considered

1. 扩展平台固定层级表，增加部、处、团队、组等字段和固定范围类型。
2. 以 Keycloak Group/User/Membership 为组织人员事实来源，管理平台通过 Admin API 管理并保存只读快照；业务权限点、自定义角色和组织范围授权由平台负责。
3. 以平台数据库为组织人员主库，再异步双写 Keycloak。

### Decision

We choose 方案 2 because Keycloak 已是统一认证系统，原生支持任意深度 Group 和 User Membership；平台可以提供符合业务的组织管理界面，同时把与具体资源相关的权限判断留在平台服务端。该分工避免组织主数据双主写入，也避免将动态业务权限耦合到 Keycloak Realm Role 和长生命周期 Token。

Keycloak 保存用户凭据、用户状态、组织 Group 树、Membership 和 `primary_org_id`。平台通过最小权限 Admin API 服务账号执行写入，随后同步通用组织节点、人员及成员关系快照。平台独占维护权限点目录、自定义角色、授权对象、资源组织范围、继承开关、有效期、授权版本和审计事件。业务请求使用当前平台授权数据做服务端校验。

### Consequences

**Positive:**
- 组织层级不再受数据库固定结构限制，新增层级无需迁移字段或改授权算法。
- 身份与凭据继续由 Keycloak 处理，平台不存储人员密码。
- 业务权限可即时撤销、按资源组织过滤并防止委派越权，不依赖 Token 过期。
- 组织与权限职责边界清晰，可独立测试和演进。
- 平台外部合法修改 Keycloak 后，可通过全量对账恢复快照一致性。

**Negative:**
- 管理写入跨越 Keycloak 和平台数据库，无法获得单一 ACID 事务，必须实现部分成功、幂等重试和对账。
- 平台需要维护组织闭包关系、授权版本和缓存失效逻辑。
- Keycloak 服务账号权限配置成为新的高风险运维边界。
- 从固定表和固定角色迁移需要权限效果对比，不能只做结构迁移。
- 组织角色与协作组织会增加权限解释复杂度，管理界面必须提供来源和范围预览。
