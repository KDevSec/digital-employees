# Feature Spec: 可配置组织树与分级权限管理

**Feature Branch**: `002-organization-permission-management`
**Created**: 2026-08-16
**Input**: User description: "部门、团队只是初始样例；组织树可新增、删除、修改和移动，人员具有一个主组织和多个协作组织，管理员可为不同人员或组织配置自定义角色与继承范围。"

## Problem Statement

当前 V0.1 把组织固定为“域—部门—团队”三层，人员组织归属依赖 Keycloak 用户属性，平台只读同步用户而不管理完整 Group 树；权限也仅支持六种固定角色和全局、域内全部部门、指定部门、本人四种范围。这无法表达公司实际存在的部、处、团队、研发组、项目组等任意层级，也无法让受委派管理员在不越权的前提下为不同组织成员配置不同权限。

平台需要把 Keycloak 继续作为身份、凭据、组织树和成员关系的唯一事实来源，同时在平台侧建立通用组织快照和业务权限中心，使组织调整、人员兼职、自定义角色、向下继承和审计能够即时、可解释地生效。

## Goals

- 支持以 `iei`、`inspur` 等可配置公司域为根的任意深度组织树。
- 允许管理员通过管理平台新增、重命名、移动、停用、恢复和归档组织节点。
- 支持每人一个主组织和零到多个协作组织。
- 由系统维护权限点目录，允许管理员按公司域创建自定义角色。
- 支持将角色授予人员或组织成员，并分别配置授权对象是否包含下级、资源范围是否包含下级。
- 所有业务 API 在服务端执行实时权限校验，并防止受委派管理员提升权限或扩大管辖范围。
- Keycloak 写入后同步平台快照；部分失败可观测、可重试、可通过全量对账恢复。
- 平滑迁移 V0.1 的域、部门、团队、人员和固定角色授权，不意外扩大现有权限。

## Non-goals

- 第一阶段不支持显式拒绝规则、策略优先级或通用 ABAC 表达式。
- 管理员不能自定义新的权限点；权限点由版本化代码和迁移维护。
- 不把业务角色或完整权限集合写入 Keycloak Realm Role 或访问令牌。
- 不建设 HR、LDAP、AD 或其他外部组织主数据同步；后续可接入 Keycloak 联邦能力。
- 不支持组织节点直接跨公司域移动；跨域调整使用显式迁移流程，第一阶段不实现该流程。
- 不物理删除已有业务引用的人员、组织、角色或授权记录。
- 不在本功能中改变 Keycloak 登录协议、BFF 会话形态或工作台机器身份协议。

## Primary User Flow (Happy Path)

1. 系统管理员在管理平台创建公司域及任意深度的下级组织。
2. 平台校验权限和并发版本后，通过最小权限服务账号写入 Keycloak Group，并同步平台组织快照与闭包关系。
3. 人员管理员创建或选择 Keycloak 用户，设置唯一主组织并按需加入协作组织。
4. 权限管理员从系统权限点创建自定义角色，再把角色授予人员或组织成员并选择资源组织范围和下级继承规则。
5. 被授权人员访问业务资源时，平台合并直接授权和组织授权，并按目标资源的组织上下文做服务端范围校验。
6. 所有成功、拒绝、部分成功和对账修复均形成审计事件；关键权限或人员状态变更使相关缓存和会话失效。

## User Stories (prioritized)

### P1 — 管理任意深度组织树

作为系统管理员或被授权的组织管理员，我希望在自己的管辖范围内维护可配置组织树，而不受固定“部门/团队”层级限制。

**Acceptance Scenarios**:
1. **Given** 系统管理员拥有全局组织管理权限，**When** 其创建公司域以及五层以上的部、处、团队和研发组节点，**Then** Keycloak Group 树与平台组织快照具有相同父子关系、稳定 ID、类型、编码、名称、状态和排序。
2. **Given** 一个组织已有成员和有效授权，**When** 有权管理员重命名该组织，**Then** 组织稳定 ID 不变，成员关系及既有授权继续生效，并记录变更前后名称。
3. **Given** 一个组织分支被移动到同域的新父节点，**When** 移动通过循环、权限和版本校验，**Then** 平台重建受影响闭包关系，旧上级继承权限失效，新上级继承权限生效。
4. **Given** 组织仍有有效下级、成员或授权，**When** 管理员尝试归档，**Then** 请求返回冲突并列出阻塞类别；清理阻塞后可归档且归档节点不能接受新成员或授权。

### P1 — 管理人员主组织与协作组织

作为人员管理员，我希望为人员设置唯一主组织和多个协作组织，以支持正式汇报关系和跨部门协作。

**Acceptance Scenarios**:
1. **Given** 一个有效 Keycloak 用户，**When** 管理员设置主组织并加入两个协作组织，**Then** Keycloak Membership、`primary_org_id` 与平台快照一致，且仅有一个有效主组织。
2. **Given** 人员从安全研发组调到 kdevsec 组，**When** 管理员变更主组织，**Then** 身份 `issuer + subject` 不变，旧主组织关系结束，新主组织关系生效，协作组织不受影响。
3. **Given** 人员被停用，**When** 其继续使用已有平台会话访问 API，**Then** 会话被撤销或请求被拒绝，人员的角色授权不再产生有效权限。

### P1 — 配置自定义角色和组织范围授权

作为权限管理员，我希望从系统权限点组合自定义角色，并授予指定人员或组织成员不同的资源范围。

**Acceptance Scenarios**:
1. **Given** 权限管理员拥有角色管理权限，**When** 其创建“CBB团队管理员”并选择组织成员管理、工作台读取和审批权限，**Then** 角色保存系统权限点引用且不修改 Keycloak Realm Role。
2. **Given** 角色被授予 CBB团队及其下级成员，资源范围为 CBB团队及其下级，**When** 安全研发组成员访问下属资源，**Then** 请求允许；访问 KOS团队资源时返回 403。
3. **Given** 一个人同时具有直接角色、主组织角色和协作组织角色，**When** 其访问各自有效范围内的资源，**Then** 有效权限取允许权限并集，过期、撤销或停用的角色不参与计算。
4. **Given** 研发一处管理员尝试授予自己没有的权限或把范围扩大到系统软件研发部，**When** 提交授权，**Then** 服务端拒绝并记录越权尝试，且不能通过新建或修改自定义角色绕过检查。

### P2 — 保持 Keycloak 与平台快照最终一致

作为平台运维人员，我希望组织和人员写入发生部分失败时能够定位并自动恢复，而不形成静默双写不一致。

**Acceptance Scenarios**:
1. **Given** Keycloak 写入成功但平台快照更新失败，**When** 管理请求结束，**Then** 返回可识别的部分成功结果，记录 `IAM_SYNC_PENDING` 与追踪 ID，并由重试任务补齐快照。
2. **Given** Keycloak 被平台外部合法修改或曾发生同步遗漏，**When** 定时全量对账运行，**Then** 平台按 Keycloak 事实修正组织、成员和人员状态，并记录差异摘要。

### P2 — 迁移并审计 V0.1 数据

作为系统管理员，我希望升级后保留现有组织、人员和权限效果，并能审计所有后续管理行为。

**Acceptance Scenarios**:
1. **Given** V0.1 存在域、部门、团队、人员和固定角色，**When** 执行数据库迁移和首次 Keycloak 对账，**Then** 数据转换为通用组织节点、成员关系、自定义或兼容角色，迁移前后的授权允许集合一致或更窄而不更宽。
2. **Given** 管理员新增、修改、移动、停用组织，调整成员或角色授权，**When** 操作成功、失败或部分成功，**Then** 审计记录包含操作者、目标、组织范围、变更摘要、结果和追踪 ID。

## Requirements

### Functional

- **FR-001**: Keycloak 必须作为用户、凭据、Group 组织树和 Group Membership 的唯一事实来源。
- **FR-002**: 管理平台必须通过专用最小权限 Keycloak Admin API 客户端执行组织和人员写操作，不得使用运行时 `admin` 超级账号。
- **FR-003**: 公司域必须可配置；每个公司域对应一棵独立组织树根，平台必须阻止普通移动操作跨域改变父节点。
- **FR-004**: 组织节点必须支持任意深度，节点类型来自可配置字典且不得约束允许的父子层级。
- **FR-005**: 每个组织节点必须具有不可变 `org_id`、Keycloak Group ID、域、父节点、域内唯一编码、类型、名称、状态、排序、版本和同步时间。
- **FR-006**: 重命名、修改类型或调整排序不得改变 `org_id`；移动不得改变 `org_id` 或已有成员身份。
- **FR-007**: 平台必须维护祖先—后代闭包关系并拒绝自引用或形成环的移动。
- **FR-008**: 有有效子节点、人员关系或角色授权的组织不得归档；归档节点不得接受新成员、子节点或授权。
- **FR-009**: 组织、人员和角色使用停用/归档状态保留历史引用，不以物理删除作为正常管理操作。
- **FR-010**: 每个有效人员必须最多具有一个主组织，并可具有零到多个不重复的协作组织。
- **FR-011**: 主组织由 Keycloak 用户属性 `primary_org_id` 标识，所有主组织和协作组织同时以 Group Membership 表达。
- **FR-012**: 人员的稳定身份键必须继续使用 `issuer + subject`；调整组织不得创建新人员身份。
- **FR-013**: 停用人员必须使其业务权限失效，并使现有平台会话在下一请求前或变更完成后 60 秒内失效。
- **FR-014**: 权限点必须由系统版本化维护，包含代码、资源类型、动作、说明、风险等级和是否可委派；管理员不得创建权限点。
- **FR-015**: 公司域权限管理员必须能从系统权限点创建、复制、修改和停用域内自定义角色。
- **FR-016**: 角色授权对象必须支持单个人员或组织；组织授权必须独立配置是否包含下级组织成员。
- **FR-017**: 角色资源范围必须绑定一个组织节点，并独立配置是否包含全部下级资源；仅本人能力必须继续校验资源所有者。
- **FR-018**: 有效权限必须合并所有匹配的直接、主组织、协作组织和祖先组织授权，采用允许权限并集，不支持显式拒绝。
- **FR-019**: 角色停用、授权撤销、授权过期或人员停用后不得参与有效权限计算。
- **FR-020**: 每个受保护业务资源必须向授权层提供资源类型、资源 ID、所有者人员 ID 和所属组织 ID。
- **FR-021**: 所有业务 API 必须在服务端校验权限点和组织范围；前端按钮或菜单隐藏不得替代服务端校验。
- **FR-022**: 委派授权者必须拥有 `role.assign`、被授权对象管理权、拟授予的全部可委派权限以及不小于拟授予范围的有效范围。
- **FR-023**: 角色创建和修改必须执行与角色授予相同的权限子集检查，防止通过自定义角色提升权限。
- **FR-024**: 平台必须保护至少一个全局系统管理员；高风险不可委派权限只能由具有相应系统级能力的管理员维护。
- **FR-025**: 权限或组织关系变更必须递增授权版本并失效受影响人员缓存；高风险变更可撤销相关平台会话。
- **FR-026**: 组织和人员管理必须采用 Keycloak 写入优先的同步写穿流程，并使用幂等操作标识、版本检查和追踪 ID。
- **FR-027**: Keycloak 成功而平台快照失败时，平台不得伪造回滚成功，必须记录待同步状态并支持幂等重试。
- **FR-028**: 平台必须提供定时全量对账，按 Keycloak 事实修复组织、人员、成员关系和状态差异。
- **FR-029**: 管理 API 必须支持组织树查询、节点 CRUD/移动/停用/恢复/归档、人员 CRUD/状态/组织关系、角色 CRUD 和授权 CRUD。
- **FR-030**: 管理界面必须展示组织树、节点详情、直接与下级成员、主与协作组织、直接与继承角色、最终有效权限和授权范围预览。
- **FR-031**: 所有组织、人员、角色和授权操作的成功、拒绝、部分成功及对账修复必须写入不可变审计事件。
- **FR-032**: 更新和移动操作必须携带版本，旧版本写入返回 HTTP 409 并不得覆盖新数据。
- **FR-033**: 平台必须迁移 V0.1 固定组织表和角色范围，并提供迁移前后权限允许集合的对比验证。

### Non-functional

- **NFR-001**: 在单域 10,000 个组织节点、100,000 个人员和每人 20 条有效授权的基准数据下，缓存命中的单资源权限判断服务端 P95 不超过 50 ms，缓存未命中 P95 不超过 250 ms。
- **NFR-002**: 组织树 API 必须支持按节点懒加载和服务端搜索；任何单次列表响应不超过 1,000 条记录。
- **NFR-003**: Keycloak 写入成功后的目标对象增量同步应在 5 秒内完成；失败重试采用指数退避并在 15 分钟内告警。
- **NFR-004**: 全量对账必须可断点续跑且幂等；100,000 个人员规模下单次运行不得阻塞在线登录和授权请求。
- **NFR-005**: 管理写接口必须生成或接收幂等键，并在重复提交时返回同一逻辑结果而不创建重复 Group、成员关系或授权。
- **NFR-006**: Keycloak 管理凭据、数据库凭据和会话秘密不得写入源码、Realm JSON 或前端资源，必须通过部署 Secret 注入。
- **NFR-007**: 审计事件不得记录密码、Keycloak Token、会话 Cookie 或完整敏感请求体。
- **NFR-008**: 所有组织范围查询必须在数据库查询或授权层过滤，禁止先返回全量数据再由前端裁剪。

## Edge Cases

- 两名管理员同时重命名或移动同一组织节点。
- 移动目标是节点自身、其后代、已归档节点或另一个公司域。
- Keycloak Group 创建成功但客户端超时，调用方使用同一幂等键重试。
- 删除主组织关系时人员仍处于启用状态且未提供替代主组织。
- 同一协作组织被重复添加，或主组织同时被添加为协作组织。
- 人员属于多个组织，而各组织角色的资源范围部分重叠。
- 自定义角色修改会扩大大量现有授权人员的有效权限。
- 授权在请求执行期间到期或被撤销。
- 组织移动导致大量祖先授权范围变化，缓存失效任务部分失败。
- 外部管理员直接在 Keycloak 修改 Group 或 Membership。
- V0.1 的 `DEPARTMENT_SET` 同时包含多个部门，需要拆成多个组织范围授权。
- 最后一个全局系统管理员被停用、移出有效范围或撤销角色。

## Success Criteria (measurable)

- **SC-001**: 自动化测试能创建并读取至少 8 层组织树，重命名和同域移动后稳定 ID 与成员关系保持不变。
- **SC-002**: 主组织唯一性、多个协作组织和人员停用场景全部由数据库约束及 API 集成测试覆盖。
- **SC-003**: 权限测试矩阵覆盖人员/组织两类授权对象、两种下级开关、直接/主组织/协作组织授权、角色并集、到期、撤销和跨范围拒绝，零越权用例通过。
- **SC-004**: 委派测试证明管理员无法授予自己没有的权限、不可委派权限或超出自身范围的权限。
- **SC-005**: 注入 Keycloak 成功/平台失败故障后，重试或全量对账能恢复一致状态且不产生重复数据。
- **SC-006**: V0.1 迁移对比报告中不存在迁移后新增的允许权限；所有原有人员保持相同 `issuer + subject`。
- **SC-007**: 每种管理写操作至少产生一条成功审计测试和一条拒绝或失败审计测试，且敏感字段扫描结果为零泄露。
- **SC-008**: 约定规模的授权性能基准满足 NFR-001。

## Assumptions

- 第一阶段以一个管理平台实例服务多个可配置公司域，但不提供跨域资源共享。
- 人员可以没有协作组织；启用的普通人员原则上必须具有主组织，系统级服务账号除外。
- 组织节点类型为可配置展示元数据，不参与权限继承算法。
- 组织授权对象通过人员当前有效 Membership 动态匹配，而不是授权时展开为静态人员列表。
- 权限点随应用版本发布；删除权限点采用停用和迁移，不直接破坏已有角色引用。
- 全局系统管理员属于平台级安全边界，不受普通公司域管理员委派。
