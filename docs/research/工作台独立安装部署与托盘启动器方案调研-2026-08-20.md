## 1. 结论先行

> v2 修订说明：初版推荐 Electron 作为「无窗口托盘启动器 + Node 服务宿主」。经 QoderWake 0.3.5 实证（附录 A）+ 用户「越轻量越好」原则，**推翻 Electron 方案**，改为下述三件独立制品模型。被推翻的论据见 §4.3。
>
> **v3 修订说明**：Windows 侧实证带来一处推翻、一处细化、三条新增一等约束 ——
> 1. **推翻**「Windows keepalive = 计划任务」：实证机上计划任务/服务/Run 键/启动文件夹**全部为空**，实际靠托盘进程做看门狗，daemon 以 `--no-keepalive` 被拉起（源码拆解 §8.2）。我们**不照搬**（那是托盘单点），改为分阶段双层，见 §7.1.2 与 D-k。
> 2. **细化** C-5：OS 守护只保证「进程在」，保证不了「能服务」。实证日志里 `daemon process exists but health is not ready` 出现 **19 次**——「进程活着但不健康」是常态而非异常，health 探活必须另有一层。
> 3. **新增** C-8（更新的 pending 态兜底与磁盘 GC）、R-13（无签名常驻 exe 被 EDR 拦）、R-14（pending 包悬挂占盘）、R-16（孤儿子进程账本）。
> 全部 22 条 Windows 动作项（W-1 ~ W-22）的落点在本报告 §5–§14 逐条就位，对照见附录 A.7 末尾。

**推荐方案：服务本体编译为单体可执行文件、进程守护完全委托操作系统、托盘壳做成可选且最薄的一层——三者独立版本化、独立分发。**

一句话架构：

```
三类制品，各自独立版本号、独立更新（实证参照：QoderWake daemon 0.3.5 / nativeApp 0.1.5 / cli 1.1.8）

① Workbench Service —— 单体可执行（Bun --compile 或 Node SEA），目标用户无需装 Node
     ├─ 绑 127.0.0.1:19820，静态托管前端产物 + API + SSE
     ├─ 原生依赖（sqlite-vec）按平台**外挂** .so/.dylib/.dll，运行时 load，不编入二进制
     └─ 写 run/service.json 暴露 pid/port/version/instanceId 供外部发现

② Keepalive —— 双层（v3 修正）：进程级委托 OS，health 级另加一层
     ├─ Linux   systemd --user unit
     ├─ macOS    ~/Library/LaunchAgents/*.plist
     └─ Windows  计划任务（Task XML 导入，四个反直觉默认值必须覆写）
     OS 负责：崩溃重启 / 退避 / 熔断 / 开机自启 —— 无自研 supervisor
     OS 不负责：「进程活着但 /healthz 不就绪」——实证中这是常态（19 次），
                故 0.2 起由托盘壳做 health 探活；0.1 无壳时由 CLI/status 承担（§7.1.2）

③ Tray Shell（可选层，仅 Windows + macOS）—— 只有托盘图标 + 右键菜单，零业务逻辑
     ├─ 与 Service 仅以 HTTP + run/service.json 耦合
     └─ Linux 不发壳（GNOME 托盘不可靠，见 §10.2），纯 headless + CLI

用户交互入口 = 系统默认浏览器打开 http://127.0.0.1:19820
```

八条核心结论：

| # | 结论 | 依据 |
|---|------|------|
| C-1 | **桌面壳不承担 UI 渲染**，只做托盘 + 打开浏览器 | UI 走系统浏览器访问 19820 是已冻结约束（白皮书 §4.4），WebView 价值在此场景归零 |
| C-2 | **工作台后端语言裁定 TypeScript** | 白皮书 §9.2/§9.4 已把"工作台是 TS"当既有前提；记忆 SDK 是 TS；避免双运行时打包 |
| C-3 | ~~桌面壳选 Electron~~ → **服务编译为单体可执行，不用 Electron 承载服务** | 初版论据「只有 Electron 能打包原生模块」已被实证推翻：原生依赖按平台外挂即可（附录 A.2）。详见 §4.3 |
| C-4 | **Shell 与 Service 独立版本化、独立分发、平台按需** | QoderWake 工业级验证：壳是独立 zip、独立版本号，且 Linux 干脆不发壳（附录 A.1）。**Windows 侧实测进一步坐实：托盘壳是 87 KB 原生 exe**，版本源（`native-shell-version`）与日志均与 daemon 完全分离（源码拆解 §8.6）|
| C-5 | **进程级守护委托 OS**，不自研退避重启；但 **health 级探活必须另有一层**（v3 细化）| systemd/launchd/计划任务原生具备重启与自启语义（附录 A.3），自研只会更差；但它们只看进程在不在 —— 实证里「进程在但 /healthz 未就绪」出现 19 次（§8.6），OS 对此无感 |
| C-6 | **更新只做"检查 + 引导下载 + 校验和"**，不做静默自动更新 | 用户明确不购签名证书；跨平台一致且零证书成本的唯一稳妥形态。见 §8 |
| C-7 | **托盘是便利层不是必需层**，Linux 本期直接不做壳 | GNOME 默认无 StatusNotifierItem；实证参照亦无 Linux 壳。⚠️ 但壳不能成为 keepalive 的**唯一**路径（实证参照就是这么做的，托盘被杀则全链断）——见 §7.1.2 |
| **C-8** | **更新的 pending 态必须有兜底应用时机、用户可见性与磁盘 GC**（v3 新增）| 实证：0.2.4 已下载完毕却**悬挂 15 天未应用**，白占 327 MB（占 profile 总 786 MB 的 42%），而用户以为自己在最新版（§8.5）。只把应用时机挂在「下次重启交接」上是不够的 |

体量预期（较初版大幅下降）：Service 单体 ~60–100 MB，Tray Shell **< 10 MB（实证参照仅 87 KB，可作为目标上限）**，常驻内存 ~40–80 MB（无 Chromium、无渲染进程）。

⚠️ 但磁盘预算不只是安装体积：实证参照安装到 `C:\Software\` 之后，又在用户目录占了 **785.8 MB**（其中 327 MB 是一份从未用上的更新包）。**profile 磁盘预算必须有上限与启动 GC**，见 §8.4。

## 3. 关键洞察：桌面壳不需要 WebView

这是本调研最重要的一条，它直接改变了候选集的评判标准。

通常"桌面应用"选 Electron / Tauri 的核心动机是**内嵌浏览器渲染前端界面**。但本项目已冻结的形态是：

> 浏览器打开 `localhost:19820` 进入交互前端 —— 白皮书 §4.4

也就是说 **UI 由用户的系统浏览器承载，桌面壳一个像素都不渲染**。桌面壳真正要干的只有五件事：

1. 在系统通知区域/菜单栏放一个图标
2. 弹右键菜单
3. 拉起/停止/守护一个本地 HTTP 服务进程
4. 调系统 API 打开默认浏览器到指定 URL
5. 打包成安装包 + 检查更新

这五件事**都不需要 WebView**。所以：

- 选 Electron ≠ 为了 Chromium；只是为了它内建的 `Tray` / `requestSingleInstanceLock` / `shell.openExternal` / `Notification` / electron-builder / 以及**Node 运行时和原生模块的成熟打包路径**
- 选 Tauri ≠ 为了 5 MB 的壳；因为业务服务本体（Node + 原生模块）的体积和打包复杂度并不会因为壳变小而消失
- 于是评判标准从"渲染性能 / 包体"转向 **"哪条路能最省事地把一个带原生模块的 Node 服务 + 一个托盘 + 三平台安装包做出来"**

另一个推论：因为不开窗口，**Electron 的渲染进程根本不会启动**，常驻内存只有 main 进程（Node + 少量 Chromium 基础设施），实测量级 ~70–110 MB，而不是网上常说的"Electron 起步 300 MB"。

### 4.3 被推翻的决定性因素：原生模块打包

初版在此处写的是："记忆能力要集成 SQLite + sqlite-vec 即 Node 原生模块，只有 Electron 的 `@electron/rebuild` + `asarUnpack` 路径成熟，SEA/pkg 是坑，所以必选 Electron"。

**实证推翻这个判断**。QoderWake 的做法（附录 A.2）是：

```
resources/sqlite-vec/<platform>-<arch>/vec0.so     ← 预编译二进制，按平台平铺
运行时 sqlite load_extension() 动态加载，**不参与主二进制编译**
```

这把问题从"打包器能不能处理 `.node`"降级为"CI 能不能把几个 `.so/.dylib/.dll` 放对目录"。后者是现代打包器的基本能力，不构成选型约束。三点说明：

1. **sqlite-vec 官方就发 loadable extension**（`.so/.dylib/.dll`），并非只有 Node 原生模块一种形态。走 loadable extension 路径时，它与宿主运行时的 ABI **解耦**——不需要 rebuild。
2. **Bun 内置 SQLite**（`bun:sqlite`），不需要 `better-sqlite3` 这类原生模块，也就不存在 ABI 重编问题。
3. 即使将来确实需要某个真正的 `.node`，也可重用同一套「外挂 + 运行时解析路径」机制，而不必为此引入一整个 Chromium。

> 结论：原生依赖**不再是选型的决定性因素**。一旦去掉这条约束，Electron 在本场景就只剩下「现成的 Tray API + electron-builder」两个便利，为此背上一整个不渲染任何东西的 Chromium，与「越轻量越好」直接冲突。

### 4.4 为什么不选 D（Python）

1. 与白皮书 §9.4 明文"不采用 Python 双语言（工作台是 TS）"直接冲突
2. 记忆 SDK 主力是 TS（105 个 API 端点的 TS SDK；Python SDK 为副）
3. 前端构建链本就在 Node 生态，选 Python 后端等于必然双运行时
4. PyInstaller 打包 + Linux 托盘 GTK 依赖，工程摩擦大

**对 Python 编排引擎的处置建议**：白皮书 §4.2 的"纯 Python 零依赖"是 1.0 的实现事实，不是 2.0 的约束。引擎逻辑本体是状态机 + 节点图 + gate 判定，**纯逻辑、零 IO 密集、零第三方依赖**，重写为 TS 的成本可控（估 1–2 人周），换来的是单运行时安装包。若坚持保留 Python 引擎，安装包需内嵌 python-build-standalone（+~40 MB）并处理三平台解释器分发 —— 不推荐，但作为 D-a 的备选记录在案。

### 4.5 裁决（v2）

| 项 | 初版裁决 | **v2 裁决** | 变更理由 |
|----|---------|-----------|---------|
| 服务形态 | Electron 宿主 | **单体可执行，首选 Bun `--compile`**（备选 Node SEA） | 原生依赖约束解除（§4.3）；轻量优先 |
| 桌面壳 | Electron（必选） | **可选极薄壳，Windows/macOS 才做，Linux 不发** | 壳与服务解耦（C-4）；不阻塞主链路 |
| 进程守护 | 自研 ServiceSupervisor | **systemd / launchd / schtasks** | C-5，见 §7 |
| 工作台后端 | TS / Node ≥22.16 + Fastify | **TS；运行时 Bun（兼容 Node 语义），HTTP 框架首选 Hono** | Hono 与 MemoryProxy 一致且跑得动 Bun/Node/Workers。实证参照用的是 Express（291 处引用），说明成熟 Node 框架在 Bun 上生产可行 —— 框架风险低于预期，但**框架 API 必须收敛到单个 route-registry adapter**，业务模块不直接碰框架（参照物做法，见源码拆解 §4.1） |
| 工作台前端 | Vue 3 + Vite | **Vue 3 + Vite（不变）** | 与管控平台一致、人力可流动；实证参照用 React 不构成改变理由 |
| 编排引擎 | 重写为 TS | **重写为 TS（不变）** | — |
| 打包 | electron-builder | **先只出单体二进制 + 安装脚本**；Windows 安装器（NSIS/Inno）后补 | 轻量优先；0.1 阶段不必先做安装器 |
| monorepo | pnpm workspaces | **pnpm workspaces（不变）**：`workbench-service` / `workbench-web` / `workbench-tray`（可选）/ `shared-protocol` | `workbench-launcher` 改名为 `workbench-tray` 并降为可选包 |

> ⚠️ Bun 作为生产运行时的主要残留风险：生态兼容性（部分 Node 原生模块/API 边角）与团队熟悉度。记为 **R-10**，缓解：业务代码只写标准 TS + Web 标准 API，不用 Bun 专有语法，保留回退到 Node SEA 的能力（T3 验证）。实证参照给了这条缓解一个有力背书：一个 63 MB 的生产 Bun 应用里 `child_process` 出现 72 次、`Bun.spawn` 只有 1 次，Bun 专有 API 基本只集中在 SQLite 一处 —— 「以 Bun 为运行时但不被 Bun 锁定」是可达成的工程状态。

## 5. 推荐架构：Service 为主 + Shell 可选

### 5.1 进程模型

```
【OS 守护层】systemd --user / launchd / schtasks
     │  Restart=always · 退避 · 开机自启 · 进程组连带回收
     ▼
┌──────────────────────────────────────────────────────┐
│ Workbench Service（单体可执行，唯一常驻进程）        │
│   ├─ Hono: /healthz /api/** /events(SSE) + 静态前端  │
│   ├─ 写 run/service.json（pid/port/version/instance）│
│   ├─ 写 run/reliability.json（cleanStop 崩溃检测）   │
│   ├─ sqlite + sqlite-vec（外挂 extension）           │
│   └─ CLI 子命令 start/stop/status/portal/update      │
└──────────────────────────────────────────────────────┘
     ▲  仅 HTTP /healthz + 读 run/service.json
     │
┌──────────────────────────────────────────────────────┐
│ Tray Shell（可选 · Win/macOS · 独立版本号 · 零业务） │
│   └─ 图标 + 右键菜单 + 调 CLI/HTTP + 开默认浏览器    │
└──────────────────────────────────────────────────────┘
                    ↓
          系统默认浏览器 → http://127.0.0.1:19820
```

关键变化（对初版）：**Launcher 不再是父进程**。初版是「Launcher 拉起并守护 Service」，现在是「OS 守护 Service，Shell 只是一个旁观的遥控器」。Shell 挂了、没装、没做，Service 都照常跑。

> **v3 边界收紧**：Windows 实证里的参照物恰好走到了反面 —— 它把保活责任**全部**放在托盘进程里（§8.2），等于又把 Shell 变回了事实上的父进程，且没有 OS 级兜底。本方案的 Shell **只做 health 探活与快速恢复，不承担唯一保活责任**（§7.1.2）。

### 5.2 0.1 阶段的最小可用形态

按「越轻量越好」，0.1 建议直接砍掉托盘：

| 阶段 | 交付 | 用户操作 |
|------|------|---------|
| **0.1**（最小） | 单体二进制 + `install.ps1` / `install.sh` | `workbench start` → 自动注册 OS 守护 + 自动开浏览器 |
| **0.2** | 加 Windows 托盘壳 | 托盘右键菜单 |
| **0.3** | 加 macOS 托盘壳 + 安装器 | 双击安装 |
| Linux | 永不发壳 | 仅 CLI + systemd |

这样 0.1 的桌面层工作量为 **0**，全部精力在 Service 本体。托盘是 0.2 的增量，不占 0.1 工期。

### 5.3 Shell ↔ Service 契约（C-4 的落点）

Shell（以及任何外部工具）对 Service 的全部认知仅限以下契约，任何满足该契约的实现都可被遥控：

| 契约项 | 定义 | 实证参照 |
|--------|------|---------|
| 启动 | 监听 `127.0.0.1:19820`，就绪后 `/healthz` 返回 200 | QoderWake `/healthz` 200 无鉴权 |
| 健康 | `GET /healthz` → `{ app, status, version, pid, uptime, dataDir }` | 同 |
| **发现** | `run/service.json` 含 `pid / port / host / version / startedAt / uid / instanceId / buildCommitId` | `run/daemon.info.json` 字段同构 |
| **崩溃检测** | `run/reliability.json` 含 `{ runId, startedAt, cleanStop }`；干净退出置 `true`，启动时读到 `false` 即知上次是崩的 | `run/daemon-reliability.json` |
| 身份区分 | `uid` 装机稳定（区分机器），`instanceId` 每次启动新生（区分本次运行）——两者分开才能判定"端口被自己占"vs"被第三方占" | 同 |
| 优雅退出 | 收到 SIGTERM 后 ≤5s 内释放端口并置 `cleanStop=true` | `SuccessExitStatus=0 143` |
| 日志 | 主日志 + **生命周期日志分离**（后者只记启停/升级/崩溃，体积小、排障先看它） | `qoderwake.log` 9 MB vs `qoderwake_lifecycle.log` 61 KB |

│   └── settings.sample.json

├── data/
│   ├── store/                sqlite（WAL）
│   └── storage-state.json    ⭐ storageSchemaVersion + lastOpenedByVersion（拒绝降级启动）
├── resources/
│   └── sqlite-vec/<os>-<arch>/   外挂 extension，按平台平铺

**配置两层分离**（实证借鉴，附录 A.4）：`config.json` = 运行时基础设施（运维关心），`settings.json` = 用户偏好与业务开关（产品关心）。实际文件**只写覆盖项**，其余走代码默认；同时发一份 `*.sample.json` 全量带注释示例，比写配置文档管用。

**v3 新增的四处都来自 Windows 实证（源码拆解 §8.9）**，每一处都对应一类已发生的事故：

| 新增项 | 它防的是什么 | 实证依据 |
|--------|------------|---------|
| `run/workers.json`（pid + **pgid** + lastSeenAt）| 杀一个会话要杀**整个进程组**（底座 CLI 下面还有它自己拉的 shell/编译器）；`lastSeenAt` 让 daemon 重启后能判定哪些 worker 是孤儿 | 参照物 `daemon.workers.json` 已是 `schemaVersion: 2`，字段含 sessionId/pid/pgid/agentId/status/lastSeenAt |
| `run/sentinels/` 哨兵文件 | 区分「用户主动选了 false」与「我们默认过一次且用户没改」—— 这两种状态在单个布尔配置项里无法表达，导致的经典 bug 是「用户关了自启，升级后又被打开」| 参照物有 `windows-tray-launch-at-login-defaulted` 这类哨兵，与 `settings.json` 里的 `launchAtLogin: false` 共存 |
| `data/storage-state.json` | 两个字段答两个不同问题：`storageSchemaVersion` 管「这份数据能不能被当前代码读」，`lastOpenedByVersion` 管「用户是不是在降级」。不从第一天写，日后无法安全拒绝降级启动 | 参照物 `.pre-upgrade-backup-state.json`：`storageSchemaVersion: 8` + `lastOpenedByVersion: 0.2.3` |
| 日志四类分文件 + **统一轮转** | 参照物的分文件分得对（读者不同：开发/运维/支持/业务），但**轮转只在服务路径配了**，默认路径累到 14.4 MB 单文件 —— 轮转被误当成 keepalive 的附属能力 | §8.3 vs §8.9 两处对比 |

> 一条工程原则从上表最后一行提炼出来：**日志轮转属于日志子系统，不属于启动路径**。不管服务是被计划任务、托盘、CLI 还是前台拉起的，轮转策略必须一样生效（W-7）。

### 5.5 Bootstrapper：拉起路径的唯一入口（0.2+ 引入）

> v3 新增。来自 Windows 实证的一个结构性发现（源码拆解 §8.3 / §8.4 / §8.6）。

实证里三条拉起路径——WinSW 服务定义的 `<executable>`、托盘日志里的 `run: qoderwake-bootstrapper.exe`——**全部指向同一个 bootstrapper，而不是业务二进制本体**。这不是巧合，是三个好处：

1. **自更新与守护注册解耦**。换 daemon 不动服务/任务注册 —— Windows 上重注册服务需管理员权限，这一层解耦直接决定了自更新能不能免 UAC。
2. **「选哪个版本」的逻辑只有一处**。pending update 的应用、降级判定、payload 展开全在 bootstrapper 里，不会散到托盘、服务、CLI 三处各写一份。
3. **安装器只落盘 bootstrapper + payload，不理解业务**。安装器因此可以很久不动 —— 实证里安装器 0.1.33 配 daemon 0.2.3，正是这个模型的后果。

**本方案的取舍（分期，记为 D-l）**：

| 阶段 | 是否引入 bootstrapper | 理由 |
|------|--------------------|------|
| **0.1** | **不引入** | 更新只做「检查 + 引导」（C-6），没有原地替换二进制的需求；守护配置直接指向 Service 本体，少一层就少一层 |
| **0.2+** | **引入** | 一旦做托盘 + pending update 原地应用，就必须让「拉起」与「选版本」分离，否则每次升级都要重注册守护配置 |

⚠️ **但有一条约束 0.1 现在就要守**：OS 守护配置里的 `ExecStart` / `<Command>` 必须指向**稳定路径**（如 `bin/current/workbench`，或一个不带版本号的固定名），**不得嵌版本号**。否则 0.2 引入 bootstrapper 时，所有已注册的守护配置都要做一次迁移 —— 而迁移失败的用户会变成「升级后服务不自启了」且难以远程诊断。这是零成本的前瞻。

### 6.2 状态灯语义

> v3 修订：原表的触发条件写的是 `/healthz`，方向是对的，但下面这条实证把它从「一个合理的选择」升级为「唯一可接受的选择」。

**探活的判据是「health 就不就绪」，不是「进程在不在」。** 实证日志里 `daemon process exists but health is not ready; skipping duplicate watchdog start` 这一行在两周内出现了 **19 次**（源码拆解 §8.6）——也就是说「进程活着但不能服务」在真实世界里是**常态而非异常**。只看 PID 的看门狗等于没看门狗：它会一直报绿，而用户打开浏览器是白屏。

| 图标 | 状态 | 触发 | 菜单变化 |
|------|------|------|---------|
| ● 绿 | 运行中 | `/healthz` 连续成功 | 显示"停止/重启"，"打开工作台"可用 |
| ◐ 黄 | 启动中 | 进程在（pid 存活）但 `/healthz` 未就绪 | 全部操作项禁用，防抖 |
| ○ 灰 | 已停止 | 用户主动停止 | 显示"启动服务"，"打开工作台"禁用 |
| ⚠ 红 | 异常 | 健康探测三连失败 / 端口冲突 | 显示"重启服务"+"查看日志"，气泡通知一次 |

⚠️ **黄态下壳必须 skip，不许重启。** 实证参照探到「进程在但不健康」时选择的是 skip 而非拉新进程——这个选择是对的：daemon 冷启动实测 **11 秒**（§8.5），若在这 11 秒窗口里因为「不健康」就重启，会造成重启风暴，而且每次都在同一个窗口里失败，永远起不来。判「真的挂了」必须以**连续三次探测失败 + 已超过冷启动预算**为条件，而不是单次不健康。

### 6.5 壳的实现形态：原生小二进制，且必须有身份

> v3 新增。本小节回答的正是 §6 头注里「待实证后再定」的那个问题（源码拆解 §8.6）。

实测的托盘壳 `qoderwake-tray.exe` = **89,072 字节（87 KB）的原生 exe**。这个数字直接完成了两件事：

1. **排除了 Electron / Tauri / 内嵌运行时任何一种可能**——这些方案的体量下限都在数 MB 到数十 MB。一个只做「图标 + 菜单 + 拉子进程 + 开浏览器」的壳，工业上的合理体量就是十万字节量级。
2. **坐实了 C-4（壳与服务独立）不只是版本号独立，而是全面独立**：版本源单独一份（`run\native-shell-version` = 0.0.20）、日志单独一份（`logs\qoderwake-tray.log`），与 daemon 完全不交叉。

→ **本方案的壳体量上限从「< 10 MB」收紧为「< 2 MB」，实现选型限在能出小原生二进制的路线**（原生 Win32 / Go systray / Rust 类），具体选哪条归 D-i 一并定。

⚠️ **但有一个代价，实证参照没付，我们必须付**：那个 87 KB 的 exe 的 VersionInfo 里仅有 `FileVersion = 0.0.20.0`，**CompanyName 与 FileDescription 均为空**。一个无发行信息、无签名、干的事是「开机常驻 + 拉子进程 + 开本地监听端口」的小原生 exe，在 EDR 与国内护航类安全软件眼里是**教科书级的可疑样本画像**。因此壳的两条硬要求：

| 要求 | 内容 |
|------|------|
| **完整 VersionInfo** | CompanyName / FileDescription / ProductName / LegalCopyright 全部填实，不得为空，也不得泄露构建工具（实证里 `bin\qoderwake.exe` 的 ProductName 竟是 **"Bun"**） |
| **代码签名** | 用户已明确不买签名证书（§8.1 口径）——但壳是常驻进程，风险高于一次性安装包。这构成一个**与现有口径的真实冲突**，不能用“应该没事”掩过去 → 归 **R-13** 与 **D-c** 一并裁 |

## 7. 服务生命周期管理（v2：委托 OS）

> v2 修订：初版设计了自研 `ServiceSupervisor`（健康探测 + 指数退避重启 + 自愈上限）。实证表明这套语义 systemd / launchd / schtasks **原生全部具备**，自研只会更差且多一份要维护的状态机。本节整体改为「OS keepalive 适配层」。

### 7.1 三平台守护配置对照

| 语义 | Linux (systemd --user) | macOS (launchd) | Windows (Task Scheduler) |
|------|----------------------|-----------------|--------------------|
| 崩溃自动重启 | `Restart=always` | `KeepAlive=true` | `<RestartOnFailure>` |
| 重启间隔 | `RestartSec=5` | `ThrottleInterval` | `RestartOnFailure/Interval` |
| 重启风暴熔断 | `StartLimitBurst=5` / `StartLimitIntervalSec=60` | `ThrottleInterval` 兜底 | `RestartOnFailure/Count` |
| **配置错误别徒劳重启** | `RestartPreventExitStatus=78` | 需自行判断退出码 | 需自行判断 |
| SIGTERM 视为正常退出 | `SuccessExitStatus=0 143` | 默认 | — |
| **连带杀子进程** | `KillMode=control-group` | 进程组 | job object |
| 启动/停止超时 | `TimeoutStartSec=30` / `TimeoutStopSec=30` | `ExitTimeOut` | — |
| **等网络就绪** | `After=` + `Wants=network-online.target` | — | — |
| 环境变量文件 | `EnvironmentFile=-<path>`（**前缀减号 = 文件不存在不报错**） | `EnvironmentVariables` | — |
| 开机自启 | `WantedBy=default.target` | `RunAtLoad=true` | `<LogonTrigger>` |
| **登出后仍存活** | `loginctl enable-linger $USER`（**不做则登出即被杀**） | 默认存活 | 默认存活 |

`RestartPreventExitStatus=78`（EX_CONFIG）与 `KillMode=control-group` 是两个值得直接抄语义的细节：前者避免"配置写错了还每 5 秒重启一次刷满日志"，后者保证 Service 派生的子进程（未来的底座 CLI 子进程）不会变成孤儿。

另有两条实现级的要求：

1. **渲染与反解析必须成对存在**（`buildSystemdUnit` 与 `parseSystemdExecStart` 那样）。只有能反解析已注册的守护配置，才能判它是否与当前版本一致，从而支持幂等重装与升级迁移。
2. **壳的登录自启与服务的 keepalive 是两份独立配置**，不共用 —— 佐证 C-4「壳与服务独立」。

#### 7.1.1 Windows：用 Task XML 导入，并覆写四个默认值

不用 `schtasks /create` 的命令行参数（含空格路径的引号转义是灾难），渲染完整 Task XML 再 `/XML` 导入：

| 字段 | 取值 | 为何重要 |
|------|-----|-----------|
| `<LogonTrigger>` | enabled | 登录即启动：**开机自启与 keepalive 是同一份配置**（D-e） |
| `<LogonType>` | **S4U** | Service-For-User：不需要存用户密码 |
| `<RunLevel>` | **LeastPrivilege** | 不要管理员权限 → per-user 安装免 UAC 的关键 |
| `<MultipleInstancesPolicy>` | **IgnoreNew** | 单实例由 OS 保证 |
| `<ExecutionTimeLimit>` | **PT0S** | ⚠️ 默认 72 小时后杀掉任务 |
| `<DisallowStartIfOnBatteries>` | false | ⚠️ 默认 true：拔电源后不启动 |
| `<StopIfGoingOnBatteries>` | false | ⚠️ 默认 true：切到电池就停服务 |
| `<StopOnIdleEnd>` / `<RestartOnIdle>` | false / false | ⚠️ 默认会因空闲策略停服务 |

标 ⚠️ 的四条是 **Windows Task Scheduler 对常驻服务而言全错的默认值**。照直觉用 `schtasks /create /sc onlogon`，会得到一个"用户拔掉电源就悄悄停掉、且 72 小时后被杀"的服务，而这类故障极难复现和归因。记为 **R-12**。

#### 7.1.2 Windows keepalive 路径：分期双层，不学参照物的托盘单点（v3 新增）

> 本小节是 v3 修订里唯一一处「实证推翻了推断，但我们不照搬实证」的地方，必须把理由写清楚。归 **D-k**。

先说实证结果（源码拆解 §8.2）。在一台长期使用的 Windows 25H2 机器上，计划任务、服务注册、HKCU/HKLM Run 键、启动文件夹 **四条路径全部为空**；实际生效的是托盘进程自己做看门狗，daemon 以 `start --no-keepalive` 被拉起。三条路径（WinSW 服务 / 计划任务 / 托盘看门狗）的料都预置在包里，但只启用了最后一条。

这确实推翻了本报告初版「Windows keepalive = 计划任务」的推断。但它同时**暴露了那条路的缺陷**：托盘进程一旦被杀（用户手动结束、崩溃、安全软件拦），**全链断且无 OS 级兜底**。参照物把保活责任从 OS 上移到了自己的托盘里，换来了「免注册、免管理员、有可见入口」，代价是引入了一个单点。

而本方案已裁定 **0.1 不包含托盘**（D-i）——若直接照搬实证口径，0.1 的 Windows 将**完全没有保活路径**。所以裁决是分期且双层：

| 阶段 | 进程级守护（「进程在不在」）| health 级探活（「能不能服务」）|
|------|------------------|---------------------|
| **0.1**（无壳）| **计划任务，唯一路径**（§7.1.1 四个默认值必覆写）| `workbench status` 里报 health；无常驻探活者，不假装有 |
| **0.2+**（有壳）| **计划任务仍保留**，作为 OS 级兜底 | **托盘壳做 health 探活**（§6.2），认定不健康才重启 |
| **企业批量**（可选）| WinSW 类真服务 + `<onfailure>` 三步退避（§5.5 / 源码拆解 §8.3）| 同上 |

三条得失说明：

1. **不取消计划任务**。它是唯一能在「托盘被杀」与「用户从未装壳」两种情况下都成立的路径，且 `LogonType=S4U` + `RunLevel=LeastPrivilege` 已经做到免 UAC（§7.1.1）——参照物避开它的理由（需注册）在我们这里成本很低，因为 Service 自己就会写守护配置（§7.2）。
2. **托盘只加一层，不拿走一层**。壳负责 OS 管不了的那一半（health），不负责 OS 已经管得很好的那一半（崩溃重启/退避/开机自启）。这也是 C-7「壳是便利层不是必需层」能继续成立的前提。
3. **必须在 T4 验收里直接打这个点**：手动结束托盘进程后，服务能不能恢复？不能则双层没落实（W-2）。

一句话：**计划任务保「进程一定在」，托盘保「进程一定能服务」，两者不互为替代。**

### 7.2 Service 自带的注册/注销能力

Service 二进制自己负责写/删平台守护配置，用户不需要手工碰 systemd 或注册表：

```
workbench start              → 注册 OS 守护 + 启动 + 首次自动开浏览器
workbench start --foreground → 前台跑，不注册守护（调试/CI/容器）
workbench start --no-keepalive → 起服务但不注册守护（临时用）
workbench stop               → 停止（保留守护注册）
workbench uninstall          → 注销守护配置 + 清理
workbench status             → 输出 JSON：pid/port/version/uptime/健康
workbench activity           → ⭐v3 新增：输出在飞任务数（优雅停服的判据，见下）
workbench portal [--print-url] → 打开浏览器（或仅打印 URL）
```

`--foreground` / `--no-keepalive` 的必要性：容器、CI、以及"我只想临时跑一下别把我系统改了"的场景。这也是 §10.3 降级路径的落点。

两条 v3 新增的约定（源码拆解 §8.6 / §8.8）：

1. **内部子命令用 `__` 前缀隐藏**。实证里 `__daemon`、`__browser_native_host` 这类双下划线子命令不进 `--help`，只给壳/安装器/浏览器插件调。好处是**公开 CLI 面与内部 IPC 面分开**：公开面要保兼容，`__` 面可以随时改，不构成对外承诺。
2. **优雅停服需要一个「在飞任务」查询接口**。实证托盘日志里有 `runtime activity resolved: conversationTasks=0 triggerTasks=0 preciseConversationTasks=True` ——也就是说壳在执行 stop 之前先问了一句「现在有没有正在跑的任务」。对我们同样成立：工作台停服时可能正有数字员工在执行任务，**拿到 stop 不能直接 kill**，而要先查、再提示用户确认或等待。

### 7.3 启动序列

```
1. 读 config/config.json（端口默认 19820）
2. 读 run/reliability.json → cleanStop === false 则记一条「上次异常退出」到 lifecycle.log
3. ⭐ 读 data/storage-state.json → storageSchemaVersion 高于本二进制所支持的版本
   → **拒绝启动**（退码 78）+ 提示「数据由更新版本 v… 写过，请升级而不是降级」
4. 端口探测：
   ├─ 空闲                              → 起服务
   ├─ 被占 + /healthz 是自家 app + uid 匹配 → 已在运行，直接打开浏览器后退出（幂等）
   └─ 被占 + 不是自家                    → 报错退出（码 78，OS 不会徒劳重启）+ 打印占用进程名
5. ⭐ 读 run/workers.json → 回收上一个生命周期遗留的孤儿子进程（§7.5）
6. ⭐ 磁盘 GC：清过期 updates/ 包 + 轮转超额日志（§8.4）
7. 起服务 → 写 run/service.json + reliability.json{cleanStop:false}
8. 就绪（**以 /healthz 真的返回 ok 为准，不是以进程 spawn 成功为准**）
   → lifecycle.log 打一条启动横幅（版本/commit/运行时/OS/端口/存储后端）
9. 首次安装 → 自动打开一次浏览器；后续启动不自动打开（哨兵文件记「已打开过」，§5.4）
```

启动横幅值得照做：把版本、commit、运行时、平台、端口、存储后端一次性打进 lifecycle.log，用户报障时截这一段就够定位环境。

标 ⭐ 的三步是 v3 新增，分别堆在三条实证上：

| 新增步 | 它防的是什么 | 实证依据 |
|--------|------------|---------|
| 第 3 步 存储版本门 | 旧版本启动后把新版写过的 sqlite 读坏或写坏 | `.pre-upgrade-backup-state.json` 同时存 `storageSchemaVersion: 8` 与 `lastOpenedByVersion: 0.2.3` 两个字段（W-15）|
| 第 5 步 孤儿回收 | 上次崩溃遗留的子进程占端口，导致本次误判端口冲突 | `daemon.workers.json` 记 pid + pgid + lastSeenAt（W-14）|
| 第 6 步 磁盘 GC | profile 无上限膨到 785.8 MB（其中 327 MB 是从未用上的包）| §8.5 pending 悬挂 15 天（W-6）|

关于第 8 步的「以 /healthz 为准」：这不是洁癖。实证里 daemon 冷启动要 **11 秒**（§8.5），这 11 秒里进程已在但服务不可用。若把「启动成功」定义在 spawn 返回上，那么 `workbench start` 会在服务就绪前 11 秒就退出并报成功，壳随即打开浏览器 → 用户看到白屏。启动的完成判据必须是 health（同 §6.2）。

### 7.4 单实例语义（对既有设计的 refinement）

既有设计（员工运行与展示设计 v0.1 §7）写的是"19820 被占则提示并**拒绝二次启动**"。本方案建议区分两种情况 —— **同一应用二次启动**是高频正常操作，直接报错是糟糕体验：

| 场景 | 既有设计 | 本方案建议 |
|------|---------|-----------|
| 重复执行 `workbench start` / 重复点图标 | 提示并拒绝 | **幂等**：不起新进程，直接打开浏览器 |
| 端口被第三方程序占用 | 提示并拒绝 | 报错退出码 78 + 打印占用进程名 + 提示改端口 |
| 旧实例僵死（文件在但无响应） | 未定义 | 检测 pid 存活 + `/healthz`；确认僵死则清 run/ 接管 |

→ 记为 **D-d**，需要用户确认并回写既有设计文档。

### 7.5 退出与清理

停止时：置 `reliability.json{cleanStop:true}` → 关闭 HTTP（≤5s）→ 删 `run/service.json` + `service.lock` → 退出码 0。**必须保证退出后端口释放**，否则下次启动会误判端口冲突。

两条实现级要求（来自实证的 Windows 踩坑沉淀）：

1. **spawn 子进程时显式不继承句柄**。若未禁止继承，子进程会拿到监听 socket 句柄；主进程退出后端口仍被一个与服务无关的子进程（比如一个 CLI 子任务）持有，表现为"服务已停但端口还占着"。这是根治，比事后清理便宜得多。
2. **停止流程里主动验证端口真的释放**，而不是"进程退出就算停好了"。Windows 上可用 `Get-NetTCPConnection -State Listen` 轮询；若发现 owner 已退出而端口仍 Listen，即上述句柄继承孤儿，只清理**路径属于本安装目录**的进程，不碰第三方。

#### 7.5.1 子进程账本：光靠「不继承句柄」不够（v3 新增）

上面两条是预防，但预防会失效（服务被 `kill -9`、掉电、OOM 时根本没机会跑清理）。实证参照物给出了补充答案：`run\daemon.workers.json`（`schemaVersion: 2`）把每个子进程记成一条带 **`pid` + `pgid` + `lastSeenAt` + `sessionId` + `status`** 的账。

两个字段值得单独指出：

| 字段 | 为何必需 |
|------|---------|
| **`pgid`**（进程组）| 子进程自己又会拉孙进程（底座 CLI 拉模型进程）。只记 pid 只能杀儿子，孙子仍会活下来并持续占资源；杀整组才干净（对应 systemd 的 `KillMode=control-group`）|
| **`lastSeenAt`** | 区分「正在跑的任务」与「上一个生命周期遗留的尸体」。没这个时间戳，启动时就不敢杀任何东西（怕杀错活任务），于是孤儿永远不会被回收 |

→ 启动时（§7.3 第 5 步）遍历 `workers.json`：`lastSeenAt` 过期 + 进程仍存活 + **可执行文件路径属于本安装目录** → 按 pgid 杀整组，并往 lifecycle.log 记一条。三个条件必须同时成立，少一个就有误杀第三方进程的风险。归 **R-16**。

#### 7.5.2 清理逻辑抽成独立脚本（v3 新增）

实证里的清理不写在安装器脚本里，而是一份独立的 `qoderwake-cleanup.ps1`（10,087 字节）。这个选择的价值在于**同一份清理逻辑能被三个场景复用**：卸载、修复安装、用户手动排障。如果写在 Inno / NSIS 脚本里，它就只能在卸载时跑，而「我想把它清干净重新装一次」是排障时最常用的一招。

→ 本方案把清理做成 **`workbench uninstall --purge`（子命令）+ 安装包内一份可单独跑的脚本**两个入口共用一份实现，且卸载器只调它，不自己写一份（W-11）。

> 0.2+ 的 Windows 自更新需要更进一步的"重启交接"机制（外部脚本 + 独立交接日志 + 分层等待），详见源码拆解 §5.5。0.1 的更新只做"检查 + 引导"，不需交接脚本；但上面两条现在就要做对。

## 8. 检查更新（无签名证书路径）

### 8.1 用户口径

用户明确：要"检查自动更新"，但**不需要签名证书**。这两点在技术上有硬冲突 —— 所以方案取"检查 + 引导"，不取"静默替换"。

外部事实核验：

| 事实 | 来源 |
|------|------|
| electron-updater：**macOS 必须代码签名**才能自动更新，否则不可用 | electron.build 官方文档 Auto Update 章节 |
| electron-updater：Windows NSIS **未签名可以完成自动更新**，但用户会遇到 SmartScreen 警告 | 官方文档 + 社区实践 |
| Tauri updater：**签名不可关闭**，但用的是自生成 minisign 密钥对（≠ 商业代码签名证书），无采购成本 | v2.tauri.app/plugin/updater |

结论：**跨平台一致、零证书成本的唯一稳妥形态是"检查 + 引导下载"**。

### 8.2 实现设计

更新源发布一份清单：

```json
{
  "version": "0.2.0",
  "releasedAt": "2026-09-01T00:00:00Z",
  "notes": "新增群组协作；修复端口冲突误判",
  "minSupported": "0.1.0",
  "artifacts": {
    "win-x64":   { "url": "https://…/ieidev-workbench-0.2.0-x64.exe",     "sha256": "…", "size": 98123456 },
    "mac-arm64": { "url": "https://…/ieidev-workbench-0.2.0-arm64.dmg",   "sha256": "…", "size": 95123456 },
    "linux-x64": { "url": "https://…/ieidev-workbench-0.2.0-x86_64.AppImage", "sha256": "…", "size": 96123456 }
  }
}
```

流程：

```
触发（启动后 30s 延迟 + 每 24h + `workbench update --check` 手动 + 壳菜单）
  → HTTPS GET manifest.json（超时 5s，失败静默，仅手动触发时报错）
  → semver 比较（三类制品各自比）
  → 有新版：`workbench status` 与 lifecycle.log 提示；有壳时额外加角标
  → 确认升级：下载到 ~/.ieidev-workbench/updates/
           → 校验 sha256 → 不匹配则丢弃并报错
           → 匹配则：先备份数据目录（§9.2）→ 停服务 → 换二进制 → 重启
  → GUI 安装包路径（P1）：下载后交给系统安装器，用户手动完成（Windows 会有 SmartScreen 警告，安装说明中预先告知）
```

安全要点：

- 更新源**必须 HTTPS**，并校验 `sha256`（弥补无代码签名的完整性缺口）
- `minSupported` 用于将来强制升级（协议不兼容时）
- 不做静默后台替换 —— 既避开签名要求，也避免"用户不知情被换版本"的合规问题
- 只在用户点击时下载，默认不预下载（省流量）

### 8.3 未签名分发的用户摩擦（必须写进安装说明）

| 平台 | 摩擦 | 缓解 |
|------|------|------|
| Windows | SmartScreen「未知发布者」警告 | 安装文档明确指引"更多信息 → 仍要运行"；提供 sha256 供核验 |
| macOS | Gatekeeper 拦截未签名/未公证应用 | 指引右键"打开"，或 `xattr -dr com.apple.quarantine /Applications/…app` |
| Linux | AppImage 需 `chmod +x` | 安装脚本自动处理 |

→ 后续若要消除摩擦，需采购 Windows OV/EV 证书 + Apple Developer 账号（macOS 公证）。记为 D-c 的备选。

### 8.4 pending 态的生命周期与磁盘预算（v3 新增，C-8 的落地）

> 本小节是实证里**唯一一个真正在现场跑坏了的机制**，不是推测风险。它同时过不了三关：时机、可见性、磁盘。

实证字段（源码拆解 §8.5）：

| 项 | 值 |
|----|-----|
| `bin\.pending-update\.pending-version` | **0.2.4**，落盘于 2026-08-05 |
| `bin\.installed-version` | 仍为 **0.2.3** |
| 悬挂时长 | **15 天**（取证日 2026-08-20）|
| 占盘 | **327.2 MB**，占 `.qoderwake` 总 **785.8 MB** 的 **42%** |
| 用户感知 | 无——UI 上没有任何 pending 痕迹，用户以为自己在最新版 |

根因不是 bug，是**设计上只给了一个应用时机**：下一次重启交接。而一个常驻服务在用户不主动重启、也不崩溃的情况下，可以一直不重启。于是下载完成到实际生效之间出现了一个无上限的黑洞。

本方案的三条硬要求：

| # | 要求 | 具体 |
|---|------|------|
| **1. 应用时机多于一个** | 除「重启交接」外，至少再给两个：**用户主动点「立即重启以应用」**（§6.1 菜单）+ **空闲窗口兜底**（无在飞任务且超过 N 小时未应用，自动重启并应用）| 在飞任务判据用 `workbench activity`（§7.2）|
| **2. pending 必须可见** | 三处都要报：`workbench status` 的 JSON 里多一个 `pendingUpdate` 字段、lifecycle.log 每次启动打一行、有壳时菜单里一行 | 否则这类故障无法远程诊断 |
| **3. 磁盘 GC + 预算上限** | 启动时（§7.3 第 6 步）清：`updates/` 里**超过 7 天未应用的包直接删**（下次需要重下，代价远低于占盘）、日志轮转超额部分删；并对 profile 总体积设一个告警阈值（建议 500 MB）写进 lifecycle.log | W-6 |

⚠️ 另有一条与上面三条同等重要的量化约束：**一次自更新的服务中断实测 ≈ 17 秒**，其中 **11 秒是 daemon 自身冷启动**，替文件只花 **0.85 秒**（§8.5 时间线）。两个推论：

1. **想缩短升级中断，要优化的是冷启动，不是交接流程**。把功夫花在交接脚本上是优化错的对象。
2. **17 秒就是「自动兜底应用」必须选空闲窗口的理由**。十几秒不可用如果落在用户正在用的时候，体验很差；落在空闲时完全无感。

否则交接还有两个实现级坑要一并防（归 §7.5 与 T10）：**端口固定继承**（交接命令里写死 `--port 19820`，好处是客户端不需重新发现，代价是一旦端口被孤儿子进程占着就卡死 → 必须配套强制验证端口释放）；**日志编码不一**（实证里 `.cmd` wrapper 写的是 GBK、PowerShell 写的主交接日志是 UTF-8，同一事件两种编码 → 全部统一 UTF-8，`.cmd` 里先 `chcp 65001`）。

## 9. 打包与分发矩阵

### 9.1 产物矩阵（v2：三类制品独立版本化）

实证参照的发布清单是**三层制品 + 壳/服务/CLI 各自独立版本号**（附录 A.1），本方案照此组织：

| 制品类 | 平台 | 形态 | 优先级 | 备注 |
|--------|------|------|--------|------|
| **① Service 裸二进制** | win/mac/linux × x64/arm64 | `.tar.gz` / `.zip` | **P0** | 供安装脚本与自更新拉取；带 sha256 |
| ① 安装脚本 | mac/linux | `install.sh`（`curl … \| bash`） | **P0** | 对齐 D-005 |
| ① 安装脚本 | Windows | `install.ps1` | **P0** | 免安装器先跑通 |
| **② GUI 安装器** | Windows x64 | NSIS / Inno exe | P1 | per-user 安装免 UAC，装到 `%LOCALAPPDATA%`；**内含 Service + Tray Shell** |
| ② GUI 安装器 | macOS arm64/x64 | dmg | P2 | 含 `LSUIElement=true` 隐 Dock |
| ② GUI 安装器 | Linux | — | **不做** | 只给脚本 + systemd（C-7） |
| **③ Tray Shell** | Windows / macOS | 独立 `.zip`，独立版本号 | P1 | 可单独更新，不跟 Service 版本锁死 |
| 全平台 | CLI 入口 `workbench` | 就是 Service 二进制本体 | **P0** | 单体二进制兼任 daemon 与 CLI |

> 制品版本独立的价值：托盘壳改一个图标不必重发整个 Service；Service 修一个 bug 不必重签整个安装包。代价是发布清单要多维一层绑定关系（`bundled: {service, shell}`）。

#### 9.1.1 版本线独立≠用户可见版本多个（v3 新增）

实证把「制品版本独立」这个对的决策做出了一个错的后果（源码拆解 §8.1）：

| 件 | 版本源 | 实测值 |
|----|--------|-------|
| 安装器 | HKLM Uninstall `QoderWake_is1` | **0.1.33** ← 「应用和功能」里显示的是这个 |
| daemon | `bin\.installed-version` | **0.2.3** ← 用户心里的「版本」是这个 |
| 托盘壳 | `run\native-shell-version` | **0.0.20** |

三条线完全错开。直接后果：**用户报障时说的版本号与研发看的版本号不是同一个东西**，取证时会白走弯路。

→ 本方案的两条硬规（W-12）：

1. **存一个「用户可见版本」并处处报它。** 安装器写入 Uninstall 项的 `DisplayVersion` **必须是 Service 版本**（不是安装器自己的版本）；`关于` 菜单、`workbench status`、启动横幅、报障模板里报的都是它。
2. **内部仍保留三条独立版本线**，但 `workbench status --verbose` 一次性把三个都打出来（service / shell / installer），供取证。用户看一个，研发看三个。

### 9.2 关键打包要点（v2）

| 项 | 做法 | 原因 |
|----|------|------|
| 服务编译 | `bun build --compile --target=bun-<os>-<arch>` | 一次出单文件，目标机无需装运行时 |
| **二进制 strip** | 发布前 `strip`，不带 sourcemap | 实证参照的 161 MB 二进制 **not stripped 且内嵌完整可读 JS 源码**，等于源码裸奔——这是反面教材 |
| **⭐ VersionInfo 重写** | 每个发布的 exe/dylib 都重写 CompanyName / FileDescription / ProductName / LegalCopyright / FileVersion | 实证里 `bin\qoderwake.exe` 的 ProductName 竟是 **"Bun"**、FileVersion 1.3.12（即构建工具的元数据没改），而 87 KB 托盘壳的 CompanyName **直接为空**。前者在企业环境会引发合规质询，后者会被 EDR 当可疑样本（§6.5 / R-13）|
| 前端产物 | 嵌入二进制（Bun 支持 embed static）或放 `resources/web/` | 两种都行，T3 实测取体积更小者 |
| 原生依赖 | `resources/sqlite-vec/<os>-<arch>/` 平铺，**不编入** | §4.3 |
| Windows 安装器 | **per-user（免 UAC），只写 HKCU，装到 `%LOCALAPPDATA%\Programs\ieidev-workbench\`** | 降低企业环境阻力。实证参照选的是 per-machine（HKLM，开局就要 UAC）却又没注册服务、自启也走托盘——**花了 UAC 的价钱，没享到 per-machine 的好处**（源码拆解 §8.4）|
| **⭐ 不装到非标准位置** | per-user 用 `%LOCALAPPDATA%\Programs\`，per-machine 变体用 `%ProgramFiles%` | 实证参照装到 `C:\Software\QoderWake\`，既不符合惯例也容易被企业策略拦 |
| **⭐ 清理脚本独立** | 安装包内带一份可单独跑的清理脚本，卸载器只调它 | 可被卸载/修复/手动排障三场景复用（§7.5.2 / W-11）|
| 升级备份 | 升级前自动备份数据目录，保留 N 份可配 | 实证参照 `backup.preUpgrade{enabled, retentionCount}` |
| **⭐ 企业变体另出** | per-machine 变体只为企业批量部署出，且它才注册真服务（WinSW 类）| 两个变体各自自洽：要 UAC 就要把 UAC 的好处吃掉 |

### 9.3 CLI 入口与 D-005 的对齐

D-005 定的是"macOS/Linux 用 `curl … | bash` 或 `npm install -g`，Windows 提供 exe"。v2 方案天然对齐：**单体二进制本身就是 CLI**，无需额外 bin 包装。

| 交付 | 形态 | 适用 |
|------|------|------|
| **脚本安装**（P0） | `curl … \| bash` / `install.ps1` → 下二进制 + 注册 OS 守护 | 开发者、服务器、所有 Linux |
| **GUI 安装包**（P1） | Windows exe（含托盘壳） | 主流 Windows 用户 |
| **纯 CLI 使用** | `workbench start --foreground` 等，见 §7.2 | CI、容器、无桌面 |

### 9.4 CI 出包

三 job 并行：`windows-latest` / `macos-14`（arm64）/ `ubuntu-22.04`（低版本 glibc 保兼容）→ 产物 + 生成发布清单（含各制品 sha256 与版本号）→ 发布到 Releases / 内部对象存储。

> v2 变化：初版写"必须在对应原生平台构建（原生模块 rebuild 需要）"。改用外挂 extension 后，**Service 本体可以交叉编译**（`bun --target`），只有 GUI 安装器与托盘壳仍需对应平台。这又省一层 CI 复杂度。

**v3 新增三条卡口（W-13），均来自实证里现存的反面例**：

| 卡口 | 规则 | 防的是 |
|------|------|--------|
| **拒 dirty 构建** | 工作区不干净（`git describe` 带 `-dirty`）则 CI 直接失败，不出制品 | 发出一个无法从 commit 重现的二进制，事后无法取证 |
| **锁运行时版本** | Bun / Node 版本写进仓库（`.bun-version` 类）并在 CI 校验，不跟 latest 跑 | 运行时小版号跳动导致只在某些发布上出现的行为差异 |
| **VersionInfo 作为发布门** | 构建后自动校 exe 的 CompanyName / FileDescription / ProductName 非空且不含构建工具名 | 就是 §9.2 那两条（ProductName="Bun"、CompanyName 为空）——人记不住，必须机检 |

## 10. 跨平台差异与降级策略

### 10.1 差异总表

| 维度 | Windows | macOS | Linux |
|------|---------|-------|-------|
| 托盘机制 | 通知区域（Shell_NotifyIcon） | 菜单栏 NSStatusItem | StatusNotifierItem / AppIndicator |
| 图标可能不可见 | 被折叠进"隐藏的图标"（Win11 默认） | 菜单栏空间不足时被挤掉 | **GNOME 默认不支持，需装扩展** |
| 图标格式 | .ico 多尺寸 | 模板图（黑+alpha） | 22/24px PNG |
| 左键行为惯例 | 单击即执行主操作 | 单击弹菜单 | 不统一 |
| Dock/任务栏隐藏 | 无窗口天然不占 | 需 `LSUIElement=true` | 无窗口天然不占 |
| 系统通知 | 原生 Toast | 通知中心（需用户授权） | libnotify（可能缺失） |
| 安装摩擦 | SmartScreen | Gatekeeper/公证 | chmod +x |

### 10.2 Linux 托盘：直接不做

外部核验：Tauri/Electron 在 Linux 的托盘均依赖 `libayatana-appindicator`/`libappindicator3`，而 **GNOME（Ubuntu/Fedora 默认桌面）自身不实现 StatusNotifierItem**，需用户安装 `AppIndicator Support` 扩展，否则**图标完全不显示**。这不是可以靠代码绕过的问题。实证参照亦无 Linux 壳（附录 A.1）。

因此 v2 直接裁定：**Linux 不发壳**（C-7 / D-h），不花力气做一个一半用户看不见的图标。Linux 入口 = CLI + systemd + 浏览器。

### 10.3 无壳运行是一等公民，不是降级

```
Service 启动与壳完全无关，不做托盘探测：
  1. 服务照常启动（绝不因为没有图标就不干活）
  2. 安装脚本 / stdout / lifecycle.log 打印「工作台已启动：http://127.0.0.1:19820」
  3. 首次安装自动打开一次默认浏览器
  4. `workbench status / stop / portal` 作为无图标下的完整管理手段

壳（若已安装）仅在此之上叠加便利：少敲一行命令。
```

**设计原则：托盘是便利层，不是必需层。服务可用性与托盘可用性完全解耦（C-7）。**

| **R-13** | **无签名 + 无发行信息的常驻小 exe 被 EDR / 国内护航类软件拦截或静默清除** | 壳被删或被拦，用户失去入口；企业环境下可能整包不让装 | **中—高**（企业终端管控环境下更高） | VersionInfo 四字段填实、不泄露构建工具（§6.5）；壳只连 127.0.0.1、不做进程注入类动作；**是否采购代码签名证书与 §8.1「不买证书」口径构成真实冲突 → 归 D-c 一并裁** |
| **R-14** | **pending 更新包悬挂占盘且用户完全无感** | 用盘白涨（实证 327 MB / 占 profile 42%），用户以为自己在最新版，报障时版本对不上 | **已发生**（实证悬挂 15 天） | 应用时机多于一个 + pending 三处可见 + 启动时磁盘 GC 与预算告警（§8.4）；`workbench status` 输出 `pendingUpdate` 字段 |
| **R-15** | **托盘成为 keepalive 唯一路径，杀托盘即全链断** | 无 OS 级兜底，用户「关掉那个图标」就等于停服，且不会自恢复 | 低（原为设计缺陷） | **已消解**：改分期双层（§7.1.2 / D-k）—— 计划任务保「进程一定在」，托盘只叠加 health 探活，不承担唯一保活职责 |
| **R-16** | **崩溃/掉电后遗留孤儿子进程占端口，新实例起不来** | 表现为「明明没在跑却说端口被占」，用户只能重启机器 | 中 | `run/workers.json` 账本记 **pid + pgid + lastSeenAt**，启动时按三条件（过期 + 存活 + 可执行文件属本安装目录）杀整个进程组（§7.5.1）；配套强制验证端口释放（§7.5）|

## 附录 A：QoderWake 0.3.5 本机实证拆解

> 取证方式：对本机已安装的 QoderWake（Linux x64，daemon 0.3.5）做**只读**观察 —— 进程/端口/文件布局/配置样例/日志/公开 HTTP 端点。**未做反编译、未提取或摘抄其源码实现**。以下记录的是**架构模式与工程做法**，不是其代码。
>
> ⚠️ 平台局限（**v3 已解除**）：本机为 Linux，而 QoderWake 在 Linux 上**不提供托盘壳**。因此"Windows 侧的安装形态、托盘实现、GUI 壳与服务的绑定方式"三项在 v2 时为空白 —— **这三项已于 2026-08-20 在 Windows 侧补齐（daemon 0.2.3 / 安装器 0.1.33 / 托盘 0.0.20），逐项答案见 A.7**。

### A.1 三层制品与独立版本化

发布清单里是三个**各自独立版本号**的制品：

| 制品 | 观察到的版本 | 角色 |
|------|------------|------|
| `daemon` | 0.3.5 | 业务本体，单体可执行，常驻 |
| `nativeApp` | 0.1.5 | 桌面壳（本机 Linux 未安装） |
| `cli` | 1.1.8 | 命令行入口 |

**可借鉴点**：壳、服务、CLI 三者版本解耦 —— 改个图标不必重发服务，服务修 bug 不必重打安装包。代价是发布清单要多维一层绑定关系。本方案 §9.1 照此组织。

daemon 本体是一个 **161 MB 的单文件可执行**（Bun `--compile` 产物特征：内嵌运行时 + 全部 JS），启动横幅自报 `Runtime: Bun 1.3.14` / `BuildBun: 1.3.14`。这是"不用 Electron 也能把带原生依赖的 TS 服务发出去"的直接反例证据。

### A.2 原生依赖外挂，不编入二进制

```
resources/sqlite-vec/<platform>-<arch>/vec0.so    ← 预编译 loadable extension，按平台平铺
```

运行时由 SQLite `load_extension()` 动态加载。**这一条直接推翻了本报告初版"只有 Electron 能打包原生模块"的论据**（§4.3）。

### A.3 进程守护完全委托 OS

Linux 侧观察到的是 systemd `--user` unit，其中值得直接抄语义的字段：

| 字段 | 语义 | 为什么值得抄 |
|------|------|------------|
| `Restart=always` | 崩溃即重启 | 自研 supervisor 的核心功能，OS 免费给 |
| `RestartPreventExitStatus=78` | 退出码 78（EX_CONFIG）不重启 | 配置写错时不会每 5 秒重启刷满日志 |
| `SuccessExitStatus=0 143` | SIGTERM(143) 视为正常退出 | 优雅停止不被记成"崩溃" |
| `KillMode=control-group` | 连带杀子进程 | 派生的 CLI/底座子进程不会变孤儿 |
| `StartLimitBurst=5` | 重启风暴熔断 | 避免无限重启 |
| `WantedBy=default.target` | 开机/登录自启 | 与 keepalive 是同一份配置（见 D-e） |

**可借鉴点**：这套语义 launchd（`KeepAlive` / `RunAtLoad` / `ThrottleInterval` / `ExitTimeOut`）与 Windows schtasks 都有对等物。自研健康探测 + 指数退避不但多写代码，还多一份要维护的状态机。本方案 §7 据此把守护 100% 委托 OS。

### A.4 配置两层分离 + 薄覆盖 + 带注释样例

```
config/
├── config.json           实际生效（薄覆盖，本机只有 3 行：仅一个 update.manifestUrl）
├── config.sample.json    全量带注释示例（1.6 KB）
├── settings.json         实际生效（薄覆盖，本机只写了 storage + channel）
└── settings.sample.json  全量带注释示例（3.4 KB）
```

两层的**职责切分**是重点：

| 层 | 文件 | 内容性质 | 关心它的人 |
|----|------|---------|-----------|
| 基础设施 | `config.json` | api host/port、更新源 manifestUrl、envMode、日志四类各自的 maxFileSize/maxTotalSize、运行记录保留策略（清扫间隔/保留天数/每触发器条数/是否 vacuum）、telemetry、observability | 运维 / 排障 |
| 用户偏好 | `settings.json` | 输出语言、`system.launchAtLogin` / `preventSleep`、endpoint 模式（public/vpc）及派生 baseUrl、`storage.backend`（sqlite / file / externalDb-postgresql）、任务队列并发上限、工作区、升级前备份、IM 渠道开关、项目分析 | 产品 / 终端用户 |

三个具体做法值得抄：

1. **实际配置文件只写覆盖项**，其余走代码默认 —— 用户 diff 一眼就知道自己改过什么，升级也不会被陈旧的全量配置绑住
2. **另发一份 `*.sample.json` 全量示例**，用 `_comment` 字段内嵌中文说明绕开 JSON 不支持注释的限制 —— 比单独写一篇配置文档更不容易过时
3. **`backup.preUpgrade{enabled, retentionCount}`**：升级重启前压缩备份，保留最近 N 份（其注释标明有效范围 1–20）。默认关闭。这是很便宜的兜底，本方案 §9.2 采纳

| 绑云 | 启动即连 `openapi.qoder.sh` 网关，MachineID 绑定 | **不借鉴**：我们要求本地可用、可离线 |
| 二进制未 strip | 161 MB not stripped，且内嵌完整可读 JS 源码 | **反面教材**：本方案强制发布前 strip（§9.2） |
| 双端口 | 除 19820 外另有辅助监听 | **不借鉴**：单端口更易解释、易做防护 |
