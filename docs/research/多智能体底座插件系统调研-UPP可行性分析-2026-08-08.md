# 多智能体底座插件系统调研——UPP 通用插件协议可行性分析

> 调研日期：2026-08-08
> 目的：为数字员工套件 2.0 的 UPP（Universal Plugin Protocol）设计提供证据底座——摸清各大智能体底座的插件/Agent/Skill 体系，评估"一份中性 manifest 翻译成多宿主原生格式"的可行性
> 锚点：白皮书 v0.3 §3.7 多宿主适配器 + §4.3 一包多宿主

## 2. 八家全景对比

### 2.1 总览

| 底座 | 类型 | Agent 定义 | Skill 定义 | Hook 系统 | 安装方式 | 市场 |
|------|------|-----------|-----------|----------|---------|------|
| **Claude Code** | CLI 编码代理 | `agents/*.md` | `skills/<name>/SKILL.md` | `hooks.json`（PreToolUse / PostToolUse / UserPromptSubmit / SessionStart / PreCompact） | `claude plugin install <id>@<marketplace>` | marketplace.json |
| **opencode** | CLI 编码代理 | TS 插件 + session API | 无原生（通过 `chat.messages.transform` 注入） | `tool.execute.before` / `tool.execute.after` / `chat.messages.transform` | 文件落地到 `$OC_HOME/hooks/` + TS 插件 | 无 |
| **CodeBuddy** | CLI 编码代理 | 同 CC（基于 Claude Code SDK） | 同 CC | 同 CC | `codebuddy plugin install <id>@<marketplace>` | known_marketplaces.json |
| **Qoder** | CLI 编码代理 | 同 CC | 同 CC | 同 CC | `qodercli plugin install <id>@<marketplace>` | known_marketplaces.json |
| **TRAE** | IDE（ByteDance） | `.trae/agents/agent.yaml` + `agent.md`（YAML 配置 + MD 指令双文件） | `.traerules` YAML frontmatter `skills` 数组 | 规则注入 + MCP 工具绑定 | `trae --install-extension` | 内置市场 + MCP |
| **OpenClaw** | 全平台代理（385k⭐） | `.agents/skills/` 目录 + `openclaw.plugin.json` 声明式契约 | `openclaw.plugin.json` 声明式（provider contracts：模型/工具/渠道各是一类扩展点） | Provider contracts 声明式（非事件钩子） | ClawHub 安装 | ClawHub |
| **Hermes-Agent** | 全平台代理（226k⭐） | `ctx.register()` TS 接口动态注册 | `skill_bundles.py` + `skill_commands.py`（Python 代码定义） | `PluginContext` 事件（register / onDispose / REST / WebSocket） | 桌面端插件面板 | Skills Hub |
| **Pi** | 轻量 CLI 代理 | 无原生（扩展注入上下文模拟） | `resources_discover` → `skillPaths` | 5 事件：`resources_discover` / `session_start` / `session_compact` / `agent_end` / `context` | `.pi/extensions/` 放 `.ts` 文件 | 无 |

### 2.2 已适配四家详细对比

#### Claude Code

```
plugin.json:
  name, version, description, author, dependencies

marketplace.json:
  条目列表（name + source + type）

agents/:
  dev-engineer.md 等 markdown 文件（agent 定义）

hooks/hooks.json:
  PreToolUse / PostToolUse / UserPromptSubmit / SessionStart / PreCompact
  每个 hook: { matcher, command, env }

skills/:
  <name>/SKILL.md（YAML frontmatter: name, description, tier + markdown body）

安装: claude plugin marketplace add <源> && claude plugin install <id>@<marketplace>
判据: plugin list --json → enabled == true && installPath 落盘
```

#### opencode

```
opencode.json:
  { "$schema": "...", "plugin": ["./plugin/index.ts"] }

TS 插件（index.ts）:
  实现 Plugin 接口，返回 { tool.execute.before, tool.execute.after, chat.messages.transform }
  核心工作：翻译层——opencode 工具名/参数 → CC 规范格式

工具名翻译:
  "bash"→"Bash", "write"→"Write", "edit"→"Edit", "read"→"Read"...
  参数翻译: {filePath}→{file_path}, {oldString}→{old_string}...

安装: 文件落地到 $OC_HOME/hooks/ + TS 插件到 $OC_HOME/plugins/
判据: 文件存在性
```

#### CodeBuddy

```
与 CC 几乎一致（基于 Claude Code SDK），主要差异：
- CLI 命令: codebuddy 替代 claude
- 配置目录: ~/.codebuddy（可覆盖 CODEBUDDY_CONFIG_DIR）
- 判据: settings.json 的 enabledPlugins（非 plugin list --json）
- 坑点: 远程条目 clone 进 marketplace 源目录（非自己的 cache），源只读时 EACCES
- 行为差异: 对主插件全有全无（UA clone 失败 → agents-team 不进 settings.json）
```

#### Qoder

```
与 CC 几乎一致，主要差异：
- CLI 命令: qodercli 替代 claude
- 配置目录: ~/.qoder（可覆盖 QODER_CONFIG_DIR）
- 坑点: qodercli marketplace add 直加主仓整目录必 EBUSY（shallow.lock 残留）
- 判据: settings.json 的 enabledPlugins
```

### 2.3 新排查四家详细发现

#### TRAE

```
Agent 定义（.trae/agents/）:
  agent.yaml（配置）+ agent.md（指令）双文件模式
  agent.yaml: name, model, definition（指向 .md）, tools（MCP 服务器列表）

Skill 定义（.traerules）:
  YAML frontmatter 中的 skills 数组
  每 skill: name, description, prompt, files（glob）, commands（shell）

MCP 集成:
  mcp.json / mcp.yaml 绑定外部工具服务器

关键发现:
  agent.yaml + agent.md 双文件模式与我们 manifest.yml + 主人设 markdown 几乎同构
  TRAE 是八家中与我们架构最接近的新底座
```

#### OpenClaw

```
插件格式:
  package.json 中 openclaw.extensions: ["./index.ts"] 声明入口
  openclaw.plugin.json 定义能力契约

openclaw.plugin.json 核心字段:
  id, activation.onStartup, enabledByDefault
  providers: ["openai", ...]（模型提供商）
  modelCatalog: { providers: { ... models: [{ id, name, cost, contextWindow }] } }
  contracts: { speechProviders, memoryEmbeddingProviders, ... }（声明式能力契约）
  setup: { providers: [{ id, envVars }] }（安装指引）
  configSchema: JSON Schema（插件配置项）

扩展生态:
  150+ 扩展在 extensions/ 目录
  每扩展 = 一个 TypeScript 包（package.json + openclaw.plugin.json + 源码）
  扩展 SDK: @openclaw/plugin-sdk

关键差异:
  插件不是"注入行为"，而是"声明能力契约"
  provider（模型接入）/ channel（消息渠道）/ tool（工具）各是一类扩展点
  没有我们熟悉的 PreToolUse/PostToolUse 事件钩子模型
```

#### Hermes-Agent

```
插件格式:
  纯 TypeScript 接口 HermesPlugin = { id, name, defaultEnabled, register(ctx) }
  插件是一个 TS 函数，调 ctx.register() 注册贡献

PluginContext 能力:
  ctx.register({ id, ... }) —— 注册贡献，自动命名空间隔离（plugin:<id>:<localId>）
  ctx.registerMany([...]) —— 批量注册
  ctx.onDispose(fn) —— 卸载清理
  ctx.rest(path) —— 插件专属 REST API 命名空间
  ctx.socket(path, onMessage) —— 插件专属 WebSocket
  ctx.os —— 系统门面（通知/打开URL/文件管理器/剪贴板）
  ctx.storage —— 插件隔离持久化（VS Code globalState 类比）
  ctx.i18n —— 插件国际化

LLM 访问:
  插件通过 ctx.llm.complete(messages) 调用 LLM
  宿主管理鉴权，插件不接触 API key
  信任门控: config.yaml 中 plugins.entries.<id>.llm 控制权限

Skill 系统:
  skill_bundles.py + skill_commands.py + skill_utils.py
  学习型技能系统，支持记忆沉淀

关键差异:
  无声明式清单——插件是代码，通过 ctx.register() 动态注册
  信任门控精细（allow_provider_override / allow_model_override / allowed_providers / allowed_models）
```

#### Pi

```
插件格式:
  TypeScript 扩展，default export 函数接收 ExtensionAPI
  来自 @earendil-works/pi-coding-agent 包

事件 API（5 个）:
  pi.on("resources_discover") → { skillPaths: [...] }
  pi.on("session_start") → void
  pi.on("session_compact") → void
  pi.on("agent_end") → void
  pi.on("context", event) → { messages: [...] }（注入/修改消息）

安装:
  扩展文件放到 .pi/extensions/ 目录

关键差异:
  最轻量——5 个事件，无市场、无 CLI 安装命令
  工具名是小写（read, write, edit, bash）
  无原生 subagent 概念（需安装 pi-subagents 扩展）
  无原生 task-list 工具
```

## 3. 关键维度归一化分析

### 3.1 Agent 定义格式

```
CC/CB/Qoder:  agents/*.md （纯 markdown，无配置分离）
TRAE:        .trae/agents/agent.yaml + agent.md （YAML 配置 + MD 指令，与我们的 manifest.yml + 主人设 同构！）
Hermes:      ctx.register({id, ...}) 动态注册（TS 代码接口）
OpenClaw:    .agents/skills/ + 扩展 package.json（技能目录 + 扩展声明）
opencode:    TS 插件代码（代码即定义）
Pi:          无原生 agent 概念（通过扩展注入上下文模拟）
```

### 3.2 Skill 定义格式

```
CC/CB/Qoder:  skills/<name>/SKILL.md（YAML frontmatter + markdown body）
TRAE:         .traerules YAML frontmatter skills 数组（name, description, prompt, files, commands）
Hermes:       skill_bundles.py + skill_commands.py（Python 代码定义）
OpenClaw:     .agents/skills/ 目录（markdown 文件）
opencode:     无原生（通过 chat.messages.transform 注入模拟）
Pi:           resources_discover → skillPaths
```

### 3.3 Hook 事件对照

| 事件语义 | CC | opencode | Pi | Hermes |
|---------|-----|----------|-----|--------|
| 工具执行前拦截 | `PreToolUse` | `tool.execute.before` | — | — |
| 工具执行后审计 | `PostToolUse` | `tool.execute.after` | — | — |
| 用户消息提交前注入 | `UserPromptSubmit` | `chat.messages.transform` | `context` | — |
| 会话启动 | `SessionStart` | — | `session_start` | — |
| 会话压缩前 | `PreCompact` | — | `session_compact` | — |
| Agent 结束 | — | — | `agent_end` | — |
| 资源发现 | — | — | `resources_discover` | — |
| 插件注册 | — | — | — | `ctx.register()` |

### 3.4 安装机制对照

| 底座 | 注册市场 | 安装插件 | 验证判据 | 配置目录 |
|------|---------|---------|---------|---------|

| TRAE | 内置市场 | `trae --install-extension` | — | `~/.trae` |
| OpenClaw | ClawHub | ClawHub 安装 | — | — |
| Hermes | Skills Hub | 桌面端插件面板 | — | — |
| Pi | 无 | `.pi/extensions/` 放文件 | — | — |

## 4. 梯队划分

按"与 CC plugin.json 体系的距离"排列：

```
距离近（可直接映射）──────────────────────────────────────────→ 距离远（需重写）

  第一梯队                  第二梯队                第三梯队
  CC  CB  Qoder  TRAE      OC  Pi  Hermes        OpenClaw
  │   │    │      │        │   │     │              │
  └─ plugin.json 系 ─┘    └─ YAML+MD 系 ─┘    └─ TS 代码接口系 ─┘   └─ 声明式契约系 ─┘
```

| 梯队 | 成员 | 特征 | UPP 适配难度 |
|------|------|------|------------|
| **第一梯队：plugin.json 系** | CC, CodeBuddy, Qoder | 都基于 CC 的 plugin.json + marketplace.json 体系，差异只在 CLI 命令名和配置路径 | **低**——一份 UPP manifest 直接翻译成 plugin.json |
| **第二梯队：YAML+MD 系** | TRAE, opencode, Pi | 都有 agent 定义文件 + skill 注入机制，事件名/语义不同但抽象层相似 | **中**——需要写薄适配器翻译事件名和文件路径 |
| **第三梯队：TS 代码接口系** | Hermes | 插件是代码，非声明式文件。但 `ctx.register()` 抽象与我们的 manifest 注册一一对应 | **中高**——需要生成 TS 代码骨架 |
| **第四梯队：声明式契约系** | OpenClaw | 插件体系完全不同——provider contract 声明式，没有事件钩子模型 | **高**——需要重写适配逻辑，部分能力无法 1:1 映射 |

## 5. 对 UPP 设计的关键启示

### 5.1 共性抽象：三个通用原语

所有八家底座都有这三样东西，只是叫法和格式不同：

```
              CC/CB/Qoder    TRAE         opencode/Pi    Hermes       OpenClaw
              ───────────    ────         ───────────    ──────       ────────
Agent 定义    agents/*.md    agent.yaml    TS 插件代码     ctx.          plugin.json
                             + agent.md                  register()    + skills/

Skill 定义    SKILL.md       .traerules    skillPaths     skill_        .agents/
                             YAML                         bundles.py    skills/

Hook 事件     hooks.json     (规则注入)    tool.execute.*  ctx context   provider
              PreToolUse等                 session_*等     events        contracts
```

### 5.2 UPP 最小可行 Schema

从八家对比中提炼，UPP 只需要定义三类原语的中性描述：

```yaml
# upp-manifest.yml（中性格式，不绑定任何宿主）
upp_version: "1.0"
id: dev-engineer
version: 1.2.0

# ── Agent 原语 ──
agents:
  - name: dev-engineer
    description: 开发工程师——端到端编码交付
    entry: agents/dev-engineer.md    # 主人设 markdown
    tier: coding                     # 抽象档位，宿主适配器按 tier 映射到具体模型

# ── Hook 原语 ──
hooks:
  - event: PreToolUse                # UPP 规范事件名
    matcher: "Bash"                  # UPP 规范工具名（PascalCase）
    command: hooks/block-advance.py
  - event: PostToolUse
    matcher: "Write|Edit|MultiEdit"
    command: hooks/post-write-check.py
  - event: UserPromptSubmit
    command: hooks/user-prompt-trigger.py

# ── Skill 原语 ──
skills:
  - name: ieidev-tdd-methodology
    entry: skills/ieidev-tdd-methodology/SKILL.md
  - name: ieidev-secure-coding
    entry: skills/ieidev-secure-coding/SKILL.md
```

### 5.3 宿主适配器职责

每个宿主适配器只做一件事：**UPP → 宿主原生格式的双向翻译**。

```
UPP manifest（中性）
  │
  ▼
宿主适配器（每个宿主 ~100-200 行）
  │
  ├── CC 适配器:      UPP → plugin.json + hooks.json + marketplace.json
  ├── opencode 适配器: UPP → opencode.json + TS plugin + 文件落地
  ├── CB 适配器:      UPP → plugin.json + hooks.json（同 CC，CLI 命令换 codebuddy）
  ├── Qoder 适配器:   UPP → plugin.json + hooks.json（同 CC，CLI 命令换 qodercli）
  ├── TRAE 适配器:    UPP → agent.yaml + agent.md + .traerules
  ├── Pi 适配器:      UPP → .pi/extensions/*.ts
  ├── Hermes 适配器:  UPP → HermesPlugin TS 代码骨架
  └── OpenClaw 适配器: UPP → package.json + openclaw.plugin.json
```

### 5.4 安装流程统一

八家安装动作抽象为 5 个标准步骤，语义完全一致：

| 步骤 | 语义 | 实现方式 |
|------|------|---------|
| ① 探测宿主在场 | 检查宿主二进制是否可执行 | `command -v <binary>` 或 `host_facts.has_binary()` |
| ② 注册市场源 | 让宿主知道从哪里拉插件 | 各宿主 CLI 命令或文件落地 |
| ③ 安装插件包 | 将 UPP 翻译后的原生格式装入宿主 | 各宿主 CLI 命令或文件落地 |
| ④ 验证装好 | 确认插件已生效 | 各宿主判据（plugin list / settings.json / 文件存在） |
| ⑤ 接状态栏 | 可选，注册 HUD 状态栏 | `ieidev_hud setup --host <host>` |

## 6. 结论

### 6.1 UPP 可行性：可行

八家底座虽然插件格式各不相同，但**抽象层完全一致**——都有 Agent 定义、Skill 定义、Hook 事件三类原语。UPP 定义这三类原语的中性 schema，每宿主写一个薄适配器做翻译，技术上是完全可行的。

### 6.2 优先级建议

| 优先级 | 底座 | 理由 |
|--------|------|------|
| P0 | Claude Code, CodeBuddy, Qoder | 已适配，plugin.json 系，UPP→plugin.json 翻译成本最低 |
| P1 | TRAE | agent.yaml+agent.md 与我们的 manifest.yml+主人设几乎同构，适配成本极低 |
| P1 | opencode | 已适配，TS 插件翻译层已有成熟模式（index.ts 就是薄适配器） |
| P2 | Pi | 5 事件 API 简单，扩展文件是 TS，适配成本中低 |
| P2 | Hermes | 插件是代码接口，但 `ctx.register()` 与我们的 manifest 注册语义一一对应 |
| P3 | OpenClaw | 声明式契约体系与事件钩子模型差异最大，适配成本最高，优先级可放后 |

### 6.3 与白皮书 v0.3 的对齐

本调研结论与白皮书 §3.7 多宿主适配器 + §4.3 一包多宿主方向一致，且为 §4.3 的"一个 plugin 包兼容四宿主"提供了扩展到八宿主的可行性证据。
