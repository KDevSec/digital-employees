## 1. MVP 定义

### 一句话

**L0/L1 单员工 on CodeBuddy + AgentHub 技能拉取——从零到可用的最短路径。**

### 用户故事

```
开发者打开工作台 → 创建新员工 → 从 AgentHub 浏览/选择 skill →
生成员工包（AGENTS.md + skills）→ 安装到 CodeBuddy（UPP）→
在 CodeBuddy 里直接派发使用（L0/L1，不需要引擎）
```

### MVP 边界

| 包含 | 不包含 |
|------|--------|
| shared-protocol（manifest + skill schema） | runtime-engine（L2+ SOP 驱动） |
| UPP CodeBuddy 适配 | workflow 编排 / 任务看板 |
| 员工管理 + 创建向导（内置模板 + 自定义） | CQO 治理 / 工程记忆 / 本地观测 |
| AgentHub skill 拉取（API 客户端） | 群组协作 / 跨员工编排 |
| 底座管理（简化版） | A2A 通信 |

### 为什么单员工不需要 runtime-engine

白皮书 §4.1 渐进增强模型：
- **L0 裸 Agent**：用户直接派员工（AGENTS.md），底座（CodeBuddy）执行。依赖：0
- **L1 +Skill**：注入方法论，agent 按方法论干活。依赖：员工包 skill 文件
- **L2 +SOP**：node-table + flow-driver + 引擎——**这里才需要 runtime-engine**

MVP 只做 L0/L1，不需要引擎。runtime-engine 是 L2+ 的增强功能（可选叠加）。

## 2. MVP 模块拆分（竖切）

每个模块是端到端完整功能（前端 + 后端 + 数据），一人可 owns 从头到尾。

### MVP 模块（4 个）

| # | 模块 | 前端 | 后端 | 数据 | 依赖 |
|---|------|------|------|------|------|
| M1 | **shared-protocol** | — | manifest schema + skill schema + 身份三元组 + provides/requires 声明 | YAML/JSON Schema | 无 |
| M2 | **UPP CodeBuddy 适配** | 底座卡片展示（简化版） | CodeBuddy shim：AGENTS.md→CB 落位 + skill 落位 + 安装/卸载 | `~/.codebuddy/` 插件目录 | M1 |
| M3 | **员工管理 + 创建向导** | 我的员工列表 + 创建向导（角色模板→身份→**skill 从 AgentHub 选**→约束→生成）+ 详情页 + 对话入口 | manifest 扫描 + 注册发现 + 包构建（AGENTS.md + 拉 skill + 打包）+ 安装触发 UPP | `~/.ieidev/registry.yml` + 员工包 | M1 + M2 + M4 |
| M4 | **AgentHub skill 拉取** | skill 浏览/搜索/详情（嵌入创建向导 Step 3） | AgentHub API 客户端（skill 列表 + 详情 + 拉取） | AgentHub（已有平台） | M1（skill schema） |

### MVP 依赖链

```
M1 shared-protocol ──────┬──→ M2 UPP CodeBuddy 适配 ──┐
                         │                              │
                         ├──→ M4 AgentHub skill 拉取 ─┤
                         │                              │
                         └──→ M3 员工管理 + 创建向导 ◀──┘
                              （需要 M2 装到 CB + M4 拉 skill）
```

**关键路径**：M1 → M2 + M4 并行 → M3

### AgentHub 集成说明

AgentHub 是已有的数字资产平台。M4 不是建 AgentHub，是**集成 AgentHub API**——只做 skill 浏览/拉取的客户端。

## 4. 技术调研结论

### 4.1 通用 hook 代理方案——不存在现成的

| 问题 | 答案 | 证据 |
|------|------|------|
| 有没有"通用 hook 代理层"可替代每底座 shim？ | **没有** | 搜索到的 5+ 个"通用适配"项目全部是搜索引擎幻觉，`gh api` 验证后 404 |
| Orkas 有通用适配层吗？ | **没有**——Orkas 是 Electron 桌面 GUI，做的是 LLM API 路由 + CLI 子进程调度 | [orkas-ai/Orkas](https://github.com/orkas-ai/Orkas) 1158 stars |
| CC hooks 是事实标准吗？ | **是**——Cursor 官方文档明确"matches Claude Code behavior for compatibility" | [cursor.com/docs/hooks](https://cursor.com/docs/hooks) |

#### 各底座 hook 差异（实测）

| 底座 | hook 机制 | 与 CC 兼容？ | shim 工作量 |
|------|---------|------------|-----------|
| **Claude Code** | settings.json + stdin/stdout JSON | 基准 | 零 |
| **Cursor** | hooks.json（4 层优先级）+ CC 兼容 | ✅ 官方兼容 | 近零（配置路径映射） |
| **opencode** | JS/TS 插件模块（`tool.execute.before/after`） | 概念等价但命名/集成方式不同 | **需要真正 shim** |
| **CodeBuddy** | 基于 Claude Code SDK（1.0 经验），已验证兼容 CC hooks | ✅ 已验证兼容 | 近零 |
| **Qoder** | 原生实现 CC Hooks 规范，已验证兼容 | ✅ 已验证兼容 | 近零 |

#### 对 UPP 的影响

1. **UPP v0.2"开放标准薄封装 + 每底座薄 shim"方向被验证为正确**——没有捷径
2. **CC hooks 是基准**——UPP 标准以 CC hooks 规范为基准（事件名、stdin/stdout JSON、退出码 0/1/2）
3. **CodeBuddy 大概率近零适配**（基于 Claude Code SDK）——MVP 先做 CodeBuddy 是对的
4. **opencode 是唯一需要真正 shim 的**——命名转换 + JS 模块 vs stdin/stdout

> ⚠️ 搜索引擎在"通用 agent 适配层"话题上幻觉率极高（5+ 个假项目）。后续此方向调研一切用 `gh api` 或 WebFetch 验证。

#### 值得关注的项目

| 项目 | Stars | 价值 |
|------|-------|------|
| [zhaoxuya520/reverse-skill](https://github.com/zhaoxuya520/reverse-skill) | 24k | 真实的跨底座 skill 适配（CC/Kiro/Cursor/Cline），值得研究其适配机制 |
| [metatool-ai/metamcp](https://github.com/metatool-ai/metamcp) | 2.6k | MCP 网关模式，工具层统一可参考（不覆盖 hook 层） |
| [musistudio/claude-code-router](https://github.com/musistudio/claude-code-router) | 36.6k | local control plane 模式，LLM 路由思想可借鉴 |

#### Orkas 可借鉴的设计（非适配层）

| 机制 | 说明 | 借鉴价值 |
|------|------|---------|
| **单一调度原语（`enqueue`）** | 所有分发路径汇集到同一个 enqueue 原语 | 高——UPP hook 分发也应单一原语 |
| **可见性切片** | 每个代理只获得 `from==me ∨ to∋me` 的消息切片 | 中——多代理上下文隔离 |
| **meta 自我进化文件** | 每个代理维护 COMPETENCE.md + LEARNING_STRATEGIES.md | 中——shim 可维护自己的能力描述 |

### 4.2 记忆项目调研

#### TencentDB Agent Memory——不适用

不是独立 Agent Memory 项目，是腾讯云向量数据库的 Python SDK。纯向量 + BM25，云服务不支持本地部署。与文件基底不变式完全冲突，无可借鉴。

#### MemOS（记忆张量）——设计有启发，技术栈不采用

[MemTensor/MemOS](https://github.com/MemTensor/MemOS) 10.7k stars，Apache 2.0。核心是 L1/L2/L3 三层记忆演化：

```
L1 Traces（轨迹）     → 原始情景记忆（≈ 我们的 Step）
L2 Policies（策略）   → 跨任务归纳（≈ 我们的 Q/R，但 MemOS 是 LLM 自动归纳）
L3 World Models       → 跨任务世界模型抽象（我们没有）
Skills               → 从 L2 结晶化可调用技能（≈ 我们的 skill_store）
```

**可借鉴（在文件基底框架内）**：

| 借鉴点 | MemOS 做法 | 我们的轻量实现 |
|--------|-----------|--------------|
| 优先级 + 时间衰减 | `V_t = α·R + (1-α)·γ·V_{t+1}` | Step 的 self_eval_score + 时间衰减派生 priority 字段 |
| 归档旧版本 | ArchivedTextualMemory + update_type | Q/G/R 修订时保留 archived 版本 + 标注修订类型 |
| 反馈落地追踪 | feedback → classifier → revisor → repair | F-NNN 反馈采纳修改 Q/G/R 时记录关联 |
| 记忆暴露为 MCP | MemOS 有 MCP Server | 召回逻辑包装为 MCP tool，跨底座可访问 |
| L1→L2 自动归纳 | LLM 驱动归纳 | 未来可选增强——Step 积累到阈值自动触发 LLM 归纳，人工归纳仍为底线 |

**不采用（与文件基底冲突）**：

| 冲突点 | 原因 |
|--------|------|
| SQLite/Neo4j/Qdrant | 铁律：markdown + JSONL 文件基底，人类可读、git 可追踪、零依赖 |
| 向量嵌入存储 | 文件无法存向量；用 grep + 召回 hook 替代 |
| LLM 全自动归纳 | token 消耗高 + 工程记录可控性要求人工归纳为底线 |

### 4.3 通信架构调研（A2A 定位）

详见 [深度调研报告 §7](AgentTeams-Matrix深度调研报告-2026-08-12.md#7-通信架构调研本地发现--远程协作--a2a-定位)，核心结论：

- **A2A 不在员工层，在工作台层**——员工是配置文件无 HTTP endpoint，工作台是运行进程有 HTTP endpoint
- **A2A 规范无 relay/broker**——只有 Client/Server 二元模型，Server 需公网可达
- **NAT 后双方 A2A 直连不可能**——管控平台 relay 必需（非可选）
- **五层通信架构**：L0 文件 → L1 A2A P2P → L2 平台 relay → L3 外部适配器 → L4 Matrix 联邦

## 5. 仓库结构建议

### 套件 monorepo + 平台独立仓

```
仓 1：ieidev-suite（套件 monorepo，pnpm workspaces）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
packages/
├── shared/            共享协议（manifest schema + handoff schema + 身份模型）
├── runtime/           编排引擎 ieidev_core R1/R2/R3（L2+，非 MVP）
├── workbench/         客户端交互前端 + HUD 服务 + A2A endpoint（Phase 3）
├── upp/               UPP 多底座适配器
├── memory/            工程记忆底座（L2+，非 MVP）
└── employees/         员工包（每个独立 npm 包）
    ├── dev-engineer/
    ├── req-architect/
    └── ...
prototype/             原型（QoderWaker 对标 + HTML 原型 → 演进为 workbench）
docs/                  设计文档（从当前仓迁移）

仓 2：ieidev-platform（管理平台独立仓）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
后端（FastAPI + PostgreSQL + Redis）
├── auth/              SSO + RBAC + 团队管理（基座，先建）
├── marketplace/       员工市场 + AgentHub 集成
├── visibility/        跨开发者运行可见
├── cost/             成本中心
├── audit/            审计中心
├── ops/              运营驾驶舱
└── observation/      远端观测（OTLP 采集）
前端（Vue）
```

### 为什么这么分

| 决策 | 理由 |
|------|------|
| 套件用 monorepo | 运行时/前端/UPP/记忆共享代码多，需原子提交跨模块改动 |
| 员工包在 monorepo 里 | 共享 manifest schema + UPP 约定，统一构建发布 |
| 平台独立仓 | 技术栈不同（FastAPI+Vue vs Python+本地 Web）、部署周期不同、访问控制不同 |
| shared 协议包 | 套件和平台的契约，放 monorepo 发布，平台仓依赖 |
| 原型在 monorepo 里 | 原型先行，后续演进为 workbench 前端代码 |
