## 1. 一句话回答

**Multica 是目前能找到的"多底座 agent 调用"最完整的公开工程实证**，它的价值对我们分两块，且两块的成熟度差得很远：

- **底座调用方式（值得深度借鉴，A 级证据）**：一个**单方法窄腰接口** + **统一事件流** + **两层身份模型** + **参数拼接顺序契约**，把 23 个形态各异的 agent CLI 收敛到一个抽象后面。这套设计我们可以几乎照搬进 UPP 的运行时适配层。同时它也给出了这条路的**真实成本账**：`codex.go` 133 KB、`hermes.go` 110 KB —— 一底座一个大文件，没有捷径。
- **协同编排（借鉴思路而非机制，C 级证据）**：它的 squad 编排**没有独立工作流引擎**，整个编排状态寄生在 issue 时间线上，靠"leader agent 发评论 @ 人"驱动。这是一个非常省事且可解释的设计，但它的表达能力上限就是"单层 leader 路由"，没有 DAG、没有并行 fan-out、没有条件分支。我们工作台如果要做真正的编排，**可以抄它的触发与防环规则表，但不能抄它的编排模型**。

## 3. 底座调用抽象（核心，A 级证据）

这一节是本次调研最有价值的部分。全部来自 `server/pkg/agent/agent.go` 与 `builtin_runtimes.go` 源码。

### 3.1 窄腰：整个抽象只有一个方法

```go
type Backend interface {
    Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}
```

**23 个底座、`pkg/agent` 下 138 个文件，对外只暴露这一个方法。**

这是本次调研第一条硬结论。对比我们 UPP v0.2 目前的设计，我们倾向于定义一组能力方法（执行/中断/查询/能力协商）。Multica 的选择说明：**中断靠 `ctx` 取消、查询靠 Session 的事件流、能力协商靠 descriptor 静态声明** —— 三件事都不需要在接口上开方法。

> **我们的动作 M-1**：UPP 的运行时适配接口收敛到**单个 `execute` + 一个静态 descriptor**。取消走 context/signal，进度走事件流，能力走 descriptor 声明。多开的方法每一个都会变成 23 份实现负担。

### 3.2 双通道 Session：事件流与终值分离

```go
type Session struct {
    // Messages 在 agent 工作时流式推送事件，agent 结束时关闭（在 Result 发出之前）
    Messages <-chan Message
    // Result 收到恰好一个值——最终结果——然后关闭
    Result <-chan Result
}
```

关键在注释里的**顺序契约**：`Messages` **先关闭**，`Result` **后发出**。这样消费者不需要 select 竞争，可以放心"读完所有事件再拿结果"。这个小约定消除了整类竞态 bug。

> **我们的动作 M-2**：执行返回值必须是"事件流 + 终值"双通道，且明文规定"事件流先终止、终值后到达"。不要把最终结果混进事件流最后一条（那样消费者要自己判断哪条是最后一条）。

### 3.3 统一事件模型：只有 7 种消息类型

```go
const (
    MessageText       MessageType = "text"
    MessageThinking   MessageType = "thinking"
    MessageToolUse    MessageType = "tool-use"
    MessageToolResult MessageType = "tool-result"
    MessageStatus     MessageType = "status"
    MessageError      MessageType = "error"
    MessageLog        MessageType = "log"
)

type Message struct {
    Type      MessageType
    Content   string          // text / error / log 的正文
    Tool      string          // tool-use / tool-result 的工具名
    CallID    string          // tool 调用 ID，用于配对
    Input     map[string]any  // tool-use 的入参
    Output    string          // tool-result 的输出
    Status    string          // status 的状态串
    Level     string          // log 的级别
    SessionID string          // status 携带的后端会话 id，用于"早期 resume 指针钉定"
}
```

四条设计读数：

1. **7 种够了。** 23 个底座、各家协议千差万别（ACP / stream-json / app-server / 自定义 JSON），最后都能压成这 7 种。我们不需要设计更丰富的事件枚举 —— 更丰富意味着更多底座映射不上而被迫塞 `other`。
2. **`thinking` 是一等公民**，与 `text` 平级。不做这个区分的话，UI 无法把推理过程折叠，而推理过程往往比正文长十倍。
3. **`CallID` 用于把 `tool-use` 与 `tool-result` 配对。** 这在并发工具调用下是必须的 —— 没有 CallID 就只能靠顺序猜，而流式场景下顺序不可靠。
4. **`SessionID` 挂在 `status` 上而不是只在 Result 里。** 注释说明理由是 "early resume-pointer pinning" —— **会话 id 必须在会话中途就能拿到并落盘**，否则进程崩在中间就永远无法 resume。这是个很实际的踩坑沉淀。

> **我们的动作 M-3**：事件模型定 7 类，`thinking` 独立成类；工具事件带 CallID；**会话 id 一拿到就落盘，不等结束**。

### 3.4 统一 Result 与成本核算

```go
type Result struct {
    Status     string  // "completed" | "failed" | "aborted" | "timeout" | "cancelled"
    Output     string
    Error      string
    DurationMs int64
    SessionID  string
    Usage      map[string]TokenUsage  // 按模型名分桶
    ResumeRejected bool
    // …两个 codex 专属的重试安全标记
}

type TokenUsage struct {
    InputTokens, OutputTokens, CacheReadTokens, CacheWriteTokens int64
    CostUSDTicks int64  // 1e-10 USD 为单位
}
const CostUSDTicksPerUSD = 10_000_000_000
```

三条值得抄：

1. **`Status` 五态而不是 bool。** `aborted`（用户主动停）/ `timeout`（看门狗杀）/ `cancelled`（上游取消）语义完全不同，运维与重试策略也完全不同。压成 `success bool` 就丢了全部可运维性。
2. **`Usage` 按模型名分桶（`map[string]TokenUsage`）。** 因为一次 turn 里 agent 可能调多个模型（主模型 + 小模型做压缩/摘要）。单一 token 计数是错的。
3. **成本用 `int64` 的 1e-10 USD 刻度，而不是 float。** 注释给的理由极具说服力：**provider 自报成本优于"token × 费率"估算**，因为 xAI 在 prompt 达到 200K 后按 2 倍计价，而聚合后的 usage 记录已经无法反推每个请求命中了哪档。→ **一旦 provider 自报了成本，就必须用它的数，不要自己算。**

> **我们的动作 M-4**：Result 定五态；usage 按模型分桶；成本字段用整数刻度（我们可以用 1e-6 CNY 或 1e-10 USD），并优先采纳 provider 自报值。

### 3.5 ExecOptions 的 fall-through 约定（这条最关键）

`ExecOptions` 有约 25 个字段。除了通用的 `Cwd / Model / SystemPrompt / MaxTurns / Timeout / ResumeSessionID / ExtraArgs / McpConfig`，还有一大堆**明显只服务于单个底座**的字段：

| 字段 | 只服务于 |
|------|---------|
| `FirstTurnNoProgressTimeout` / `HandshakeTimeout` / `ServiceTier` | codex |
| `ThinkingLevel` | claude / codex / opencode / codebuddy / dsh / grok |
| `OpenclawMode` | openclaw |
| `ClaudeSettingsPath` | claude |
| `QwenpawWorkspace` | qwenpaw |

**核心约定（源码注释明文）：不支持某字段的 backend 应当忽略它，而不是报错。**

> `other backends ignore the field rather than fail (so MUL-2339 can grow runtime support incrementally without breaking unrelated agents)`

这是一个和"能力矩阵/capability negotiation"完全相反的取舍，理由写在注释里：**这样新增 runtime 支持可以增量推进，不会打断无关的 agent。**

同一份注释还坦白了 `ExtraArgs` 的一次真实腐烂：

> `Deliberately not enumerated here — the previous list went stale as backends were added, which is how MULTICA_QWENPAW_ARGS shipped plumbed but dropped. Grep for ExtraArgs to see today's set.`

即：**曾经在字段注释里维护一张"哪些 backend 支持 ExtraArgs"的清单，随着底座增加清单腐烂了，导致 qwenpaw 的参数管道接好了但实际被丢弃。** 修正方式不是补文档，而是**删掉这张清单，让读者去 grep**。

> **我们的动作 M-5（重要）**：UPP 的执行选项采用**宽结构 + fall-through 语义**：底座不认识的选项**静默忽略**，写进规范。不要设计"能力矩阵 + 不支持则报错" —— 我们只有 3~5 个底座时它工作良好，到 10 个以上必然腐烂。
>
> **配套动作 M-6**：**任何"哪些底座支持哪个字段"的清单都不要写在注释或文档里** —— 写了就会腐烂并造成静默失效。要么让它可执行（descriptor 里声明、单测断言），要么不写。

### 3.6 两层身份：protocol_family vs runtime identity

这是 `builtin_runtimes.go` 的全部内容，也是整个多底座设计里最精巧的一处。

**问题**：Claude Code 有一堆兼容 fork，`omp`（Oh-My-Pi）与 `pi` 协议完全相同。如果每个 fork 都当新底座，就得复制一份 30 KB 的适配文件；如果都当同一底座，用户界面上就无法区分、模型列表也会错。

**解法**：拆成两层。

```go
type BuiltinRuntime struct {
    ID               string  // runtime 身份，如 "omp"
    ProtocolFamily   string  // 执行协议族，如 "pi"
    DefaultCommand   string  // "omp"
    EnvPrefix        string  // "MULTICA_OMP"
    DisplayName      string  // "Oh-My-Pi"
    SkillsDir        string  // ".omp/skills"
    UserSkillsDir    string  // ".omp/agent/skills"
    LaunchHeader     string  // "omp (json mode)"
    DefaultExecutable string
    ProviderLabel    string
    ModelDiscovery   func(...) // 可为 nil
}

func ResolveBackend(provider string, cfg Config) (Backend, error) {
    if IsBuiltinRuntime(provider) { return NewRuntime(provider, cfg) }  // 走身份
    return New(provider, cfg)                                            // 走族
}
```

源码注释里的一句话是整个设计的题眼：

> **"Adding a new compatible fork of an existing runtime is a descriptor entry, not a cross-stack change."**

即：**新增一个兼容 fork 的成本 = 加一行 descriptor**，不需要改数据库、不需要改前端、不需要改适配层。descriptor 是"single declaration site"（唯一声明点）。

**代价（也很真实）**：`SupportedTypes` 那 23 个 protocol_family 是白名单，而且**与数据库 `runtime_profile.protocol_family` 的 CHECK 约束是靠 migration 一个个加宽的**（📁 从 migration 编号看：120 → 134 加 qoder → 136 traecli → 175 deveco → 179 grok → 202 qwen → 242 qoderclicn → 253 qwenpaw → 254 reasonix → 313 dsh → 327 mcode）。

**也就是说：新增一个 protocol_family 要跑 DB migration，新增一个 runtime identity 只要加一行代码。** 这个成本差异正是两层拆分的意义所在 —— 它把"绝大多数新增"（fork、换皮、区域版）压到了便宜的那一层。

> **我们的动作 M-7（重要）**：UPP 必须区分**协议族**与**运行时身份**两层：
> - 协议族 = 真正的适配代码（我们 0.1 只做 1~2 个）
> - 运行时身份 = 一份 descriptor（命令名、环境变量前缀、显示名、skills 目录、模型发现函数）
>
> 并且：**运行时身份的注册不要落库、不要进 DB 约束**，就放在代码里的一张表。落库的那一层要尽量少 —— Multica 用 migration 加宽 CHECK 约束 11 次是个可以避免的代价。

### 3.7 真实调用形态：`launchHeaders` 揭示的四类

源码里有一张 `launchHeaders` 表，把每个底座的实际启动骨架写了出来。归成四类：

| 类别 | 底座 | 形态 |
|------|------|------|
| **ACP（Agent Client Protocol）** | hermes / kimi / reasonix / kiro / qoder / qoderclicn / traecli / grok / qwenpaw / dim / mcode（**10+ 个**）| `<cmd> acp` 或 `--acp`，stdio 上跑 JSON-RPC 式协议 |
| **stream-json** | claude / codebuddy / cursor / qwen | `-p --output-format stream-json --input-format stream-json` |
| **app-server** | codex | `codex app-server` —— 长连接 RPC，有 handshake |
| **json / 非交互** | copilot / deveco / openclaw / opencode / pi / omp；antigravity 走 `agy -p`；dsh 走 `dsh --profile multica (stdio)` | 一次性调用 + JSON 输出 |

**这是本次调研第二条硬结论：ACP 已经成为 agent CLI 接入的事实主流。** 23 个底座里 10 个以上原生支持 ACP，说明我们在 UPP 里**第一优先适配的应该是 ACP**，而不是各家的私有 stream 格式。

> **我们的动作 M-8**：UPP 的**第一个协议族实现 ACP**，第二个实现 `stream-json`（覆盖 Claude Code 系）。其余形态按需增加。这两个族能覆盖 Multica 23 个底座里的绝大多数。

### 3.8 参数拼接顺序契约与协议 flag 集中过滤

📄 官方文档给出的顺序契约：

```
<your command> <your fixed arguments> <Multica's protocol arguments> <the agent's custom arguments>
```

四段。并且明确了两条冲突消解规则：
- **Multica 的协议参数后置生效，冲突时它胜出**
- **agent 上选择的 model 覆盖 profile 里 pin 的 `--model`**

更重要的是 A 级实证的这一条：**协议关键 flag（`-p` / `--output-format` / `--input-format` / `--permission-mode` 等）会从用户填的 fixed_args 里被剔除**。实现方式是 `filterLaunchPrefix` 在 `New`（工厂函数）里**统一过滤，不做 per-backend opt-in**。

理由（源码注释）：**ExtraArgs 曾因为走 per-backend opt-in 而腐烂**（§3.5 那个 qwenpaw 事故）。所以这次改成在唯一入口集中做。

> **我们的动作 M-9**：
> - 参数拼接定四段顺序并写进 UPP 规范，明确"平台协议参数后置且胜出"
> - **任何"必须过滤/必须注入"的处理都放在唯一工厂入口集中做，禁止 per-backend opt-in**。这是从他们的事故里直接买到的教训：opt-in 机制在 N 增长时一定会漏。

### 3.9 System prompt 走文件，不走参数

`SystemPrompt` 字段的注释是本次调研第三条硬结论：

> `SystemPrompt carries the Multica runtime brief for the few providers that cannot pick it up from disk. The daemon leaves it empty for every other provider (see daemon.providerNeedsInlineSystemPrompt), because the brief is already delivered as a per-task context file in the workdir — CLAUDE.md, AGENTS.md, CODEBUDDY.md or QWEN.md depending on the runtime.`
>
> `A backend must therefore NOT assume this is populated, and adding a new backend that only reads SystemPrompt will silently receive nothing.`

即：**默认路径是"往工作目录写一个 per-task 的上下文文件"**（按 runtime 选 `CLAUDE.md` / `AGENTS.md` / `CODEBUDDY.md` / `QWEN.md`），只有少数拿不到磁盘上下文的 provider 才内联传 system prompt。

这与 QoderWake 的 shadow-skills 注入（往底座约定目录 `.agents/skills/` 投递文件）是**两份独立证据指向同一结论**：

> **向底座的约定目录投递文件，是多底座场景下最通用、最低成本的能力注入面。**

理由也很清楚：每个 agent CLI 都会读工作目录里的约定文件（这是它们的核心特性），但**并非每个都提供 `--system-prompt` 参数**，参数长度还受 shell 限制。

注释最后那句警告也要记下来：**新写的 backend 如果只读 `SystemPrompt`，会静默收到空值。** 这是 fall-through 语义的代价 —— 所以需要 §3.10 的兜底。

> **我们的动作 M-10（重要，已与 QoderWake §8.8.2 交叉验证）**：UPP 的**第一类适配面定为"文件系统约定"** —— 我们的员工人格、技能、上下文以文件形式投递到底座约定目录，而不是依赖底座提供 API 或参数。每个运行时 descriptor 声明自己的约定文件名与 skills 目录。

### 3.10 多路独立看门狗

`ExecOptions` 里有 **5 个不同的超时**，各管一件事：

| 字段 | 管什么 | 注释里的关键点 |
|------|-------|--------------|
| `Timeout` | 硬墙钟 | **0 = 无死线**，完全交给活跃度看门狗，"只要还在出事件就不因跑得久而被杀"（MUL-3064）|
| `SemanticInactivityTimeout` | 语义静默：跑着的 turn 是否安静了 | — |
| `FirstTurnNoProgressTimeout` | 首轮无进展：进程起来了但从没产出过 | 注释明说这与上一条"回答的是不同问题" |
| `IdleWatchdogTimeout` | 通用无消息 | **只能收窄 daemon 全局窗口，不能扩大**；全局为 0 时仍完全禁用 |
| `HandshakeTimeout` | 启动 RPC（codex app-server）| **0 = 用 provider 默认值，而不是禁用** |

四条设计读数：

1. **`Timeout = 0` 表示"无硬死线"，而不是"立刻超时"或"用默认值"。** 长任务不该因为跑得久被杀，只该因为不出声被杀。
2. **"从没产出过" 与 "产出后安静了" 是两个独立问题，必须两个独立超时。** 这条极容易被合并成一个，合并后的症状是：冷启动慢的底座总被误杀，或者卡死的会话迟迟不被回收。
3. **局部超时只能收窄不能放宽全局安全边界。** 这是配置权限设计，避免单个 agent 配置绕过平台的安全兜底。
4. **`0` 的语义在不同字段里不同**（有的是禁用、有的是用默认值）—— ⚠️ 这其实是个反面教材，我们应该**用可选类型/显式 sentinel 区分"未设置"与"设为零"**，而不是靠注释说明。

> **我们的动作 M-11**：会话看门狗至少要三路独立：**硬墙钟（默认无）+ 首轮无产出 + 产出后静默**。局部配置只能收窄不能放宽。`0` 的语义用显式可选类型表达，不要靠文档约定。

### 3.11 fail-closed 惯例（三处）

Multica 在三个地方选了"宁可报错/宁可空，不要猜"：

| 处 | 做法 | 意义 |
|----|------|------|
| `backendOverrideApplicator` | 某 backend 未实现该接口时，`NewRuntime` **直接报错**而不是回落到族默认行为 | 新 runtime 接入时**必须显式处理**，不会静默走错路径 |
| `ResumeRejectionUndetectable` | 是一张 **opt-in 清单**（antigravity / copilot / cursor / deveco / opencode）—— 只有名单里的 backend 才允许说"我判断不了 resume 是否被拒" | **新 backend 默认被要求能判断**，判断不了要显式登记 |
| `ModelDiscovery` 为 nil | 返回**空模型列表**，而不是回落到族的 `--list-models` 命令 | 因为 omp 对 `--list-models` 是非零退出 —— 回落会产生一个看起来像"模型列表为空"的假象，实际是命令失败 |

`ResumeRejected` 字段的注释还给出一条极精细的语义区分：

> `false is NOT evidence of the opposite. For a backend listed in ResumeRejectionUndetectable it means "could not tell"; for every other backend it means "checked, and this was not a rejection".`

即：**同一个 `false` 在不同 backend 下含义不同，消费方必须结合 provider 名才能解释。** 🔶 这其实是三态被压成了布尔 + 旁表，不如直接定义三态枚举（`rejected` / `not-rejected` / `unknown`）。

> **我们的动作 M-12**：
> - UPP 的新底座接入走 **fail-closed**：未显式实现的钩子报错，不静默回落
> - 需要"某底座做不到某事"时，用 **opt-in 豁免清单**（默认要求全部支持），而不是 opt-in 支持清单（默认全部不支持）—— 前者让遗漏变成报错，后者让遗漏变成静默失效
> - **三态就定义三态枚举**，不要用 bool + 旁表解释

### 3.12 多底座适配的真实成本账（📁）

`server/pkg/agent/` 共 138 个文件，**一底座一文件**，字节数如下：

| 文件 | 字节 | 文件 | 字节 |
|------|------|------|------|
| `codex.go` | **133,166** | `openclaw.go` | 28,943 |
| `hermes.go` | **110,193** | `kimi.go` / `reasonix.go` / `dim.go` / `pi.go` … | 各 ~10–30 KB |
| `models.go` | 98,109 | `copilot.go` / `kiro.go` / `antigravity.go` … | 各 ~10–30 KB |
| `claude.go` | 42,423 | `qoder.go` / `qwen.go` / `qwenpaw.go` / `mcode.go` … | 各 ~10–30 KB |
| `thinking.go` | 35,680 | | |
| `cursor.go` | 35,249 | | |
| `opencode.go` | 31,048 | | |

共享层：`agent.go`、`builtin_runtimes.go`、`launch.go`、`exec_format{,_windows,_other}.go`、`proc_windows.go`（10,518 B）/ `proc_other.go`、`{cursor,copilot,pi}_invocation{,_windows,_other}.go`、`stream_json_result.go`、`stream_scanner.go`、`stderr_tail.go`、`version.go`、`acp_{deliverable,effort,usage}.go`、`mcp_config.go`、`browser_mcp_config.go`。

**三条读数**：

1. **抽象没有消灭适配成本，只是把它隔离了。** 一个成熟底座适配 = 30~130 KB 代码。任何"我们做个通用协议就能一把接所有底座"的想法都要在这个数字面前重新估算。
2. **`codex.go` 133 KB 说明 app-server 这类长连接协议远比一次性调用贵。** 我们选 ACP（stdio JSON-RPC）而不是各家私有长连接，成本上是对的。
3. **`*_windows.go` / `*_other.go` 成对出现了 5 处以上**（`exec_format`、`proc`、`cursor_invocation`、`copilot_invocation`、`pi_invocation`）。**进程与参数处理在 Windows 上必须分支** —— 与 QoderWake §8 的 Windows 实证结论一致。⚠️ 我们要在 0.1 就把"进程启动/杀死/参数转义"抽成显式的平台分支层，而不是等 Windows 出问题再补。

> **我们的动作 M-13**：0.1 只实现 **1 个协议族（ACP）**，并把预算按"每个新底座 30 KB 适配代码 + Windows 分支"来估。UPP 规范要写明"适配一个底座的工作量下限"，避免规划时低估。
>
> **配套动作 M-14**：进程启动/终止/参数转义从第一天就抽成显式平台分支层（`proc_windows` / `proc_unix`），不共用实现。

## 4. daemon 与运行时治理（📄 官方文档）

### 4.1 daemon 命令面

`multica daemon start / status / logs -f / restart / stop / --foreground`

`workspaces_root` 的优先级：**flag > `MULTICA_WORKSPACES_ROOT` 环境变量 > profile config**。（三层优先级链，与我们的配置分层设计一致，可直接抄。）

### 4.2 运行时治理数值（这些数字很值钱）

| 项 | 值 | 我们的解读 |
|----|-----|-----------|
| 心跳间隔 | **15 秒** | — |
| 离线判定 | 异常退出后 **约 3 分钟**内显示离线 | ≈ 心跳的 12 倍。宽容度很大，因为误判离线的代价（任务不派发）比晚判的代价高 |
| 排队等待上限 | 离线时任务排队 **最多 2 小时** | 给"用户合上笔记本去吃饭"留足窗口 |
| 运行中任务失败 | **可自动重试** | — |
| daemon 重启后 | 重新注册 + **回收未干净结束的任务** | 与 QoderWake `daemon.workers.json` 账本同一需求 |
| 自动清理 | **离线 7 天且无 agent 绑定**则自动清理 runtime | 有绑定的不清理 —— 清理条件是"离线 + 无引用"双条件 |
| 并发上限 | daemon 默认 **20** / 每 agent 默认 **6**，**取小** | 两层限流，`MULTICA_DAEMON_MAX_CONCURRENT_TASKS` 可调 |

> **我们的动作 M-15**：直接采用这套治理参数作为 0.1 的起点（心跳 15s / 离线判定 3min / 排队 2h / 双层并发 20 与 6 取小 / 离线 7 天且无引用则清理）。这些数字是别人跑出来的，我们没有更好的先验。

### 4.3 runtime 的私有/公开模型

📄 默认**私有**，**只有 runtime owner 能公开它，workspace admin 也不行**。

文档给的理由很直接：**花的是别人的机器和别人的 CLI 凭据**。并且**公开也不共享 CLI 登录凭据**。

> 这是一条很清晰的权限设计原则：**资源的共享权归资源提供者，不归组织管理者。** 我们的工作台如果支持"把我的机器贡献给团队跑员工"，必须照这条设计，否则会出现"管理员把我的 Claude 订阅额度分给全公司用"这种事故。

### 4.4 自定义 runtime profile 的两条约束

📄
1. **必须挑一个已支持的 protocol family** —— 用户可以自定义命令与参数，但不能自定义协议。（这印证了 §3.6 两层身份的边界：身份层开放给用户，协议层不开放。）
2. **`command` 字段是 exec + args，不是 shell** —— 无管道、无重定向、无 `&&`/`;`、无反引号、无变量展开；需要这些就自己包一个 wrapper 脚本。

> **我们的动作 M-16**：用户可自定义 runtime，但**只能在已有协议族内**自定义命令与参数；命令字段明确为 **exec+argv 而非 shell 串**，并在文档里明说"要 shell 特性请自己写 wrapper"。这既是安全边界（避免命令注入）也是可解释性边界。

## 5. 协同编排：Squads（📄 官方文档，用户重点关注项）

### 5.1 模型

- squad = **1 个 leader agent + N 个 member**（member 可以是 agent 也可以是人）
- 把 issue 派给 squad → **只唤醒 leader**，不并发唤醒全员
- **leader 不自己实现**，只做路由与评估
- leader 通过**发一条 delegation 评论 @ 中选人** → 触发被 @ 者的新任务
- 一轮 dispatch 结束后，**父 issue 停在 `in_progress`**（不自动流转）
- 归档 squad 后 issue 转给前 leader，**不可恢复**

### 5.2 leader 每轮被注入的三块上下文

| 块 | 可编辑性 | 内容 |
|----|---------|------|
| **Squad Operating Protocol** | **系统硬编码，不可编辑** | 编排的基本规则 |
| **Squad Roster** | 系统生成 | 成员名单，**含精确的 mention markdown `[@Name](mention://agent/<uuid>)`** |
| **Squad Instructions** | 用户自定义 | 路由规则（"前端的活给 A，数据库的活给 B"）|

**"硬编码协议 + 系统生成名单 + 用户自定义规则"这个三段式分层是本节最值得抄的一点。** 它把"必须遵守的机制"、"必须准确的事实"、"允许灵活的策略"分开了：机制不给用户改（改了编排就坏），事实由系统保证（用户手写会写错），只有策略开放。

其中一条极具体的踩坑沉淀：**mention 必须是精确的 markdown 链接 `[@Name](mention://agent/<uuid>)`，手打 `@name` 不会触发。** 所以系统必须把可复制的精确形式喂给 leader —— 否则 LLM 会自然地写 `@张三`，然后整条编排链静默断掉。

> **我们的动作 M-17（重要）**：我们工作台的编排提示注入采用同样三段式：
> - **协议段**：硬编码不可改
> - **事实段**：系统生成（成员、能力、可用工具、精确的引用语法）
> - **策略段**：用户自定义
>
> 并且：**任何需要 LLM 精确产出的机器可读标记（成员引用、任务 id、工具调用格式），都必须把精确形式预先喂进上下文，不能指望模型自己拼对。**

### 5.3 leader 的可观测动作

`multica squad activity <issue-id> action --reason "..."` —— **leader 把自己的评估写进时间线**。

即：编排决策不是隐式的，而是**留痕的一等动作**。这解决了"为什么这个任务派给了 A 而不是 B"这个必然会被追问的问题。

> **我们的动作 M-18**：编排器的每次路由决策必须落一条带 reason 的时间线记录。不是日志 —— 是用户可见的时间线。

### 5.4 再触发规则表（防环的核心）

📄 这张表是整个 squad 机制最精细的部分：

| 事件 | 是否触发 leader | 理由 |
|------|---------------|------|
| **非成员**发评论 | ✅ 触发 | 外部输入需要 leader 重新评估 |
| 成员发进展更新（**无 @**）| ✅ 触发 | 有新进展，leader 要决定下一步 |
| 任何**显式 @ 他人 / @all** | ❌ 不触发 | **显式 @ 本身就是路由信号**，不需要 leader 再路由 |
| **leader 自己**发评论 | ❌ 不触发 | **防环** |
| 仅含 issue 交叉引用的评论 | ✅ 触发 | — |
| issue 在 **Backlog** 状态 | ❌ 不触发 | 未启动的工作不消耗算力 |
| **已有排队/派发中的任务** | ❌ 去重，不重复入队 | 防重复消费 |
| role description | 仅作上下文，**不授权、不自动触发** | 描述不等于权限 |

**三条硬结论**：

1. **"leader 自己的评论不触发 leader"是 agent 编排的第一防线。** 没有这条就是无限循环烧钱。任何 agent 编排系统的第一条规则都应该是这个。
2. **"显式 @ 就不再路由"是一条很聪明的语义降级。** 它让人类和 agent 都能"绕过 leader 直接指派"，同时避免了双重路由。
3. **去重是基于"已有排队/派发中的任务"而不是基于评论内容。** 幂等边界画在任务队列上，不画在触发源上 —— 这是对的，因为触发源多样（评论、cron、外部 webhook）而队列是唯一收口。

> **我们的动作 M-19（重要）**：我们的编排触发规则直接照抄这张表，尤其是：
> - **编排器自身产生的事件绝不回触发自身**（防环第一条）
> - **显式指派跳过自动路由**
> - **幂等去重画在任务队列上**（"该 issue/该员工已有在飞任务则不入队"），不画在事件源上
> - **未启动状态的工作项不触发**

### 5.5 CLI 面

`multica squad create --name --leader` / `multica squad member add <squad-id> --member-id --type agent --role "..."`

**编排的全部操作都有 CLI** —— 这与 README 里那句 "Agents drive Multica through the same CLI you do" 对应：**agent 自己就能创建和调整 squad**。

### 5.6 ⚠️ 这套编排模型的能力上限（我们不能照抄的部分）

必须明确指出：**Multica 的 squad 不是工作流引擎，而是"issue 时间线上的评论路由器"。** 由此带来的上限：

| 缺失能力 | 后果 |
|---------|------|
| 无 DAG / 无显式依赖 | 无法表达"A 和 B 完成后才做 C" |
| 无并行 fan-out | leader 一轮只发一条 delegation 评论 |
| 无条件分支 | 分支判断只能藏在 leader 的自然语言推理里，不可测、不可复现 |
| 无编排状态机 | 状态就是 issue 状态 + 评论历史，无法回放、无法从中间恢复 |
| 无重试/补偿语义 | 只有任务级重试，没有编排级补偿 |
| 编排正确性依赖 LLM | leader 读错 roster 或写错 mention 语法，链路静默断裂 |

**它换来的好处也很实在**：零额外基础设施、完全可解释（时间线就是全部真相）、人机同构（人和 agent 在同一条时间线上被 @）、实现极轻。

> **我们的裁决建议（M-20）**：我们工作台的编排走**双层**：
> - **底层是显式编排引擎**（DAG / 状态机 / 可回放 / 可从中间恢复）—— 因为我们面向的是企业流程，"不可复现的编排"过不了验收
> - **上层保留 Multica 式的"评论路由"作为人机交互面** —— 因为它的可解释性和人机同构确实好
>
> 换句话说：**抄它的交互模型与触发规则表，不抄它的编排实现。** 编排状态必须有独立载体，不能寄生在业务对象的评论流里。
>
> 这条要写进 `specs/` 相应功能的 `decisions.md`。

## 6. 数据与安全边界（📄）

| 留在本机 | 存在 server |
|---------|------------|
| 本地 CLI 二进制 | issue 与评论 |
| CLI 的登录凭据 | agent 配置 |
| 代码目录 / workspace | 任务上下文、运行记录、回写结果 |
| | **agent 的自定义环境变量** |
| | **MCP 配置** |

⚠️ **最后两条是需要提醒的**：agent 的自定义环境变量与 MCP 配置**存在 server 侧**，执行时下发到 daemon。这意味着**如果用户往自定义环境变量里塞了 API key，那个 key 就上了 server**。

对自建部署无所谓（server 也是自己的），但对用他们托管服务的用户是一条实质的信任边界。

> **我们的动作 M-21**：我们的设计里，**凭据类配置必须有"仅本地"的存储选项**，且默认就是本地。云端只存"这里需要一个名为 X 的凭据"的引用，不存值。这是与 Multica 的一处明确差异化，也是企业客户会问的第一个问题。

### 7.1 直接抄（0.1 就要）

|----|------|------|

### 7.2 0.2+ 再说

| 项 | 为什么缓 |
|----|---------|
| 23 个底座 | 0.1 一个协议族两个底座足够验证抽象 |
| 云端 runtime（`cloudruntime`）| 与"本地优先"定位需要先做取舍 |
| provider 自报成本采集 | 先把 token 统计做对，成本核算 0.2 |
| skill lockfile / skillbundle / skill cache | 0.1 skill 数量少 |
| 多 Git 托管 + 5 个 IM 渠道 | 不在 0.1 范围 |
| Autopilots（cron 编排）| 触发子系统 0.2（与 QoderWake 触发器十六件套一并设计）|

### 7.3 明确不抄

| 项 | 原因 |
|----|------|
| **squad 编排寄生在 issue 评论流** | §5.6 —— 企业流程需要可回放、可恢复、可测的编排状态机 |
| 单层 leader 路由作为唯一编排模型 | 表达能力不足（无 DAG / 无并行 / 无条件分支）|
| `daemon.go` 370,891 B 单文件 | 反面教材。我们的 daemon 主文件设硬上限 |
| protocol_family 与 DB CHECK 约束绑定（11 次 migration 加宽）| 可避免的成本，协议族白名单放代码层 |
| `0` 在不同超时字段语义不同 | 用显式可选类型代替 |
| `ResumeRejected` bool + 旁表解释 | 三态就定义三态 |
| agent 自定义环境变量与 MCP 配置存 server | §6 —— 我们默认仅本地 |
| Electron 桌面端 | 我们的工作台壳是 87 KB 原生托盘（QoderWake §8.6 实证）|

## 8. 与 QoderWake 实证的交叉验证

两份独立调研（一份是 Windows 上跑的闭源产品的运行时实证，一份是开源仓库的源码实证）在四处得出相同结论。**独立双证据的结论可以直接当裁决用，不需要再论证。**

| # | 结论 | Multica 证据 | QoderWake 证据 |
|---|------|-------------|---------------|
| X-1 | **CLI 与 daemon 同一个二进制** | `server/cmd/multica` | `qoderwake.exe __daemon` |
| X-2 | **能力注入走"向底座约定目录投递文件"，不依赖底座 API** | system prompt 以 `CLAUDE.md`/`AGENTS.md`/`CODEBUDDY.md`/`QWEN.md` 投递到 workdir（§3.9）| `resources/shadow-skills/.agents/skills/` 注入（§8.8.2）|
| X-3 | **agent 通过宿主自己的 CLI 反向驱动宿主** | `internal/selfexec` + "Multica CLI skill" + squad CLI | `builtin-skills/qoderwake-assistant/` 含 32 KB SKILL.md + 30 KB CLI 命令参考（§8.8.3）|
| X-4 | **Windows 的进程/参数处理必须独立分支** | `proc_windows.go` / `exec_format_windows.go` / 3 个 `*_invocation_windows.go`（§3.12）| WinSW、Inno Setup、句柄继承坑、GBK 日志、重启交接脚本（§8.2–8.5）|

一处**明确的分歧**，值得记下：

| 分歧 | Multica | QoderWake | 我们的选择 |
|------|---------|-----------|-----------|
| 底座 CLI 是否随包分发 | **不分发**（"Multica drives them; it doesn't ship them"）| **随包分发**（`qodercli-wake.exe` 160 MB）| **不分发** —— 我们是多底座定位，N × 160 MB 不可接受；但要把"CLI 版本不在支持区间"当一类一等错误 |
