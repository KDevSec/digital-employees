## 1. 数字员工配置的最简版本（Employee Spec）

MVP 只要一个**与底座无关的 canonical package**，三个文件级要素就够：

```
<employee-id>/                  # 员工配置包（spec，工作台的唯一事实源）
  employee.yml                  # profile 元数据
  persona.md                    # 人设/系统提示词正文（host 无关的纯 markdown）
  skills/
    <skill-name>/
      SKILL.md                  # 沿用 SKILL.md 事实标准
      references/…              # 可选
```

`employee.yml` 最简 schema：

```yaml
id: dev-engineer
display: 开发工程师
version: 0.1.0
description: 一句话职责描述（给工作台列表页看）
model_tier: 编码档          # 抽象档位，不写具体模型名 —— 具体模型由适配层查 tier-map
persona: persona.md
skills:                      # 显式声明，而不是扫目录，便于后续引用外部 skill 仓库
  - skills/ieidev-tdd-methodology
```

两个刻意的取舍：

- **选 SKILL.md 作为能力载体**是对的：它本质是"markdown 指令 + 触发描述"，是各底座的最大公约数——ClaudeCode 原生支持，Codex/OpenCode/Qoder 都能通过 AGENTS.md 引用或插件机制消化。MVP 不碰 MCP、hooks、subagents，这些每家差异太大，留给 v2 按底座能力降级（adapter 声明 `capabilities`，装不了的项 warn 并跳过）。
- **model 写抽象档位而非具体模型名**，这正是你 tier-map.yml 已经验证过的模式：spec 说"编码档"，适配层落地时才翻译成 `opus` / `deepseek-v4-flash`。

## 2. 工作台的抽象管理：三层对象模型

工作台管理的不是一层东西，是三层，把它们在数据模型上分开是 MVP 最重要的设计决定：

```
EmployeeSpec（抽象配置包）
   │  install(spec, host) —— 经过适配层
   ▼
Deployment（落地实例 = spec × host × home目录）
   │  launch(deployment, workdir)
   ▼
Session（工作实例 = deployment × 一次会话）
```

本地存储建议：

```
~/.workbench/
  specs/<employee-id>/<version>/     # canonical 配置包，按版本存
  registry.json                      # deployment 台账
~/digital-staff/                     # 所有落地员工的 home（见第 3 节）
```

`registry.json` 每条 deployment 记录：`{employee_id, spec_version, host, home_dir, installed_at, status}`。

一条铁律：**工作台永远不直接编辑落地后的 host 配置，只从 spec 经 adapter 重新生成**。落地产物是"编译产物"，spec 是源码。adapter 生成时在 home 里落一个 `.workbench-manifest.json`（spec 版本 + 生成文件清单 + hash），这样：升级 = 重跑 adapter；漂移检测 = 对 hash；卸载 = 按清单删。MVP 做单向同步即可（用户改了落地文件 → 检测到漂移就警告"覆盖或放弃"，不做反向回写）。

## 3. 本地落地：专属工作目录（employee home）

你的直觉——"一个落地员工一个专属工作目录，会话从这里开始"——我认为是对的，而且它恰好解决了"数字员工 + session = 工作实例"的身份连续性问题。建议结构：

```
~/digital-staff/<host>/<employee-id>/      # employee home = 员工的"工位"
  CLAUDE.md 或 AGENTS.md                    # adapter 由 persona.md 生成
  .claude/skills/…                          # adapter 由 spec.skills 生成（按 host 落对应位置）
  .workbench-manifest.json
  memory/                                   # 员工跨会话的长期记忆（persona 里声明"你的记忆在 ./memory/"）
  jobs/                                     # ★ 具体工作目录挂载点
  sessions/                                 # 每次会话的元数据记录
```

关键是"**跳转到具体工作目录**"怎么实现。这里有个坑要指出：多数底座（ClaudeCode 为代表）是在**启动时按 cwd 及其祖先目录**发现配置的——会话启动在 home、然后 `cd` 到别处，员工身份配置未必跟着走。三种方案：

- **方案 A（推荐，正好落实你的想法）：把项目挂进 home 下面**。`jobs/<project>` 用 Windows 目录联接（`mklink /J`）指向真实项目目录，会话直接**启动在 `home/jobs/<project>`**。ClaudeCode 向上走祖先目录时会找到 home 的 CLAUDE.md 和 skills——员工身份天然生效，且真实项目目录零污染、同一项目可同时挂到多个员工的工位下。Windows junction 对进程基本透明（不像 symlink 常被 realpath 解析掉），恰好是这个方案在 Windows 上可靠的原因。
- **方案 B（fallback）：启动在项目目录 + 启动参数注入身份**。如 `claude --append-system-prompt "$(persona)" --settings <home>/settings.json`。适合不支持祖先目录发现的底座，由各 adapter 自己选。
- **方案 C（不推荐）：把配置装进项目目录**。污染项目、多员工同项目会打架。

所以适配层的抽象契约是两个纯函数：

```
adapt(spec, host, home_dir)        → 落地文件 + manifest     # 安装期
launch(deployment, workdir, task)  → 底座 CLI 启动命令        # 会话期，A/B 策略由 adapter 内部决定
```

## 4. Session = 工作实例

MVP 里 session 可以做得很薄：工作台 `launch` 时在 `home/sessions/<timestamp>.json` 落一条 `{workdir, task, host_session_id}`，续聊直接复用底座原生机制（`claude --resume` 等）。"一位数字员工的一个工作实例"这个等式成立的根基是：**身份（home + persona + memory）跨会话不变，会话只是同一身份的一次运行**——memory/ 目录哪怕 MVP 只是个空目录加一句 persona 声明，也把这个语义占住了。

---

## 一句话总结 MVP 边界

- spec = `employee.yml + persona.md + skills/`，别的都不要
- 工作台 = specs 仓库 + registry 台账 + `install/launch` 两个动词
- adapter = 每个 host 一个，`adapt` + `launch` 两个纯函数，落地物是可重新生成的编译产物
- home 工位 + junction 挂载项目，是"抽象配置"与"cwd 强相关的底座现实"之间成本最低的桥

如果你认可这个框架，下一步值得先做的是：拿 `staff.yml` 里的一个员工（比如 dev-engineer）手工按上述结构摆一个 spec 包，写第一个 claude-code adapter 脚本跑通 install → junction → launch 全链路，验证方案 A 在你的 Windows 环境上配置发现确实生效——这是整个设计里唯一有实证风险的点。

# 问题2：

关于本地落地，除了我提到的专属工作目录这个思路，你还有其他更好的思路吗？

# 回答：

有，而且值得把这个问题拆开看。"专属工作目录"方案的本质是**把员工身份锚在目录层（cwd 祖先发现）**——这只是身份锚点的一种选择。按"身份锚在哪一层"分类，至少还有四种思路：

---

## 思路一：配置域隔离（身份锚在用户配置层）⭐ 我认为比目录方案更好

几乎所有主流底座都支持用环境变量重定向"用户级配置目录"：

- ClaudeCode：`CLAUDE_CONFIG_DIR`
- Codex：`CODEX_HOME`
- OpenCode：`OPENCODE_CONFIG` / `XDG_CONFIG_HOME`

于是员工落地 = **一个专属配置目录 + 一个启动包装器**：

```
~/digital-staff/<employee-id>/
  config/claude/          # adapter 生成的"用户级"配置：CLAUDE.md、skills、settings
  memory/
  launch.ps1              # $env:CLAUDE_CONFIG_DIR = "...config\claude"; claude
```

会话**直接启动在真实项目目录**，身份从被劫持的"用户层"注入。对比你的目录方案：

- **不需要 junction**，绕开了"祖先目录发现是否可靠"这个唯一实证风险点（junction 在个别工具里会被 realpath 解析、被 `.gitignore`/文件监视器搞出怪问题）；
- 同一项目多个员工并行天然无冲突，各自一个 config 域；
- 员工身份对项目目录**零侵入、零痕迹**；
- 附带解决了一个目录方案没解决的问题：**账号/凭证/历史也随员工隔离**（config dir 里通常还存 session 历史、认证态），"员工"的拟人化程度反而更高。

代价：依赖各 host 提供该环境变量（主流都有，Qoder CLI 需确认）；以及登录态要每员工各配一次。

## 思路二：纯启动器方案（身份锚在进程层，无持久落地）

不落任何目录，工作台在 launch 时现场组装身份：`claude --append-system-prompt "$(persona)" --settings <spec>/settings.json ...`。员工不是"装出来的"，是"每次启动时算出来的"。

- 优点：零漂移问题（没有编译产物就没有漂移）、升级即时生效、实现最薄；
- 缺点：受限于各 host 的 CLI 旗标能力（skills 注入常常没有对应旗标）、员工没有"家"——memory/会话史无处安放，"员工+会话=工作实例"的身份连续性语义变弱。

适合当**降级路径**：某个底座不支持配置域隔离时，adapter 退到这个策略。

## 思路三：插件化落地（身份锚在插件层）

把员工 spec 编译成 host 原生插件（你的 `agents-team` 现在就是这么干的），用 host 自己的插件机制安装。

- 优点：复用 host 的分发/更新/卸载基建，adapter 只做"spec → 插件包"的格式转换；
- 缺点：插件通常是**用户全局生效**的——所有员工的 skills 同时加载，员工之间没有边界，"一次会话 = 某一位员工"这个语义靠不住。除非叠加思路一（每员工一个 config 域、域内只装自己的插件），但那样主体已经是思路一了。

## 思路四：容器化落地（身份锚在运行环境层）

每个员工 = 一个镜像（底座 CLI + 配置烘焙进去），项目目录 volume 挂载进来，一个 session = 一个容器实例。

- 优点：隔离最彻底——员工能被赋予独立的网络/文件系统/凭证边界，天然支持并行多实例、资源限额、"解雇即删镜像"；这是数字员工规模化后的终局形态；
- 缺点：对 MVP 太重（Docker/WSL2 依赖、Windows 文件挂载性能、交互式 TUI 体验打折）。

不建议 MVP 做，但建议 MVP 的 adapter 接口**为它留位**：`adapt/launch` 契约不变，容器只是又一个 "host"。

---

## 我的建议：MVP 用「思路一 + 你的员工 home」的合体

你的"专属工作目录"里其实混了两个概念，拆开各归其位：

1. **员工的家（home）**——存 spec 编译产物、memory、sessions 台账。这个概念保留，它承载身份连续性，是对的；
2. **身份注入机制**——从"cwd 祖先发现 + junction"换成"`CLAUDE_CONFIG_DIR` 指向 home/config"。会话直接在真实项目目录启动，不再需要 jobs/ 挂载点。

即：**家还在，但员工不再要求"你到我工位来干活"，而是"我带着我的工具箱去你的项目现场"**。junction 方案降级为某个底座不支持 config-dir 重定向时的 fallback，纯启动器是最后兜底——这三档正好都收敛在 adapter 的 `launch()` 内部，工作台抽象层完全不感知。

另外补一个与员工身份正交、但对"工作实例"很有价值的机件：**session 级用 git worktree**。同一员工对同一项目开多个并行会话时，`launch` 可选为每个 session 开一个 worktree，避免两个工作实例在同一工作副本上互相踩——这是目录方案和配置域方案都不自带、但都能叠加的能力。

# 回答：

这些问题基本都踩在点子上，我逐个给判断，最后补几个我认为能让原型"更会讲故事"的设计。

## 1. 配置创建 / 安装适配 分两步 —— 对，而且要在信息架构上分开

不只是流程上分两步，建议整个工作台的**信息架构就按三层对象模型来切页面**：

```
📦 配置库（EmployeeSpec，资产）→  👤 在岗员工（Deployment，实例）→  💬 会话（Session，运行）
```

- **配置库页**：配置卡片列表（名称、职责、SKILL 数、已安装到几个底座）。这里体现"配置可保存复用"。
- **在岗员工页**：员工卡片列表——这是给相关方看的主视觉页（见第 6 点）。
- 创建配置的终点是"保存到配置库"，然后给一个**可选的**"立即安装"引导，而不是强制串成一个向导。这样"配置是资产、员工是实例"的概念在交互上自解释：同一份配置卡片上可以看到"已安装：ClaudeCode ×1、OpenCode ×1"。

## 2. 配置创建页（MVP）应包含什么

左侧表单 + 右侧实时预览，四个区块就够：

| 区块     | 内容                                                          |
| ------ | ----------------------------------------------------------- |
| 基本信息   | 员工 ID、显示名、**头像**、一句话职责描述                                    |
| 角色说明   | persona 的 markdown 编辑框，**给 2-3 个内置模板**（开发工程师/测试工程师/调研员）一键填充 |
| 模型档位   | 下拉选抽象档位（编码档/评审安全档/执行档…），**不选具体模型**——这个细节在演示时正好用来讲"配置与底座无关"  |
| SKILLs | 从列表勾选（见下）                                                   |

**右侧实时预览强烈建议做**：随表单变化实时渲染出配置包的文件树（`employee.yml + persona.md + skills/…`）和 yaml 内容。成本极低（就是个模板渲染），但它把"抽象配置包"这个概念从口头解释变成了肉眼可见的东西——对相关方演示价值很高。

头像别省，拟人化是这个产品叙事的核心，demo 时"一张工牌"比十页 PPT 有说服力。

## 3. SKILL 来源：从数字资产平台拉取，不要在工作台自定义

明确建议后者，理由：

- **产品定位**：工作台是"组装与运行"，资产平台是"生产与治理"。SKILL 创作有自己的生命周期（编写、评审、版本、上下架），塞进工作台会让 MVP 边界失控；
- 资产平台**已经存在并部署**了，这是现成的故事线："资产平台产出能力 → 工作台组装成员工"，两个系统各就其位，汇报时这个分工图很好画；
- 工作台自定义 SKILL 做出来也只会是个简陋的 markdown 编辑器，反而拉低观感。

可以留一个次要入口"导入本地 SKILL.md"（收在角落甚至 MVP 先不做），作为逃生通道。

## 4. MVP 接受什么形式的 SKILL

就一种：**SKILL.md 标准包**（目录含 `SKILL.md`，可带 `references/`），即 ClaudeCode skill 的事实标准格式——这正是上次讨论选定的"各底座最大公约数"。选择器需要的元数据：`name / description / version / tags / 来源`。明确不收：带 hooks、MCP 依赖、可执行脚本的复杂 skill——这些放 v2，按底座能力协商降级。

## 5. 原型阶段 SKILL 写死 —— 对，但要"写得像真的"

完全同意 mock 掉资产平台，只做选择逻辑。两个建议让 demo 更可信：

- **用你们真实存在的 skill 名字**填这个写死列表，比如 `ieidev-tdd-methodology`、`ieidev-test-points`、`ieidev-ui-autotest`、`ieidev-sr-authoring`、`ieidev-secure-coding`、`ieidev-env-recon`……配上真实的一句话描述和 tag（开发/测试/需求/安全）。相关方里懂行的人一眼就能看出这不是空壳；
- 交互形态：搜索框 + tag 筛选 + skill 卡片（名称/描述/版本/来源标"数字资产平台"），点击加入右侧"已选能力"栏。加个假的"从资产平台同步"刷新按钮转一秒，暗示背后有真实集成点。

## 6. 安装逻辑的交互设计

入口两个：配置详情页的"安装为数字员工"按钮 / 在岗员工页的"+ 聘用新员工"（先选配置）。安装本身建议做成**一个三步弹层/页面**：

1. **选底座**：卡片式（ClaudeCode / Codex / OpenCode / QoderCLI 各一张，带 logo），每张卡显示本机检测状态——"✅ 已检测到 v2.x" / "⚠️ 未检测到，去安装"。多选（一份配置装多个底座 = 多位员工）。
2. **实例信息**：员工实例名/花名（默认 = 配置名 + 底座后缀）、工位目录（默认 `~/digital-staff/<host>/<id>`，可改）。适配策略（config-dir 隔离/junction/启动器）**不暴露**，收进"高级选项"折叠里——那是 adapter 的内政。
3. **执行与结果**：这一步是**演示适配层概念的主舞台**，别做成一个转圈 spinner 完事。做成步骤流水：

```
① 读取配置包 v0.1.0
② 适配 ClaudeCode：persona.md → CLAUDE.md ✓   skills → .claude/skills/ ✓   编码档 → opus ✓
③ 写入工位 ~/digital-staff/claude-code/dev-engineer/ ✓
④ 注册台账 ✓
```

每行带一句真实的转换日志。**同一份配置装到两个底座时，②的日志内容不同**（OpenCode 那边是 `persona.md → AGENTS.md`、档位映射成 `deepseek-v4-flash-free`）——这一屏就把"抽象配置 × 适配层 = 具体员工"讲透了，是整个原型里概念密度最高、也最值得打磨的一屏。

结果页落到一张**员工工牌卡**：头像、花名、底座 badge、工位路径、状态（空闲），主按钮"启动会话"。

## 补充：一条 demo 主线建议

给相关方演示时按这条线走一遍，正好把三层模型走完：

**配置库空态 → 创建"开发工程师"配置（右侧预览实时长出文件树）→ 保存 → 安装到 ClaudeCode + OpenCode（看两份不同的适配日志）→ 在岗员工页出现两张工牌 → 点"启动会话"拉起终端**

最后一步哪怕只是 `start powershell` 带个欢迎横幅，闭环感也完全不同——建议原型里做真，成本很低但它证明了这不只是画饼。
