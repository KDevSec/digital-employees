## 1. 问题：安装到底座的痛点

当前架构（白皮书 v0.5）：员工 = 扩展配置包，通过 UPP 安装到智能体底座（Claude Code / CodeBuddy / Qoder / opencode），底座提供 agent 运行时。

**痛点清单**：

| 痛点 | 说明 |
|------|------|
| **UPP 适配器维护成本** | 8+ 底座每个写 shim（安装面 + 运行面），底座升级时每适配器都要跟进 |
| **hook 差异** | CC/Cursor/opencode 命名和集成方式都不同（PreToolUse vs tool.execute.before vs stdin/stdout vs JS 模块） |
| **上下文污染** | 底座自己的系统提示词/工具/会话历史和员工的混在一起，影响运行效果 |
| **运行效果受限** | 底座不支持的功能员工也用不了（如某些底座无 subagent、无 hook） |
| **记忆/观测需桥接** | HUD 读 .ieidev/ 文件 → 推 OTLP，间接路径，非 agent 循环内直接生成 |
| **可达 Level 受限** | 不同底座可达 Level 不同（CC/opencode L3，TRAE/Pi L1-L2，OpenClaw L0-L1） |

## 2. 替代方案：工作台就是运行时

### 核心思路

**不安装到任何底座——工作台自己实现 agent 循环，直接调 LLM API + MCP 工具。**

```
当前模式：                              替代模式：

工作台（管理 UI + HUD）                  工作台（管理 UI + Agent 运行时 + HUD + 记忆 + 观测）
  ↓ UPP 安装到                             ↑ 直接加载
底座（CC / CB / Qoder）← 运行时            员工（AGENTS.md + skills）
  ↑ 加载                                    → 直接调 LLM API（Claude / OpenAI / Qwen）
员工（AGENTS.md + skills）                  → 通过 MCP 执行工具
                                           → 直接写记忆 / 发 OTLP
                                           → 自己的 hook 系统
```

### 灵感来源

- **Orkas**（[orkas-ai/Orkas](https://github.com/orkas-ai/Orkas)，1158 stars）：local-first 多 Agent 桌面应用，自己调 LLM API + 调度子进程，不安装到任何底座。BYO LLM keys。
- **Claude-code-router**（36.6k stars）：local control plane 模式，一个本地控制面管所有 AI agent。
- **MCP 生态成熟**：MCP 已是工具接入事实标准，工作台作为 MCP client 可以调用任意工具，不需要底座提供工具集。

## 3. 技术拆解：工作台需要什么才能成为运行时

| 能力 | 怎么实现 | 难度 | 说明 |
|------|---------|------|------|
| **LLM API 调用** | 直接 HTTP 调 Claude/OpenAI/Qwen API（BYO key，同 Orkas） | 低 | 标准 API 调用，已有大量 SDK |
| **Agent 循环** | system prompt + messages → LLM → tool_use → 执行 → tool_result → 重复（标准 ReAct/tool-use loop） | 中 | 标准模式，需处理上下文窗口管理 / 中断 / resume |
| **工具执行** | **MCP client**——MCP 已是我们的标准！工作台作为 MCP client 调用 MCP server | 低 | MCP 生态已有 file ops / bash / git / web 等工具 server |
| **Skill 加载** | 读 SKILL.md → 注入到 system prompt / 按需加载（渐进式披露三级） | 低 | 已设计（白皮书 §4.1 L1） |
| **Hook 系统** | 自己实现 PreToolUse / PostToolUse / SessionStart 等（CC hooks 规范，事实标准） | 中 | 比适配 8 个底座简单得多——只实现一次 |
| **记忆** | 直接读写 .ieidev/memory/（文件基底）或接 TencentDB Agent Memory SDK | 低 | 已设计 |
| **OTLP 观测** | agent 循环内直接生成 span（trace_id / span_id / gen_ai.* 属性） | 低 | 写入 events.jsonl（OTLP span 格式） |
| **Session 管理** | 对话历史 + 上下文窗口 + 断点续跑 | 中 | 需自建，但 flow-state.json 已有断点续跑设计 |

### 关键洞察

**工作台成为运行时的工程量，比维护 8 个底座的 UPP 适配器更少。**

原因：
1. LLM API 调用是标准 HTTP，已有成熟 SDK
2. 工具执行走 MCP——已有标准，不需要每底座适配
3. Hook 只实现一次（CC hooks 规范），不需要每底座转换
4. 记忆/观测直接集成，不需要桥接层

## 4. TencentDB Agent Memory 重新调研（修正）

> ⚠️ 之前调研（深度调研报告 §4.2）找错了项目——找到的是 `vectordatabase-sdk-python`（向量数据库 SDK），不是 `tencentdb-agent-memory`（Agent 记忆平台）。以下为修正。

### 项目信息

| 维度 | 内容 |
|------|------|
| GitHub | [TencentCloud/tencentdb-agent-memory](https://github.com/TencentCloud/tencentdb-agent-memory) |
| License | MIT |
| 技术栈 | Node.js >= 22.16 |
| 定位 | "Agents remember. Humans innovate." — 团队级 AI Agent 记忆中枢 |

### 四大记忆资产

| 资产 | 说明 | 与我们的对应 |
|------|------|------------|
| **Chat Memory** | L0（原始对话）→ L1（原子事实）→ L2（场景知识）→ L3（用户画像）四层蒸馏 | ≈ 我们的 Step → Q/R/F（但 TencentDB 是自动蒸馏，我们是人工归纳） |
| **Skill** | 从对话和工具调用中提取可复用工作流，支持版本/资源文件/触发边界/执行步骤/验证规则 | ≈ 我们的 skill_store + 员工自进化 |
| **Wiki** | 产品/设计文档转化为带链接图的结构化页面（受 Karpathy LLM Wiki 启发） | ≈ 我们的 knowledge/ 目录（但更结构化） |
| **CodeGraph** | 索引代码符号/文件/调用关系/影响路径，让 Agent 修改前做影响分析 | ≈ 我们的 ieidev-codegraph（但更成熟） |

### 架构

```
TencentDB-Agent-Memory/
├── MemoryCore/        核心记忆引擎（L0-L3 蒸馏管线）
├── MemoryHub/         控制面板（团队/Agent 创建、资产绑定、权限管理）
├── MemoryKnowledge/   知识管理（Wiki + CodeGraph + OpenAPI）
├── MemoryProxy/       代理层——连接 Claude Code / CodeBuddy / OpenClaw / Hermes
├── MemoryPanel/       前端控制面板
├── sdk/memory-core/   供第三方集成的 SDK（@tencentdb-agent-memory/memory-core）
└── deploy/            Docker 一键部署
```

### 关键特性

| 特性 | 说明 |
|------|------|
| **本地部署** | ✅ Docker 一键部署 `./start-all.sh`，Panel 在 localhost:8125 |
| **检索** | BM25 + 向量 + RRF 互惠排名融合，回退到 L0/L1 |
| **权限** | Fixed Binding + ACL（private / team / restricted / agent 四级） |
| **Agent 集成** | MemoryProxy 模块——明确支持 Claude Code / CodeBuddy / OpenClaw / Hermes |
| **SDK** | `@tencentdb-agent-memory/memory-core` npm 包 |
| **性能** | PersonaMem 从 48% → 76%（相对提升 59%） |
| **与 OTLP** | ❌ 当前无直接关系——但可以打通 |

### 与我们记忆方案的关系

| 维度 | 我们（.ieidev/memory/） | TencentDB Agent Memory |
|------|------------------------|------------------------|
| 存储介质 | markdown + JSONL 文件 | Docker 服务（可能内部用 DB） |
| 记忆模型 | Step/Q/G/R/F 五类叙事 | L0-L3 四层蒸馏 + Skill/Wiki/CodeGraph |
| 蒸馏方式 | 人工（每日汇总从文件聚合） | 自动（LLM 驱动 L0→L1→L2→L3） |
| 本地部署 | 是（纯文件） | 是（Docker） |
| git 可追踪 | 是 | 否 |
| 外部依赖 | 无 | Docker + Node.js |
| CodeGraph | 有（ieidev-codegraph） | 有（更成熟） |
| 团队共享 | 无（单开发者） | 有（team/restricted/agent 权限） |

### 配合方式

**如果工作台自跑（不用底座），可以直接集成 TencentDB Agent Memory SDK**——不需要 MemoryProxy（那个是给 Claude Code / CodeBuddy 桥接用的）：

```
工作台 agent 循环
  │
  ├── 轻量模式（MVP，零依赖）：
  │   └── .ieidev/memory/ 文件基底（不变）
  │
  └── 增强模式（后续，接 TencentDB Agent Memory）：
      ├── Chat Memory → L0-L3 自动蒸馏（替代人工每日汇总）
      ├── Skill → 从对话提取可复用工作流（替代/增强 skill_store）
      ├── Wiki → 结构化文档知识库（增强 knowledge/ 目录）
      └── CodeGraph → 代码影响分析（增强 ieidev-codegraph）
```

## 5. OTLP + 记忆 + 观测统一事件源

### 当前问题

观测和记忆是分离的两条管线，同一个事件写两次、格式不同、无法关联：

```
观测管线：引擎 events → OTLP span → HUD → Collector → Honeycomb
记忆管线：引擎 events → events.jsonl → step-recorder → .ieidev/memory/
```

### 统一方案：OTLP span 格式作为 events.jsonl 的事件格式

**引擎只写一次**（OTLP span 格式写入 events.jsonl），双消费：

```jsonl
{
  "trace_id": "flow-dev-engineer-coding-flow-001",
  "span_id": "span-006",
  "parent_span_id": "span-005",
  "name": "gate.g-code-review",
  "attributes": {
    "gen_ai.agent.name": "dev-engineer",
    "gen_ai.conversation.id": "coding-flow",
    "gen_ai.evaluation.score": 85,
    "gen_ai.evaluation.label": "PASS",
    "gen_ai.usage.input_tokens": 12000,
    "gen_ai.usage.output_tokens": 3500,
    "ieidev.flow.slug": "coding-flow-run-001",
    "ieidev.node.id": "n6b",
    "ieidev.gate.verdict": "pass"
  },
  "events": [...],
  "status": "ok",
  "start_time": "2026-08-12T10:00:00Z",
  "end_time": "2026-08-12T10:02:30Z"
}
```

```
双消费：
  ├── HUD 服务读 events.jsonl → 推 OTLP → Honeycomb（观测管线）
  └── step-recorder 读 events.jsonl → 抽 key_facts → 写 .ieidev/memory/（记忆管线）
```

### 好处

| 好处 | 说明 |
|------|------|
| **单次写入，双消费** | 引擎只写一次 events.jsonl |
| **trace_id 贯穿** | 一次 flow = 一个 trace_id，Step 记录带 trace_id，记忆召回可按 trace 关联完整链路 |
| **parent_span_id 因果链** | span 间有父子关系，"哪个 gate 触发了哪个 retry"可追溯 |
| **OTel GenAI 标准属性** | gen_ai.usage.* / gen_ai.evaluation.* / gen_ai.agent.name 直接用标准字段 |
| **未来可切真 OTLP** | events.jsonl 是"文件版 OTLP"，未来接真 Collector 格式完全兼容 |
| **与 TencentDB Agent Memory 配合** | trace_id 可作为记忆和 TencentDB 之间的关联键 |

### 与文件基底不变式的关系

**不冲突**——events.jsonl 仍然是 JSONL 文件，只是每行 JSON 从 ad-hoc 格式升级为 OTLP span 格式。人类仍可 `cat` / `grep` / `jq` 读，git 仍可 diff。

### 与 MemOS L1/L2/L3 的呼应

```
MemOS L1 Traces（轨迹）     ← OTLP span 就是结构化的 L1 Trace
MemOS L2 Policies（策略）   ← 未来可选：从 L1 span 自动归纳
MemOS Skills               ← L2 结晶化

TencentDB Chat Memory      ← L0→L1→L2→L3 自动蒸馏（比 MemOS 更实用）
```

用 OTLP span 格式记 events.jsonl = 给自动蒸馏铺好结构化数据基础。

## 6. 三种模式对比

| 维度 | A. 安装到底座 | B. 工作台自跑 | C. 混合（B 为主 + A 兼容） |
|------|-------------|-------------|------------------------|
| **运行时** | 底座（CC/CB/Qoder） | 工作台自己 | 工作台为主，底座为兼容 |
| **UPP 适配器** | 8+ 底座每个写 shim | ❌ 不需要 | 薄兼容层（仅常用底座） |
| **hook 一致性** | 每底座不同，需转换 | ✅ 自己实现，完全一致 | 主路径一致，兼容路径有差异 |
| **上下文控制** | 受底座限制 | ✅ 完全自控 | 主路径自控，兼容路径受限 |
| **工具访问** | 受底座工具集限制 | ✅ MCP 标准，任意扩展 | 主路径 MCP，兼容路径走底座 |
| **记忆集成** | 需桥接 | ✅ 直接读写 | 主路径直接，兼容路径桥接 |
| **OTLP 观测** | 需 HUD 桥 + Pilot | ✅ 循环内直接生成 | 主路径直接，兼容路径桥接 |
| **用户习惯** | 用熟悉的 Claude Code | 用工作台 | 主路径用工作台，兼容路径可用 CC |
| **工程量** | 高（8 适配器 + 持续维护） | 中（1 个运行时，一次性） | 最高（运行时 + 兼容层） |
| **多底座价值** | 一份资产多底座上岗 | ❌ 牺牲多底座 | 保留但降级为兼容 |
| **运行效果** | 受底座限制 | ✅ 最佳 | 主路径最佳，兼容路径打折 |
| **TencentDB Memory 集成** | 需 MemoryProxy 桥接 | ✅ 直接用 SDK | 主路径直接，兼容路径 proxy |

## 7. 混合方案（推荐）

### 架构

```
主路径：工作台自跑（最佳运行效果）
  ├── 直接调 LLM API（Claude / OpenAI / Qwen，BYO key）
  ├── MCP 工具层（工作台作为 MCP client）
  ├── 自己的 hook 系统（CC hooks 规范，只实现一次）
  ├── 记忆直接集成
  │   ├── 轻量模式：.ieidev/memory/ 文件基底（MVP）
  │   └── 增强模式：TencentDB Agent Memory SDK（后续）
  ├── OTLP 观测直接生成（events.jsonl 用 OTLP span 格式）
  └── Session 管理（flow-state.json 断点续跑）

兼容路径（可选，Phase 2+）：UPP 适配器（降级运行）
  ├── 也支持安装到 Claude Code（习惯用 CC 的用户也能用）
  └── 但这是"兼容层"不是"主路径"——效果可能打折
```

### 为什么推荐混合

1. **主路径给最佳效果**：工作台自跑 = 完全控制 = 最佳运行效果
2. **兼容路径给用户选择**：不是所有人愿意换工具，UPP 兼容层让 CC 用户也能用
3. **MVP 更简单**：先做主路径（工作台自跑），不需要 UPP——UPP 推到 Phase 2+
4. **工程量可控**：主路径是一次性工作（agent 循环 + MCP + LLM API），比 8 适配器更少

## 8. 对 MVP 的影响

### 如果选择"工作台自跑"为主路径

MVP 模块变化：

| 原 MVP 模块 | 修正 |
|-----------|------|
| M1 shared-protocol | 不变 |
| ~~M2 UPP CodeBuddy 适配~~ | **替换为 M2' agent-runtime**（工作台内 agent 循环 + MCP client + LLM API client + hook 系统） |
| M3 员工管理 + 创建向导 | 简化——不需要"安装到底座"，改为"在工作台中加载" |
| M4 AgentHub skill 拉取 | 不变 |

**MVP 不再需要 UPP**——不需要写 CodeBuddy shim，不需要处理 CodeBuddy 的 hook 兼容性。工作台自己就是运行时。

### MVP 修正后

| # | 模块 | 前端 | 后端 | 依赖 |
|---|------|------|------|------|
| M1 | **shared-protocol** | — | manifest schema + skill schema + 身份三元组 | 无 |
| M2' | **agent-runtime** | — | LLM API client + agent 循环（ReAct loop）+ MCP client + hook 系统 + session 管理 | M1 |
| M3 | **员工管理 + 创建向导** | 员工列表 + 创建向导（skill 从 AgentHub 选）+ 详情 + 对话界面 | manifest 扫描 + 注册 + 包构建 + 加载到 agent-runtime | M1 + M2' + M4 |
| M4 | **AgentHub skill 拉取** | skill 浏览/搜索 | AgentHub API 客户端 | M1 |

### 关键路径变化

```
原：M1 → M2(UPP CB适配) + M4 并行 → M3
新：M1 → M2'(agent-runtime) + M4 并行 → M3
```

M2'（agent-runtime）比 M2（UPP 适配）更通用——不绑定 CodeBuddy，且产出可复用于所有员工。
