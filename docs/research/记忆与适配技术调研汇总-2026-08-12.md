| 作者团队 | 39 人，Zhiyu Li 等 |

**"MemTensor" = "Memory Tensor" = "记忆张量"。**

### 2.2 核心概念：MemCube（记忆立方体）

论文核心思想：**将记忆视为操作系统管理的系统资源**（类比 OS 管理 CPU/内存），而非 RAG 那种无状态的外部检索补丁。

MemCube 是基本单元：
- 封装记忆内容 + 元数据（provenance 来源追踪 + versioning 版本管理）
- 可组合（compose）、可迁移（migrate）、可融合（fuse）
- 支持在记忆类型之间灵活转换

### 2.3 三种记忆类型

| 记忆类型 | 代码模块 | 说明 |
|---------|---------|------|
| **Plaintext（纯文本）** | `textual/` | 树结构记忆（tree）、偏好记忆（preference）、技能记忆（skill）。`TextualMemoryItem` 带 `SourceMessage` 溯源 + `ArchivedTextualMemory` 版本归档 |
| **Activation-based（激活）** | `activation/` | KV cache（`kv.py`）、vLLM KV（`vllmkv.py`）。直接操作 LLM 的 KV 缓存 |
| **Parameter-level（参数级）** | `parametric/` | LoRA 适配器（`lora.py`）。将记忆编码进模型参数 |

三个设计目标：**可控性（controllability）、可塑性（plasticity）、可演化性（evolvability）**。

### 2.4 L1/L2/L3 三层记忆演化模型（核心设计）

记忆不是静态存储，而是**自动从低层向高层演化**：

**L1（Traces 轨迹）** — 原始情景记忆：
- `capture/` 模块从 `episode.finalized` 事件触发
- Step extractor 提取步骤 → normalizer 归一化 → reflection extractor 提取反思
- α scorer 对反思质量打分
- Embedder 生成 `vec_summary` + `vec_action` 向量
- 记录 V（价值）和 R（奖励），优先级带指数时间衰减
- ≈ 我们的 Step（执行日志）

**L2（Policies 策略）** — 跨任务策略归纳：
- 监听 `reward.updated` 事件
- 高 V 值轨迹与已有策略关联（blended cosine + signature bonus + hard-gate）
- 未匹配轨迹进入 `l2_candidate_pool`，按 `signature = primaryTag|secondaryTag|tool|errCode` 分桶
- 当桶内积累 ≥ N 个不同 Episode → LLM 归纳提示 → 生成候选策略
- `gain = weightedMean(with) − mean(without)` 评估收益
- 生命周期：candidate → active → retired
- ≈ 我们的 Q/R（但 MemOS 是 LLM 自动归纳，我们是人工归纳）

**L3（World Models 世界模型）** — 跨任务世界模型抽象：
- 监听 `l2.policy.induced` 事件
- 活跃 L2 按 domain key 分桶 + centroid cosine 分裂 → 兼容集群
- 每个集群调用 LLM 抽象提示 → 生成 (ℰ, ℐ, C) 草稿（Environment, Intent, Constraints）
- 与最近世界模型合并（cosine ≥ θ）或新建
- 我们没有这一层

**Skills（技能结晶化）** — 从 L2 策略提取可调用技能：
- 监听 L2 策略诱导/更新 + 奖励更新
- 资格检查 → 证据收集 → LLM 结晶化草稿 → 启发式验证器 → 打包为 `SkillRow`
- 生命周期：probationary → active/retired（Beta(1,1) 后验 η）
- ≈ 我们的 skill_store

### 2.5 检索机制

三层混合检索：

| 层级 | 检索内容 | 机制 |
|------|---------|------|
| Tier-1 | Skill | 技能匹配 |
| Tier-2 | Trace + Episode | 标签预过滤 + 轨迹召回 |
| Tier-3 | World Model | 世界模型匹配 |
| 融合 | RRF + MMR | Reciprocal Rank Fusion + Maximal Marginal Relevance 多样性排序 |

五个检索入口：`turnStart` / `toolDriven` / `skillInvoke` / `subAgent` / `repair`

### 2.6 奖励与反馈系统

**奖励系统**（`reward/` 模块）：
- 每个 Episode 的 `R_human ∈ [-1,1]`，通过 rubric LLM 评分（三轴：goal / process / satisfaction）
- 反思加权反向传播：`V_T = R_human`，`V_t = α_t·R + (1-α_t)·γ·V_{t+1}`
- 优先级带指数时间衰减

**反馈系统**（`feedback/` 模块）：
- 分类器 + 修正器 + 决策修复（偏好 / 反模式）
- 自然语言反馈可纠正、补充或替换已有记忆

### 2.7 本地插件架构

MemOS 有四种部署模式，其中**本地插件**最贴近我们场景——100% 端侧、零云依赖：

```
apps/memos-local-plugin/
├── adapters/openclaw/          ← 进程内 TS 适配器
├── adapters/hermes/            ← JSON-RPC 桥接到 Python
├── agent-contract/             ← MemoryCore 接口 + events + errors + DTO + jsonrpc
└── core/                       ← Agent 无关的算法核心
      ├── pipeline/             ← 编排器 (onTurnStart/onTurnEnd/onFeedback/onShutdown)
      ├── capture/              ← 记忆采集 (step-extractor + reflection-extractor + α-scorer + embedder)
      ├── memory/
      │     ├── l1/             ← L1 轨迹存储 + 多模态搜索 + 优先级
      │     ├── l2/             ← L2 策略归纳 (跨任务模式提取)
      │     └── l3/             ← L3 世界模型抽象 (跨任务世界模型)
      ├── skill/                ← 技能结晶化 (L2 → 可调用 Skill)
      ├── retrieval/            ← 三层检索 (Tier1-Skill / Tier2-Trace / Tier3-World) → RRF + MMR
      ├── reward/               ← 奖励系统 (R_human → V_t 反向传播)
      ├── feedback/             ← 反馈分类 + 修正 + 决策修复

      ├── embedding/            ← 6 个嵌入提供商 (含本地 MiniLM)
      ├── llm/                  ← 6 个 LLM 提供商 (含 local_only 模式)
      ├── hub/                  ← 可选团队共享
      └── telemetry/            ← 匿名使用统计
```

技术栈：TypeScript + Node.js + SQLite（持久化）+ FTS5（全文搜索）+ 向量搜索（本地嵌入）

### 2.10 不采用（与文件基底冲突）

| 冲突点 | 原因 |
|--------|------|
| SQLite/Neo4j/Qdrant | 铁律：markdown + JSONL 文件基底，人类可读、git 可追踪、零依赖 |
| 向量嵌入存储 | 文件无法存向量；用 grep + 召回 hook 替代 |
| 异步记忆调度器 | step-recorder fire-and-forget 已够用，工程记录不是高并发生产系统 |
| LLM 全自动归纳 | token 消耗高 + 工程记录可控性要求人工归纳为底线 |
| 多模态记忆 | 我们场景不需要（工程记忆只处理文本） |

## 3. OTLP + 记忆 + 观测统一事件源

### 3.1 问题

当前观测和记忆是分离的两条管线，同一个事件写两次、格式不同、无法关联：

```
观测管线：引擎 events → OTLP span → HUD → Collector → Honeycomb
记忆管线：引擎 events → events.jsonl → step-recorder → .ieidev/memory/
```

### 3.2 方案：OTLP span 格式作为 events.jsonl 的事件格式

**引擎只写一次**（OTLP span 格式写入 events.jsonl），双消费：

```jsonl
{
  "trace_id": "flow-dev-engineer-coding-flow-001",
  "span_id": "span-006",
  "parent_span_id": "span-005",
  "name": "gate.g-code-review",
  "kind": "internal",
  "attributes": {
    "gen_ai.agent.name": "dev-engineer",
    "gen_ai.conversation.id": "coding-flow",
    "gen_ai.evaluation.score": 85,
    "gen_ai.evaluation.label": "PASS",
    "gen_ai.usage.input_tokens": 12000,
    "gen_ai.usage.output_tokens": 3500,
    "ieidev.flow.slug": "coding-flow-run-001",
    "ieidev.node.id": "n6b",
    "ieidev.gate.verdict": "pass",
    "ieidev.gate.by": "reviewer-expert"
  },
  "events": [
    {"name": "tool.dispatch", "time": "...", "attributes": {"tool": "Agent", "subagent": "dev-engineer-impl"}},
    {"name": "tool.result", "time": "...", "attributes": {"status": "ok"}}
  ],
  "status": "ok",
  "start_time": "2026-08-12T10:00:00Z",
  "end_time": "2026-08-12T10:02:30Z"
}
```

```
双消费：
  ├── HUD 服务读 events.jsonl → 推 OTLP → Honeycomb（观测管线）
  └── step-recorder 读 events.jsonl → 抽 key_facts → 写 .ieidev/memory/（记忆管线）
```

### 3.3 好处

| 好处 | 说明 |
|------|------|
| **单次写入，双消费** | 引擎只写一次 events.jsonl |
| **trace_id 贯穿** | 一次 flow = 一个 trace_id，Step 记录带 trace_id，记忆召回可按 trace 关联完整链路 |
| **parent_span_id 因果链** | span 间有父子关系，"哪个 gate 触发了哪个 retry"可追溯 |
| **OTel GenAI 标准属性** | gen_ai.usage.* / gen_ai.evaluation.* / gen_ai.agent.name 直接用标准字段，step-recorder 不用手动抽 key_facts |
| **未来可切真 OTLP** | events.jsonl 是"文件版 OTLP"，未来接真 Collector 格式完全兼容，零迁移 |
| **与 MemOS L1 对齐** | OTLP span = MemOS L1 Traces 的结构化版。未来 L1→L2 归纳时，span 格式比扁平 JSON 更容易做自动归纳 |
| **与 TencentDB 可关联** | trace_id 可作为文件记忆和 TencentDB Agent Memory 之间的关联键 |

### 3.4 与文件基底不变式的关系

**不冲突**——events.jsonl 仍然是 JSONL 文件，只是每行 JSON 从 ad-hoc 格式升级为 OTLP span 格式。人类仍可 `cat` / `grep` / `jq` 读，git 仍可 diff。只是结构更丰富。

### 3.5 记忆召回增强

```
当前召回：
  UserPromptSubmit hook → grep 关键词匹配 .ieidev/memory/ → 注入召回指针

增强后召回：
  UserPromptSubmit hook →
  ├── grep 关键词匹配（不变，快）
  └── 可选：按 trace_id 查 events.jsonl → 拉完整执行链路上下文
      "上次 dev-engineer 在这个 gate 失败后怎么处理的？"
      = 按 gen_ai.evaluation.label=FAIL + ieidev.node.id 匹配 → 找到 trace_id → 拉完整 span 链
```

## 4. Orkas + 通用 hook 代理调研

### 4.1 重要前置说明：搜索引擎幻觉

本次调研遭遇大量 WebSearch 幻觉——在"通用 agent 适配层"话题上系统性幻觉严重：

| 幻觉内容 | 实际验证 |
|---------|---------|
| `orkas-ai/multi-agent-base-adapter` 仓库 | **不存在**。orkas-ai 下只有 4 个仓库 |
| `run-loop/mcp-middleware` "universal middleware adapter" | **404 不存在**（gh API 验证） |
| opencode 的 `before_read/after_read` 等 hook 点 | **README 和官方文档均无此内容** |
| `docs.codebuddy.io/plugins/overview` 等 CodeBuddy 文档页 | **不可达** |

**启示**：在"通用适配层"方向调研时，一切 GitHub 仓库用 `gh api` 验证，一切文档用 WebFetch 直访，不信 WebSearch 摘要。

### 4.2 Orkas 真实定位

[orkas-ai/Orkas](https://github.com/orkas-ai/Orkas)（1158 stars，TypeScript）：

> "Open-source multi-agent AI desktop client — build and command your AI agent team through conversation."

**它是 Electron 桌面 GUI 应用**，让用户通过单一对话界面指挥 AI 代理团队。**不是**多智能体底座适配框架。

**底座适配策略**（与 UPP 不是一回事）：
- 第一层：LLM API 提供商适配（BYO key）——支持 Claude/OpenAI/Gemini/DeepSeek/Kimi/GLM/Qwen/MiniMax/Doubao
- 第二层：外部 CLI 编码代理作为子进程——支持 Claude Code/Codex/OpenCode/Cline

**结论**：Orkas 没有"通用适配层"概念。从 Orkas 源码学不到通用方案。

### 4.3 Orkas 可借鉴的设计

| 机制 | 说明 | 借鉴价值 |
|------|------|---------|
| **单一调度原语（`enqueue`）** | 所有分发路径汇集到同一个 enqueue 原语，无并行路由 | 高——UPP hook 分发也应单一原语 |
| **可见性切片** | 每个代理只获得 `from==me ∨ to∋me ∨ mentions∋me` 的消息切片 | 中——多代理上下文隔离 |
| **meta 自我进化文件** | 每个代理维护 COMPETENCE.md + LEARNING_STRATEGIES.md | 中——shim 可维护自己的能力描述 |
| **结构化分发 + 延迟唤醒** | `dispatch_to({to, message})` 仅暂存，接收代理在回合结束后才唤醒 | 中 |
| **基于回合的安全停止** | `MAX_WORKER_TURNS=100`，以回合数而非墙钟时间作为阈值 | 中 |

### 4.4 各底座 hook 机制实测对比（核心发现）

| 维度 | Claude Code | Cursor | opencode |
|------|-------------|--------|----------|
| 配置格式 | settings.json (hooks 字段) | hooks.json (4 层) | opencode.json (plugin 数组) + JS 模块 |
| 集成方式 | stdin/stdout JSON 脚本 | stdin/stdout JSON 脚本（兼容 CC） | JS/TS 插件模块（进程内） |
| 工具前/后事件 | PreToolUse / PostToolUse | preToolUse / postToolUse（同名） | tool.execute.before / after（概念同，名不同） |
| 退出码语义 | 0=proceed, 1=abort, 2=modify | 0/2（兼容 CC） | throw 阻止 / 修改对象 |
| 修改输入输出 | exit 2 + stdout JSON | updated_input / updated_mcp_tool_output | 修改 output 对象 |
| MCP 钩子 | 无原生 | beforeMCPExecution / afterMCPExecution | 无原生（走 plugin） |
| 会话事件 | SessionStart/SessionEnd/Stop | sessionStart/sessionEnd/stop（同名） | session.created/idle/updated 等 |
| LLM 评估钩子 | 无 | type: "prompt" | 无 |
| failClosed | 无 | 有 | 无 |

### 4.5 CC hooks 是否已是事实标准？

**结论：基本是，且有强证据。**

1. **Cursor 官方文档明确兼容 CC hooks**：退出码 2 语义"matches Claude Code behavior for compatibility"，且"supports loading hooks from third-party tools like Claude Code"
2. **事件名共享**：preToolUse、postToolUse、sessionStart、sessionEnd、stop
3. **通信协议一致**：都是"spawned processes that communicate over stdio using JSON"
4. **Cursor 是 CC hooks 的超集**：在 CC 基础上扩展了 MCP hooks、Tab hooks、prompt 类型钩子、failClosed
5. **opencode 概念等价但命名不同**：`tool.execute.before/after` 与 `PreToolUse/PostToolUse` 概念一致，但命名和 API 风格不同

**但 CC hooks 还不是"无需适配"的统一标准**：opencode 用 JS 插件模块而非 stdin/stdout JSON 脚本，命名也不同。

### 4.6 通用 hook 代理层技术可行性

| 方案 | 可行性 | 原因 |
|------|--------|------|
| MCP 作为通用中间层 | 部分可行 | MCP 覆盖工具层，不覆盖 hook/生命周期事件 |
| UTCP 通用工具调用协议 | 工具层可行 | 统一 tool calling，不统一 hook 行为 |
| 进程注入/代理 HTTP | 存在但解决不同问题 | 这些是多 LLM 后端路由，不是 hook 层 proxy |

**结论**：**没有现成的"通用 hook 代理层"可以让 UPP 直接用**。UPP 选择"开放标准薄封装 + 每底座薄 shim"是现实可行的唯一路径。

### 4.8 对 UPP 的影响

1. **UPP v0.2"开放标准薄封装 + 每底座薄 shim"方向被验证为正确**——没有捷径
2. **CC hooks 是基准**——UPP 标准以 CC hooks 规范为基准
3. **Cursor 近零适配**——官方兼容 CC
4. **CodeBuddy 大概率近零适配**——基于 Claude Code SDK（需真机验证）
5. **opencode 是唯一需要真正 shim 的**——命名转换 + JS 模块 vs stdin/stdout
6. **shim 实现优先级**：CC（零）→ Cursor（近零）→ CodeBuddy（需验证）→ opencode（需 shim）
