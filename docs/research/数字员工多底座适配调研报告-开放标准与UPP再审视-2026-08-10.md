> 调研日期：2026-08-10
> 目的：回答「我们创建的数字员工，如何安装并运行在多个智能体底座上」——不预设必须沿用现有 UPP 方案，对候选路径做开放重审

> 依据：本项目现有 UPP 草案 + 八底座插件体系实查 + 2026-08-10 行业开放标准网络核证（参考链接见 §7）

## §0 TL;DR（一页结论）

| 结论 | 说明 |
|------|------|
| **核心判断** | 「UPP 该不该自造一套中性协议」需要重新审视。**行业正在把 UPP 想做的事标准化了**：Agent/Skill → `Agent Skills`（agentskills.io，30+ 产品原生采纳）；项目指令 → `AGENTS.md`（Linux 基金会 AAIF，6 万+ 项目）；工具/连接器 → `MCP`（AAIF）；**事件/Hook → Claude Code Hooks 规范本身已成为事实跨底座标准**（VS Code、Qoder CN/Lingma、Docker、腾讯云全部原生实现） |
| **对现有 UPP 的冲击** | UPP v0.1 草案把「CC 风格 PascalCase 事件名」当作自研的中性协议，但**这些名字恰恰就是别人在原生实现的开放/事实标准**。继续自造 = 重复造轮子 + 与生态漂移 |
| **推荐路径（路线 C：开放标准薄封装）** | 把 UPP 从「自研中性协议」改造成「**开放标准的打包/分发层**」：员工包即 `AGENTS.md`（或 CLAUDE.md）+ `skills/`（Agent Skills 标准）+ `hooks/`（CC Hooks 规范）+ `mcp.json`。**底座原生支持的部分零适配器**；只对原生不支持 open 标准的底座写薄 shim |
| **保留的硬约束** | CQO 实时拦截（PreToolUse）仍是**唯一真正的非标准化能力**，只在有事件模型的底座可用；L2/L3 编排仍是「运行面」，开放标准不覆盖，仍需引擎侧（已 base-agnostic） |
| **下一步建议** | 先做一轮「八底座对 open 标准原生支持度」真机盘点（§5.3），决定薄 shim 的规模，再回写 UPP 草案 |

## §1 问题重述

我们要解决的核心问题：**一个数字员工（身份 + 方法论 + SOP 编排 + 治理/记忆），如何以最小的维护成本，安装并运行在 Claude Code / opencode / CodeBuddy / Qoder / TRAE / Pi / Hermes / OpenClaw 等多个异构底座上。**

拆开是两个子问题：

1. **安装面（静态）**：员工包的 Agent 定义、Skill、指令、连接器，如何落到各底座的原生格式？
2. **运行面（动态）**：底座的工具/事件协议，如何驱动我们的引擎循环（flow-driver）、CQO 治理、工程记忆？

现有方案是自研 **UPP（Universal Plugin Protocol）**：UPP v0.1 草案（未入库） 定义一份中性 manifest（Agent/Hook/Skill/Command/MCP 四类原语 + 能力协商），每底座写一个薄适配器做「安装面翻译 + 运行面协议模拟」。

本次调研的开放重审点是：**「自研中性协议 + 每底座适配器」是不是最优路径？** 尤其是当行业正在为同样的问题制定开放标准时。

## §2 现状盘点：UPP 方案已确立的成果

读 [UPP 可行性调研](多智能体底座插件系统调研-UPP可行性分析-2026-08-08.md) 与 UPP v0.1 草案（未入库），现有方案的核心价值是**摸清了八底座的插件体系并提炼出三类通用原语**（Agent / Skill / Hook 事件）：

| 底座 | Agent 定义 | Skill 定义 | 事件/Hook |
|------|-----------|-----------|----------|
| Claude Code | `agents/*.md` | `skills/<n>/SKILL.md` | `hooks.json`（PreToolUse 等） |
| opencode | TS 插件 + AGENTS.md | `~/.claude/skills/`（CC 兼容） | `tool.execute.*`（翻译层实证） |
| CodeBuddy/Qoder | 同 CC | 同 CC | 同 CC |
| TRAE | `agent.yaml`+`agent.md` | `.traerules` YAML | 规则静态注入 |
| Pi | 扩展注入 | `resources_discover`→skillPaths（**SKILL.md 格式**） | 5 事件（session_start/compact/agent_end/context） |
| Hermes | `ctx.register()` | `skill_bundles.py` | `PluginContext` 事件 |
| OpenClaw | `.agents/skills/` + plugin.json | markdown | Provider contracts |

UPP 方案的三个实证支点（草案 §0，未入库）——引擎不依赖 hook、L0-L3 天然降级阶梯、opencode 运行面翻译已实证——**仍然成立**，它们不是本次调研要推翻的东西。

**本次调研要追加的新证据是：行业正在为同一批原语制定开放标准，且采纳度已经很高。** 这意味着 UPP 的「自研中性格式」可能不是必要的，甚至是次优的。

## §3 关键发现：行业向开放标准收敛（带参考链接）

### 3.1 Agent Skill / Skill 定义 → `Agent Skills` 开放标准（agentskills.io）

- **SKILL.md** 格式（YAML frontmatter + markdown 正文 + scripts/references/assets）+ 渐进式披露三级加载，已被 **30+ 智能体产品原生采纳**：Cursor、Gemini CLI、OpenAI Codex、VS Code、Claude Code、Roo Code、OpenHands、Goose、JetBrains Junie、Lingma 等（[agentskills.io](https://agentskills.io)、[NVIDIA Agent Skills 词条](https://www.nvidia.com/en-eu/glossary/agent-skills/)、[Anthropic Engineering Blog](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)、[Alibaba Cloud Skills Portal](https://help.aliyun.com/en/skillsportal/understand-agent-skills)）。
- **与 UPP 的 `skill-def` 原语完全同构**：UPP 的 `skills/<name>/SKILL.md` 就是 Agent Skills 标准。我们 1.0 已经在写 SKILL.md。
- **关键影响**：UPP 不需要「翻译」Skill 到各底座——把 skill 按 open 标准写好，**原生支持它的底座直接零适配**。

### 3.2 项目指令/Agent 定义 → `AGENTS.md`（AAIF / Linux 基金会）

- OpenAI 把 **AGENTS.md**（项目级可移植指令格式）捐赠给 Linux 基金会下的 **Agentic AI Foundation（AAIF）**，联合 Anthropic（MCP）、Block（goose），获 Google/Microsoft/AWS/Bloomberg/Cloudflare 支持（[OpenAI 官方](https://openai.com/index/agentic-ai-foundation/)）。
- 已获 **60,000+ 开源项目 + 框架采纳**：Codex、Cursor、Devin、Factory、Gemini CLI、GitHub Copilot、Jules、VS Code 等（同上）。
- **opencode 原生支持 AGENTS.md**，且向后兼容读取 `CLAUDE.md` 与 `~/.claude/skills/`（[opencode 文档](https://open-code.ai/zh/docs/rules)）。
- **关键影响**：员工的主 agent 定义不必是自研 manifest 翻译——写成 `AGENTS.md`（或 `CLAUDE.md`）即可被 opencode 等原生读取。

### 3.3 工具/连接器 → `MCP`（Model Context Protocol，AAIF 成员）

- MCP 已是跨底座工具接入的事实标准，被本项目 §1.5 也采用（`connectors:`）。MCP 不赘述，但它是「连接器零适配」的基础。

### 3.4 事件/Hook → **Claude Code Hooks 规范本身就是事实跨底座标准**（本次最重要发现）

UPP 草案 §4.2 把 `PreToolUse / PostToolUse / UserPromptSubmit / SessionStart / PreCompact / Stop` 当作「UPP 规范事件名」。但调研发现——**这些名字已经被多家底座原生实现了**：

| 底座/平台 | Hook 事件 | 与 CC 规范 | 参考 |
|----------|----------|-----------|------|
| **VS Code (GitHub Copilot)** | PreToolUse, PostToolUse, UserPromptSubmit, SessionStart, Stop, SubagentStart/Stop, PreCompact | 同名 | [VS Code Agent hooks](https://code.visualstudio.com/docs/copilot/customization/hooks) |
| **Qoder CN / 通义 Lingma** | UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop | 同名同语义 | [阿里云 Qoder CN Hooks](https://help.aliyun.com/zh/lingma/qoder-cn/user-guide/hooks) |
| **腾讯云（文档 1831）** | SessionStart, SessionEnd, PreToolUse, PostToolUse, UserPromptSubmit, Stop, PreCompact | **「完全兼容 Claude Code Hooks 规范」** | [腾讯云 Hooks 文档](https://cloud.tencent.com/document/product/1831/134517) |
| **Docker Agent** | pre_tool_use, post_tool_use, user_prompt_submit, session_start, pre_compact, stop | 同语义（snake_case） | [Docker Docs Hooks](https://docs.docker.com/ai/docker-agent/configuration/hooks/) |
| Claude Code | 原生 | 参照系 | [CC Hooks](https://docs.anthropic.com/en/docs/claude-code/hooks) |

**含义**：Claude Code 的 Hook 事件模型正在成为**跨编码底座/IDE 的事实标准**。我们 1.0 存量（hooks.json + Python hook 脚本按 CC 协议 stdin 喂送）天然就是「标准协议」。UPP 把「CC 事件名」再命名成「UPP 规范事件名」是多余的一层——**直接以 CC Hooks 规范为中性协议即可**，且越多底座原生实现它，适配器就越薄。

## §4 候选方案（含现有 UPP + 4 条替代路径）

### 方案 A：现状延续——UPP 自研中性协议 + 每底座适配器

把「CC 风格事件名」作为自研 UPP 中性协议，八底座各写 ~100-200 行适配器做安装面翻译 + 运行面 shim（opencode 适配器已实证）。

| 维度 | 评价 |
|------|------|
| ✅ 优点 | 完全可控；opencode 翻译模式已实证；不依赖外部标准演进 |
| ❌ 缺点 | ① 自研中性协议与生态漂移（§3.4 显示 CC 事件名本就是事实标准，自研是重复造轮子）；② 八底座适配器都要维护；③ 底座升级时每适配器都要跟进（草案 B-3） |

### 方案 B：最低公共分母——只发 Agent 定义 + Skill（L0/L1）

只打包 `agents/*.md` + `skills/`（SKILL.md 标准），依赖「markdown 是通用语言」在八底座上原生运行，不做任何 L2 编排 / CQO 钩子翻译。

| 维度 | 评价 |
|------|------|
| ✅ 优点 | 零适配器；真正一次写好到处跑；Agent Skills/AGENTS.md 已提供标准 |
| ❌ 缺点 | 封顶 L1——SOP 编排（L2/L3）与 CQO 治理在这些底座上完全缺位；员工退化成「带方法论的助手」 |

### 方案 C（★ 推荐）：开放标准薄封装——UPP 退化为「打包/分发层」

**UPP 不再定义自研中性协议，而是定义「开放标准的打包与分发约定」**：

- **Agent 定义** → `AGENTS.md`（或 `CLAUDE.md`）——opencode 等原生读取
- **Skill** → `skills/`（Agent Skills 标准，30+ 底座原生）
- **Hook/事件** → CC Hooks 规范（VS Code/Qoder CN/Lingma/Docker/腾讯原生）
- **连接器** → `mcp.json`（MCP 标准）
- 员工包 = 一堆**符合开放标准的文件** + 一个轻量分发清单；底座**原生支持 open 标准的部分直接零适配**，只有不支持的底座写薄 shim

| 维度 | 评价 |
|------|------|
| ✅ 优点 | 站在行业收敛方向；L0/L1 + 连接器大面积零适配；Hook 层吃到 CC 规范的生态红利；维护成本从「八适配器」降到「几个薄 shim」 |
| ❌ 缺点 | 依赖标准成熟度（Agent Skills 互操作深度尚浅、目录约定碎片化 .claude/.cursor/.roo/）；L2/L3 编排与 CQO 实时拦截仍需引擎/代码化重实现；open 标准不覆盖的部分（如 Hermes 代码注册、OpenClaw 契约）仍需少量 shim |

### 方案 D：MCP 作为统一运行时（员工 = MCP server）

把数字员工的能力暴露为一个 MCP server，任何支持 MCP 的底座 attach。

| 维度 | 评价 |
|------|------|
| ✅ 优点 | MCP 采纳近普世；连接器天然解决 |
| ❌ 缺点 | **MCP 只覆盖「工具/连接器」**——不覆盖 Agent 身份、提示词、Hook 事件、SOP 编排。数字员工的「人设 + 方法论 + 治理」无法仅靠 MCP 交付。只能作为运行面的一个补充面，不能作为主方案 |

### 方案 E：运行面反转——工作台作统一运行时，底座只当前端

数字员工在**我们的工作台/远程运行平台**（白皮书 §3.1）里跑，各底座通过 MCP/薄插件做一个「终端」连进来；一个运行时、多个前端。

| 维度 | 评价 |
|------|------|
| ✅ 优点 | 彻底消灭 N 适配器问题；引擎已 base-agnostic（纯 CLI + 文件）；CQO/记忆集中实现 |
| ❌ 缺点 | 底座被降级为前端，牺牲「员工原生跑在用户熟悉的底座里」这一产品价值；离线/CLI 场景变重；架构成本高 |

## §5 方案对比与决策建议

### 5.1 对比矩阵

| 维度 | A 现状UPP | B 最低公共分母 | **C 开放标准薄封装** | D MCP运行时 | E 工作台反转 |
|------|-----------|---------------|---------------------|-------------|--------------|
| 适配器数量 | 8 个（都要维护） | 0 | 少量薄 shim | ~0（工具面） | 少量前端 shim |
| L0/L1 覆盖 | 8/8 | 8/8 | **8/8（零/极少适配）** | ✗（无身份/方法论） | 8/8 |
| L2/L3 编排 | 需翻译 | ✗ 无 | 引擎侧（base-agnostic） | ✗ | 集中实现 |
| CQO L-a 实时拦截 | 4 家有事件模型 | ✗ | **吃到 CC 规范生态（VS Code/Qoder/Lingma/Docker/腾讯）** | ✗ | 集中实现 |
| 维护成本 | 高 | 低 | **低** | 中 | 中高 |
| 与生态一致性 | 漂移风险 | 高 | **高** | 高（仅工具） | 低 |
| 落地风险 | 中 | 低 | 中（依赖标准成熟度） | 中 | 高（架构重） |
| 员工「原生跑在底座里」 | 是 | 是 | **是** | 部分 | 否 |

### 5.2 决策建议

1. **采纳方案 C 为主路线**：把 UPP 从「自研中性协议」重构为「开放标准的打包/分发层」。理由：行业已把 UPP 想做的事标准化（Agent Skills / AGENTS.md / MCP / CC Hooks 规范），站在收敛方向上能显著降低适配器维护成本，且不牺牲 L0/L1 覆盖。
2. **保留方案 A 的适配器技术**（安装面翻译 + 运行面 shim）作为「开放标准之外的兜底」——只对不原生支持 open 标准的底座（Hermes 代码注册、OpenClaw 契约）写薄 shim。
3. **方案 E 作为中长期演进方向**：2.0 工作台承载「我的员工」时，天然成为统一运行时，底座退化为前端；但 2.0 首期不宜以它为唯一路径（保住「员工跑在用户熟悉底座」的价值）。
4. **CQO 实时拦截的定位不变**：它仍是唯一非标准化的硬能力，只在有事件模型的底座可用；无事件模型底座维持 L-b + 熔断降级（沿用草案 §5.3）。

### 5.3 落地前必做：八底座对开放标准的原生支持度真机盘点

决定「薄 shim 的规模」。据此回写 UPP 草案的 manifest schema 与 §6 映射矩阵：

| 底座 | AGENTS.md | Agent Skills (SKILL.md) | CC Hooks | MCP | 需薄 shim？ |
|------|-----------|------------------------|----------|-----|------------|
| Claude Code | ✅ CLAUDE.md | ✅ 原生 | ✅ 原生 | ✅ | 否 |
| opencode | ✅ 原生 | ✅（CC 兼容 `~/.claude/skills/`） | 🔶 TS 插件翻译 | ✅ | 轻 |
| CodeBuddy / Qoder | ✅ | ✅ | ✅（CC 系） | ✅ | 否 |
| Qoder CN / Lingma | 待核 | ✅ | ✅ 原生（同名） | ✅ | 否（Hook 原生！） |
| TRAE | ? | `.traerules`（需确认是否兼容 SKILL.md） | ✗ | ✅ | 中 |
| Pi | ? | ✅（resources_discover→SKILL.md） | ✗（自有 5 事件） | ❓ | 中 |
| Hermes | ✗ | 🔶（skill_bundles.py，非标准） | ✗ | 🔶 | 高（代码化） |
| OpenClaw | ? | 🔶（.agents/skills/，ClawHub 分发 skills） | ✗ | ✅ | 中高 |

> 图例：✅ 原生 · 🔶 需 shim/模拟 · ? 待真机验证。此表为基于现有调研 + 2026-08-10 网络资料的推断，**落地前需逐底座真机验证**（沿用草案 §8 V 系列）。

## §6 对现有 UPP 草案的修订建议

若采纳方案 C，UPP v0.1 草案（未入库）需做以下修订：

1. **§2/§3：manifest 从「自研中性原语」改为「open 标准文件清单 + 分发元数据」**——`upp-manifest.yml` 不再自己定义 Agent/Hook 事件的中性 schema，而是声明「这份员工包含哪些 AGENTS.md / skills（Agent Skills 标准）/ hooks（CC Hooks 规范）/ mcp.json」。
2. **§4.2「UPP 规范事件名」改述**：明确「事件名 = CC Hooks 规范 = 事实跨底座标准（VS Code/Qoder CN/Lingma/Docker/腾讯原生实现）」，删掉「自研中性协议」的表述，避免与生态漂移。
3. **§5 能力协商**保留（可达 Level + 降级目录仍有效），但把「适配器职责」从「翻译自研协议」改为「判定底座对 open 标准的原生支持度 → 只补缺失的 shim」。
4. **§7 硬边界**基本保留（CQO L-a 只在有事件模型底座可用、Hermes L2 代码化重实现等），新增一条边界：**「依赖 Agent Skills/AGENTS.md/CC Hooks 标准的成熟度」**，落地前做 5.3 真机盘点。
