# 管理平台 V0.1 部署与外部访问设计

**状态**：V0.1 方案一已实现；方案三为后续生产演进目标
**日期**：2026-08-16

## 1. 目标与边界

管理平台、Keycloak 和工作台参与同一条 OIDC 前端跳转链。浏览器看到的管理平台地址、OIDC issuer、Redirect URI、Web Origin 和工作台地址必须来自同一个部署配置源，否则物理机浏览器会被错误地重定向到虚拟机内部的 `localhost`。

V0.1 只解决单机 Docker Compose 验收环境的显式地址配置，不引入 DNS、证书、反向代理、高可用或自动公网发现。

## 2. 当前方案：显式 `PUBLIC_HOST`

### 2.1 配置契约

操作者使用以下任一种方式指定不含 scheme 和端口的 IPv4 地址或 DNS 主机名：

```bash
PUBLIC_HOST=192.168.153.128 ./tools/up.sh
```

或在不提交 Git 的 `tools/.env` 中配置：

```dotenv
PUBLIC_HOST=192.168.153.128
```

优先级为：命令行 `PUBLIC_HOST` > `RUNTIME_ENV_FILE`/`tools/.env` > `127.0.0.1`。本地配置只解析 `PUBLIC_HOST`，不会作为 shell 脚本执行。

### 2.2 URL 派生

| 服务 | 派生地址 |
|---|---|
| 管理平台 | `http://${PUBLIC_HOST}:18000` |
| Keycloak | `http://${PUBLIC_HOST}:18080` |
| 工作台 Demo | `http://${PUBLIC_HOST}:19820` |
| OIDC issuer | `http://${PUBLIC_HOST}:18080/realms/digital-employees` |

Compose 插值把相同值注入平台、工作台和 Keycloak。Realm JSON 使用 `PLATFORM_PUBLIC_URL` 与 `WORKBENCH_PUBLIC_URL` 占位符完成首次导入。对于已存在的 Realm，`tools/up.sh` 在 Keycloak 就绪后调用 Admin API，幂等更新 `platform-web` 和 `workbench-desktop` 的 Redirect URI 与 Web Origin，因此改变地址不要求删除数据库卷。

### 2.3 安全约束

- `PUBLIC_HOST` 不接受 scheme、端口、路径、空白或 shell 元字符。
- V0.1 仅允许回环或 RFC1918 私网 HTTP；公网地址必须使用 HTTPS。
- Keycloak hostname 保持显式设置，不根据未经信任的 Host 请求头生成 issuer。
- PostgreSQL 不发布宿主机端口。
- `tools/.env` 和运行数据不进入 Git。

## 3. 后续方案三：稳定域名、DNS、HTTPS 反向代理

### 3.1 目标拓扑

建议使用三个稳定名称：

```text
https://platform.example.com   -> 管理平台
https://iam.example.com        -> Keycloak
https://workbench.example.com  -> 工作台 Web 入口（仅部署演示或远程工作台场景）
```

DNS 负责将名称映射到当前入口 IP，IP 变化只更新 DNS，不改变 OIDC issuer。边缘 Nginx/Tengine/Ingress 只暴露 443，内部继续通过 Compose 网络使用 HTTP：

```text
Browser --HTTPS--> Reverse Proxy --HTTP--> platform-web/keycloak/workbench
Platform API --container network--> Keycloak/PostgreSQL
```

### 3.2 Keycloak 配置

- `KC_HOSTNAME=https://iam.example.com`
- `KC_HTTP_ENABLED=true`，仅供代理到容器的内部连接。
- `KC_PROXY_HEADERS=xforwarded`，代理必须覆盖而不是透传客户端提供的 `X-Forwarded-*`。
- 保持 hostname strict；不启用完全动态 Host Header 模式。
- `platform-web` Redirect URI：`https://platform.example.com/auth/callback`
- `workbench-desktop` Redirect URI：按桌面 loopback 或受控工作台入口精确登记，禁止宽泛 `*`。

Keycloak hostname 会影响 Discovery、issuer、重置密码链接及 Token 校验，因此必须使用稳定域名。参考：[Keycloak hostname v2](https://www.keycloak.org/server/hostname)。

### 3.3 平台与代理配置

- 平台公开 base URL 改为 `https://platform.example.com`。
- OIDC issuer 改为 `https://iam.example.com/realms/digital-employees`。
- BFF 与工作台人员会话 Cookie 启用 `Secure`，保持 `HttpOnly`、`SameSite=Lax`。
- 代理设置 HSTS、TLS 1.2/1.3、安全响应头和请求大小限制。
- 管理平台与 Keycloak 管理控制台可进一步限制来源网段或接入 VPN。
- 证书由企业 CA、ACME 或现有证书平台签发，私钥通过部署 Secret 注入，不提交仓库。

### 3.4 迁移步骤

1. 准备三个 DNS 记录和有效 TLS 证书。
2. 部署反向代理并先验证各上游健康端点。
3. 配置 Keycloak 固定 HTTPS hostname 与可信代理头。
4. 精确更新两个 OIDC Client 的 Redirect URI/Web Origin。
5. 更新平台和工作台公开 URL，重建相关容器。
6. 使用新浏览器会话验证 Discovery issuer、管理平台登录、工作台 PKCE、登出和回调。
7. 关闭 18000、18080、19820 的外部直接访问，只保留代理的 443。
8. 执行完整单元测试和真实 E2E，再切换 DNS。

### 3.5 验收标准

- 浏览器地址栏及所有 302 `Location` 只出现预定 HTTPS 域名。
- Discovery 中的 issuer 与 Token `iss` 均为 `https://iam.example.com/realms/digital-employees`。
- HTTP 入口统一 301/308 到 HTTPS，Cookie 均带 `Secure`。
- 伪造 Host/X-Forwarded-Host 不改变 issuer 或回调目标。
- 三个容器业务端口不可从外部网络直接访问。
- 真实管理平台和工作台 OIDC E2E 全部通过。

## 4. 非目标

- 本次不实现方案三的 DNS、证书、代理配置或生产 Secret 管理。
- 不采用 Keycloak `hostname-strict=false` 的完全动态 URL 模式。
- 不在 V0.1 引入 Kubernetes、Ingress Controller 或服务网格。
