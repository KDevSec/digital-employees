## 1 三层模型（总纲）

```
EmployeeSpec（底座无关，员工包 = 唯一事实源；E-12 管线产物 / 模板库）
   │  adapt(spec, host) —— 幂等：建 home + config 域（身份编译/skills/MCP/auth）+ manifest
   ▼
Deployment（spec × host × home = 一行 registry 台账）
   │  launch(deployment, workdir, prompt, permission, model, effort) —— 纯构造 LaunchSpec
   ▼
Session（一次会话 = 一位员工的一个工作实例；spawn 归 L3 spawn runner）
```

**核心语义**（S4 §3.1 采纳 + D-043）：

1. **安装 = 员工上岗**：`adapt()` 建立员工在该底座的全部运行时资产（config 域）；安装后底座自行加载，工作台不驻留底座进程。
2. **身份与工作区分离**：身份/技能锚在员工 home 的 config 域；任务产物在共享工作区；会话 = 「带着工具箱去项目现场」（cwd=workdir 启动 CLI，config 域注入身份）。
3. **落地物 = 编译产物，永不手改**：config 域内一切文件由 adapter 生成；升级=重跑 adapt；漂移=对 manifest hash；卸载=按 manifest 清单删。
4. **多员工并发无冲突**：每员工独立 config 域，身份互斥铁律（S4 3.2 跨底座 4/4 实证）在域层面天然满足——同一 workdir 任意时刻可 spawn 任意已安装员工，无需切换事务。

**模块结构**（workbench-service 绿地新增）：

```
workbench/workbench-service/src/
├── installs/                  安装域（三层模型实现）
│   ├── spec/                  EmployeeSpec schema（zod）+ parser 接口（§2）
│   ├── registry/              Deployment 台账读写（§3.3）
│   ├── executor/              事务化安装执行器（§6）
│   ├── report/                安装报告 + manifest（§7）
│   ├── uninstall/             反向清理（§8）
│   └── launch/                LaunchSpec 构造 + spawn 辅助（§4.3）
├── bases/                     底座域：在场探测 + 版本断言（§9）
└── adapters/                  每底座档案 + transforms（§5）
    ├── contract.ts            adapter 契约类型（§4）
    ├── claude-code/           profile.yml + transforms/
    ├── codebuddy/             profile.yml + transforms/
    └── qoder/                 profile.yml + transforms/
routes：server/routes/installs.ts + bases.ts（I0-5 分域注册，鉴权「会话+激活」）
```

## 2 EmployeeSpec 与 parser 接口

**包结构真源已定稿**（i0-prereview 分支，评审中；2026-08-27 确认可参考）：[shared-protocol 详细设计 v0.2](../详细设计/shared-protocol详细设计-v0.2.md)（八类 manifest）+ [员工模板设计](../../plans/2026-08-26-员工模板-design.md)（七模板已物化为活样例 `workbench/templates/`）。**员工包与模板同构**：

```
<package>/                 # 员工包 = 安装单元（E-12 管线产物）
  manifest.yml             # 八类 v0.2（元数据 10 项 / 八件套 1+7 / 管理面 3 段）
  AGENTS.md                # 指令真相源（六段式渲染产物，含 S4 授权措辞）
  skills/<slug>/SKILL.md   # Agent Skills 标准包（与 manifest.skills 清单一致）
  hooks/hooks.json         # 红线编译产物（E-12 构建期从 redlines 声明编译，compiled=true 的规则）
  commands/ knowledge/ orchestration/    # 约定路径（V0.1 预留 / 引擎账本消费，不落位）
```

**消费方式**：复用 `@devzero/shared-protocol` 包（`workbench/shared-protocol/`，L1 线交付物）导出面——`manifestSchema / skillEntrySchema / deriveRequires / deriveCapabilities`——**本线不重复定义 schema**（PR-008 capability 词表漂移的根治）。该包在 main 未合入前：本线以 parser 接口桩 + fixture 先行 TDD（fixture 按 manifest v0.2 手工构造，对照 `workbench/templates/dev-engineer/` 活样例）；合入后切换 import 真源（依赖边界：`installs/spec/` 独立模块，切换点单一，不合契约文件）。

```ts
// installs/spec/types.ts —— L2 消费面（从员工包解析；字段与 manifest v0.2 对齐）
interface EmployeeSpec {
  id: string                    // manifest.id（纯 id；employeeId(id,org) 拼装归平台交互 V0.2+）
  display: string
  version: string               // manifest.version
  instructions: string          // AGENTS.md 全文（身份编译源——identity copy 基线）
  skills: SkillEntry[]          // manifest.skills（name/version/source_type，D-047 两支）
  requires: { level: 'L0'|'L1'|'L2', capabilities: string[] }
                                // level = 落盘唯一协商输入；capabilities = deriveRequires() 派生（不落盘）
  connectors: ConnectorRef[]    // stdio/http 双型（§4.5 MCP 落域源；D-042 url 型同引擎连接器形态）
  tier: string                  // constraints.tier 五档单值（launch effort/model 映射输入，D-046 第四层）
  hooksFile?: string            // 包内 hooks/hooks.json 路径（存在时 = adapt merge 源）
}

interface EmployeeSpecParser { parse(packageRoot: string): Promise<EmployeeSpec> }   // 接口；实现待 shared-protocol 合入 main
```

- **协商输入**：`requires.level`（落盘）+ `deriveRequires()` 推导 capabilities（shared-protocol §2.3 派生表：skills 非空 +skill-def；runbook/个人表 +bash-exec+slash-command；个人表 +subagent-dispatch）——negotiator 不自建词表。
- **安装期包校验**（消费 shared-protocol 校验语义）：skills/ 目录与 manifest 清单一致；compiled redlines → hooks/hooks.json 必须存在（跨字段校验 4——一等安装期错误）。
- **persona 措辞**：S4 §3.4 授权框架措辞已由模板设计 §4 六段式「我是谁」段落实（AGENTS.md 渲染含「本角色为用户配置的数字员工岗位」），本线无需二次加工。

## 3 Deployment：home 布局与 registry

### 3.1 员工 home（家；S4 §3.3）

```
~/digital-staff/<host>/<employee-id>/          # <host> ∈ {claude-code, codebuddy, qoder}
  config/            # 隔离配置域（adapt 产物全部在此；§5 各底座布局）
  memory/            # 跨会话长期记忆（AGENTS.md 声明「你的记忆在 ./memory/」）
  sessions/          # 会话台账 {workdir, task, host_session_id, started_at}
  reports/           # 安装报告 install-<ts>.json（§7）
  .devzero-manifest.json   # 版本 + 文件清单 + hash（漂移/卸载数据基础）
  .transaction/      # 事务日志（安装期；§6.4）
```

- 同一员工装多底座 = 多个 home（`<host>` 维度分目录），registry 每底座一行。
- **持久用户路径**，禁用 /tmp（P-13：codex 拒绝临时目录建 helper；S3 互证「/tmp 丢文件」）。
- 命名前缀统一 **devzero**（D-040）：`.devzero-manifest.json`、merge 撤销标记 `_devzero`、溯源注释 `generated by devzero`。S4 讨论稿的 `.workbench-manifest.json` 为旧品牌名，本设计按 D-040 修订。

### 3.2 registry 台账（D-043：L4 花名册与编排 Deployment 台账统一口径一个真源）

```
~/digital-staff/registry.json
{
  "registry_version": 1,
  "deployments": [{
    "employee_id": "frontend-dev",
    "spec_version": "0.1.0",
    "base": "qoder",                          // host id
    "home": "C:/Users/liyong/digital-staff/qoder/frontend-dev",
    "status": "installed",                    // installing|installed|upgrading|broken|uninstalling
    "identity_anchor": "config-domain",       // §4.2 档案快照（实测修正后回写）
    "base_version": "1.1.26",                 // 安装时实测版本（P-8：CLI 静默自升级，断言留空间）
    "installed_at": "…", "last_launch_at": "…",
    "manifest_path": "<home>/.devzero-manifest.json"
  }]
}
```

- 写入时机：`adapt()` 事务内（status 先 installing → 完成转 installed）；`launch()` 后更新 last_launch_at。
- 崩溃恢复依据：非终态行 = 未完成事务（§6.4）。
- **职责边界**：员工身份真相源 = 员工包（`employees/<id>/`，E 系列管线）；安装状态真相源 = registry。两层真源不同域，不冲突（继承 v0.1「roster.json 不设」裁决）。

## 4 adapter 契约（三动词）

```ts
// adapters/contract.ts
interface BaseAdapter {
  readonly profile: BaseProfile                       // §5 档案（含 identity_anchor）
  adapt(spec: EmployeeSpec, opts: { home: string }): Promise<AdaptResult>      // 幂等建域（§6 执行器驱动）
  launch(input: LaunchInput): LaunchSpec               // 纯构造（§4.3）
  listModels(base: { version: string }): Promise<ModelInfo[]>   // D-046 数据源
}
interface LaunchInput {
  deployment: DeploymentRef                            // home + base + 身份内容
  workdir: string                                      // 任务工作区（cwd）
  prompt: string                                       // 任务指令（D-046：节点 prompt 模板插值结果）
  permission?: PermissionMode                          // 会话权限模式预配（D-042 spike §3.4）
  model?: string                                       // 四层解析链落定的具体模型
  effort?: string                                      // 抽象档位 → 底座旗标（映射收敛 adapter，D-046）
}
```

### 4.1 adapt(spec, host)——幂等建域

每次调用对同一 (spec, host) **幂等**：校验 manifest hash → 未变更则跳过（unchanged）；版本变更则升级（重跑编译）；域内产物缺失/漂移则修复（自愈）。产出：config 域全套（身份文件 + skills + MCP 配置 + 凭证置备）+ manifest + registry 行。

### 4.2 身份锚：三底座统一 config-domain（D-049 裁决）

**裁决与证据链**（避免重复分析，结论以此为准）：

- D-043 原文「CC=config-domain / Qoder=project-file / launcher 兜底」——本次修订：**三底座统一 config-domain 为主路径**。
- 依据①：qodercli = CC 架构复刻（D-034 旗标面同构实证：--print/--cwd/--setting-sources/--plugin-dir/--config-dir）；CC 的 config 域身份+skills 全链已实证（S4 V1 3/3、V6）。
- 依据②：**S1 方案 B「config 根身份脆弱」的真实语义 = 竞争场景双输**（config 域身份 × 项目层身份并存时 2/2 双弃用，V-X1c）——**纯净场景（config 域唯一身份）S1 从未测过、从未被否定**；且该竞争边界三底座均未实测（S4 V1 测试目录无用户身份文件），非 Qoder 特有风险。
- 依据③：用户裁决 2026-08-27「按理说 Qoder 和 CC 一样」+ 统一后架构收益：当值/停靠区/duty.json 整体退役、多员工可并发 spawn 同一 workdir（project-file 覆盖式做不到）。
- **待验与回退**：Qoder config 域身份注入（≥3 采样，P-10 抽检戒备）+ skills 同域加载 + 「config 域身份 × workdir 用户手写 AGENTS.md」竞争边界（三底座同测）→ M2 联调首日按 S4 §3.5 判据规范实测；**失败回退 = 档案值改 `identity_anchor: project-file`**，launch() 两档行为都已实现（§4.3），回退是档案切换非代码改造。

锚层档案字段（`adapters/<base>/profile.yml`）：

```yaml
identity_anchor: config-domain        # config-domain | project-file | launcher-flag（兜底档）
```

### 4.3 launch()——LaunchSpec 构造（Windows 四坑对策在此层）

**launch 不 spawn 进程**：返回 `{command, args[], env{}, cwd}` 纯构造值（表驱动可测）；进程生命周期管理（超时 kill/孤儿回收/续跑）归 L3 spawn runner（D-048 分工）。L2 提供两个 spawn 辅助：

1. **prompt 文件中转**：prompt 写入 `<workdir>/.devzero/prompt-<ts>.md`，命令行以 `@file` 或 stdin 引用——规避 npm .CMD 垫片多行 prompt 首个 `\n` 截断坑（协同编排 §12.1 坑1，已选文件中转方案）。
2. **垫片解析**：Windows 下探测 `.CMD` 垫片并解析出真实 node/js 入口直连（坑1 根治）；spawn 后产物自检（坑4 python Store 占位符类假成功的通用对策）。

各底座 LaunchSpec 映射（`transforms/launch.ts`；旗标细节待 M2 实测核，标 ⏳）：

| 抽象参数 | Claude Code | CodeBuddy | Qoder（qodercli） |
|---|---|---|---|
| 命令 | `claude` | `codebuddy` | `qodercli` |
| config 域 | env `CLAUDE_CONFIG_DIR=<home>/config` | env `CODEBUDDY_CONFIG_DIR=<home>/config` ⏳ | `--config-dir <home>/config` ⏳（或 env，实测核） |
| cwd | workdir | workdir | workdir |
| prompt | `-p @<promptFile>` ⏳（文件引用形态） | 同 CC ⏳ | `--print` + stdin/prompt 文件 ⏳ |
| permission | `--permission-mode <mode>` ⏳ | 同 CC ⏳ | 同构假设 ⏳ |
| model | `--model <model>` | 同 CC ⏳ | 同构假设 ⏳ |
| effort | `--effort`? ⏳（CC 支持性待核） | ⏳ | ⏳ |

> 回退档（project-file 锚）launch 行为：workdir 落薄壳身份文件（AGENTS.md `@import` 根内路径 + 溯源注释，S1 V-X3：引用目标必须在 scope 根内），覆盖式落位（后 launch 覆盖先 launch，互斥单值天然满足）；skills 同步落 workdir 命名空间目录（§5.4 回退落位）。

### 4.4 listModels(base)

数据源 = 底座配置（各底座模型列表的获取方式 M2 实测核：CC `claude model list`?⏳ / qodercli ⏳ / CB ⏳），返回 `ModelInfo[]{id, label, tier?}`；tier-map（沿用 1.0 五档语义：评审安全档/设计档/探索档/编码档/执行档，D-046/Q7）将抽象档位映射到具体模型 id。发起表单四层解析链：节点 model_tier > 任务级选择 > 员工 manifest 档位 > 底座默认（D-046，解析在编排侧，L2 只提供 listModels 与 tier-map 查询）。

### 4.5 MCP 落位分工（D-042/D-043 消解 PR-025）

| MCP 内容 | 落位 | 职责方 |
|---|---|---|
| 引擎连接器（url 型 `http://127.0.0.1:19980/mcp`） | 任务工作区 `.mcp.json` | **编排器**（L3，非本线） |
| 员工自带连接器（spec.connectors） | **员工 config 域内**（各底座域内 MCP 约定位置 ⏳ M2 实测核） | 本线 adapt() |
| 用户自己的连接器 | 用户底座全局配置 | 用户（不触碰） |

员工连接器落 config 域 → 随域隔离，PR-025 的「多员工 MCP 共存上下文污染」在主路径下消解（每员工会话只加载自己域的连接器）。AGENTS.md SOP 配套指令（回写 L1）：「引擎工具不可用 = 工作台未运行 → 停止推进并上报，不得绕路」（D-042 spike ④：模型会自作主张降级）。

## 6 安装执行器（B-03；S1 §8 事务化八条全量落实）

### 6.1 执行流

```
① 协商（negotiate(spec, profile, probe)：探测修正覆盖静态声明；missing_required ≠ ∅ → 一等安装期错误，B-8）
→ ② 生成落位计划（§5 档案 + manifest hash 预计算；幂等：同版本 hash 一致 → unchanged 跳过）
→ ③ 冲突预检（config 域残留漂移 / 回退档 workdir 用户文件）
→ ④ 开事务：registry 行 status=installing + 事务日志 .transaction/（计划 + 每步 phase）
→ ⑤ 逐项执行：copy/convert 先写临时文件再原子 rename（Windows：目标存在即抛 → 先删后 rename + 代际重名 .r2.*，不与句柄占用较劲，§12.1 坑2）
        merge 三件套：写前备份原文件 → 程序化深合并（禁文本拼接）→ 写后回读校验 + 捕获底座 parse error 信号（P-1/P-5：底座容忍坏 JSON 静默半生效）
→ ⑥ manifest 落盘 + 报告写入 home/reports/ + registry 转 installed
→ ✗ 任一失败 → 按事务日志逆序回滚（rename 回退/恢复备份/删已拷目录）→ registry 行标 broken + 报告 result=rolled-back（**安装期错误一等公民：完整错误对象 + 用户可读文案 + 恢复指引**）
```

### 6.2 事务化八条映射（S1 §8 → 本设计机制）

| S1 条款 | v0.2 机制 |
|---|---|
| 1. 三步落位单事务 | executor 单事务覆盖 config 域全套落位 |
| 2. merge 三件套 | §6.1 ⑤（备份/深合并/回读校验） |
| 3. 撤销标记双锚 | merge 类 `_devzero: <employee_id>` JSON 键 + copy 类溯源注释 + manifest checksum（缺一不可） |
| 4. 创建 vs 合入区分 | 目标不存在→本安装创建（卸载可整删）；已存在→按标记摘条目保文件（显式判定，不做隐式归零整删） |
| 5. 当值切换崩溃恢复 | **改写**：config-domain 模型无身份切换窗口；对应窗口 = registry installing→installed 两阶段（§6.4） |
| 6. 卸载顺序 | §8（摘 merge 条目→删 copy→清目录→归属豁免 diff→报告） |
| 7. hook 命令生成器 | Windows 转义模板（`cmd /c` + 重定向引号处理，P-4）+ 每模板预触发验证进 CI |
| 8. 报告记录 base_version | §7 报告字段 + registry 行同步（P-8） |

### 6.3 幂等与升级

- 同版本重装：manifest hash 逐项比对，一致跳过（unchanged）。
- 跨版本升级：重跑 adapt 编译 → 域内产物替换；memory/ 与 sessions/ **永不触碰**（用户资产豁免）。
- 域内漂移（产物被手改）：hash 不符 → plan 阶段列冲突，默认「重编译覆盖」（产物=编译物原则），报告记录 diff 摘要。

### 6.4 崩溃恢复（PR-026 裁决：双消费方）

1. **服务启动扫描**：registry 非终态行（installing/upgrading/uninstalling）→ 校验事务日志与 manifest 完整性：完整 → 补转终态（收尾）；不完整 → 标 broken + UI 提示重跑（adapt 幂等自愈）。
2. **下次同目标 plan/execute 前**：检测 broken 行 → 先自愈（重跑 adapt 修复域）再继续新计划。
3. 验收含 **kill -9 注入用例**（安装中途强杀进程 → 重启服务 → 扫描恢复 → 重装成功且域状态一致）。

## 8 卸载（B-05）

```
输入：registry 行 + home/.devzero-manifest.json（placements 真源）+ 残留扫描
① 保护检查：sessions/ 有活动会话（进程存活）→ 阻止并提示（0.2 会话进程接管后扩展）
② registry 行 status=uninstalling（崩溃恢复锚点）
③ merge 类（仅回退档 workdir 产物）：按 _devzero 标记精确摘除；无法解析 → 报告列 manual[] + diff
④ copy/convert 类：checksum 一致 → 删；不一致（用户改过）→ 默认保留 + kept[] 记录，force 可强删
⑤ 删 home（memory/ 与 sessions/ 默认保留并迁移至 ~/digital-staff/.unclaimed/<id>-<ts>/，报告列明；用户资产不销毁）
⑥ 残留扫描：按 devzero 命名空间约定 glob（ds-* 目录 / _devzero 标记 / 溯源注释文件 / .devzero-*）→ 孤儿文件确认清理（归属豁免：第三方运行时投递如 .ieidev/ 不计「不干净」，P-5）
⑦ registry 行删除 + 卸载报告 ~/.devzero/installs/uninstalled/<id>@<base>.json（audit 保留）
```

**验收**：卸载后 workdir 与用户全局配置 diff 干净（除用户数据与豁免项）；重复卸载幂等（无 registry 行则 no-op）。
