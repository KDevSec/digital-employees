## 1 定位与模块架构

workbench-service = **单体二进制兼任 daemon 与 CLI**（调研 §9.1：CLI 入口就是 Service 二进制本体）。进程模型：OS 守护层（计划任务/systemd/launchd）守护唯一常驻进程；托盘壳（M3 起）只是旁观遥控器，不在本模块内。

### 1.1 模块划分与依赖方向

```
workbench-service/
├── cli/            命令行入口与参数解析（唯一调用 main 的地方）
├── app/            业务模块（每模块一个目录，互不 import）
│   ├── platform-access/   平台访问：发现/接入/心跳（登录 v0.2 的迁移落位，A 系列）
│   ├── employees/         员工管理 + 创建向导后端（E 系列，详细设计 3 填充）
│   ├── packages/          员工包构建（E-12，详细设计 3 填充）
│   ├── agenthub/          AgentHub 客户端（E-13，详细设计 3 填充）
│   ├── installs/          安装执行器 + 安装报告（B 系列，详细设计 4 填充）
│   ├── bases/             底座在场探测（B-06，详细设计 4 填充）
│   └── update/            检查更新（U-01~U-04）
├── server/         HTTP 宿主：Hono route-registry adapter + 静态前端 + SSE
├── runtime/        进程生命周期：启动序列/单实例/孤儿回收/优雅退出（Bun API 允许区）
├── guard/          OS 守护注册：Task XML / systemd unit / launchd 渲染与反解析
├── config/         配置两层 + zod schema + sample 生成
├── storage/        SQLite + WAL + sqlite-vec 外挂 + 存储版本守卫（Bun API 允许区）
├── logging/        日志四类 + 轮转 + lifecycle 横幅
└── main.ts         组装：依赖注入，模块经 registry 注册路由
```

**依赖规则**（lint 强制，源码拆解 §4.1 借鉴）：

1. `app/*` 业务模块**只 import** `server/route-registry` 提供的注册函数、`config`、`storage`、`logging` 的类型与工具——**不直接 import Hono/Express 任何符号**
2. Hono **只出现在 `server/route-registry.ts` 一个文件**；换框架只改这一个文件
3. Bun 专有 API（`bun:sqlite` 等）只允许出现在 `storage/` 与 `runtime/` 两个目录（D-018 的 lint 红线）；其余代码只写标准 TS + Web 标准 API（R-10 回退保障）
4. `app/*` 模块之间**禁止横向 import**（员工不直接调安装器，经 server 层组合或事件）
5. `cli/` 是唯一入口组装层；`main.ts` 只做依赖注入与启动序

### 1.2 route-registry adapter 模式

```ts
// server/route-registry.ts —— 全仓唯一出现 Hono 的文件
export interface RouteModule {
  register(routes: RouteRegistry): void   // 模块实现此接口
}
export interface RouteRegistry {
  get(path: string, handler: Handler): void
  post(path: string, handler: Handler): void
  // ...业务模块能看到的全部 HTTP 面
}
```

每个 `app/*` 模块导出 `RouteModule` 实现；`main.ts` 收集全部模块按序注册。Handler 签名是**框架无关的**（`{ params, query, body, session } => { status, json }`），adapter 负责与 Hono 互转。**收益**：业务代码零框架耦合（Node SEA 回退时 adapter 换 fastify 适配即可，T3 验证口径）。

## 3 进程模型与启动序列（S-13）

### 3.1 启动状态机

```
            ┌─────────────────────────────────────────────────┐
            v                                                 |
  ┌──────────────────┐   失败(配置/schema)   ┌─────────────────┴──┐
  │ 1 解析 CLI/配置   │ ───────────────────> │ 退出(码 78)         │
  └────────┬─────────┘                      └────────────────────┘
           v
  ┌──────────────────┐  cleanStop=false
  │ 2 崩溃检测         │ ──────────> lifecycle.log 记「上次异常退出」
  └────────┬─────────┘
           v
  ┌──────────────────┐  高于本二进制支持版本
  │ 3 存储版本门       │ ──────────> 拒绝启动(78) + 「请升级不要降级」
  └────────┬─────────┘
           v
  ┌──────────────────┐  自家uid+healthz匹配        ┌──────────────────────┐
  │ 4 端口探测(三分支) │ ─────────────────────────> │ 幂等：开浏览器后退出(0) │
  └────────┬─────────┘  第三方占用                 └──────────────────────┘
           │            ─────────────────────────> 报错(78)+占用进程名
           v 空闲
  ┌──────────────────┐
  │ 5 孤儿回收        │  workers.json 三条件整组杀
  └────────┬─────────┘
           v
  ┌──────────────────┐
  │ 6 磁盘 GC         │  updates/ >7天 + 超额日志
  └────────┬─────────┘
           v
  ┌──────────────────┐
  │ 7 起服务/写契约    │  service.json + reliability.json{cleanStop:false}
  └────────┬─────────┘
           v
  ┌──────────────────┐
  │ 8 healthz 就绪     │  （完成判据 = /healthz 200，非 spawn 成功）
  │    启动横幅        │  lifecycle.log：版本/commit/运行时/OS/端口/存储后端
  └────────┬─────────┘
           v
  ┌──────────────────┐
  │ 9 后台任务起       │  心跳定时器(A-05)/更新检查(U-01:30s 后)
  │    首启开浏览器     │  仅一次（哨兵 run/sentinels/first-run-browser-opened）
  └──────────────────┘
```

每步落一条 lifecycle.log（含步号），排障时能直接看到卡在哪一步。

### 3.2 启动就绪语义

「启动成功」= `/healthz` 返回 200（实测参照冷启动 11s，期间进程在但不可服务）。`workbench start` 的 CLI 返回以此为界（S-02 验收），托盘左键直达同理（TR-04）。

## 4 CLI 命令面（S-02）

```
workbench start                  注册 OS 守护（若无）+ 幂等启动 + 首启自动开浏览器
workbench start --foreground     前台跑，不注册守护（调试/CI/容器）
workbench start --no-keepalive   起服务但不注册守护（临时用；不注销已有注册）
workbench stop                   优雅停服（保留守护注册）
workbench status [--verbose]     JSON：pid/port/version/uptime/health/pendingUpdate
                                 --verbose 追加 service/shell/installer 三版本线（W-12）
workbench activity               JSON：{ conversationTasks, triggerTasks }（优雅停服判据，TR-07 消费）
workbench portal [--print-url]   打开浏览器到工作台（或仅打印 URL）
workbench update --check         手动触发更新检查（U-01）
workbench uninstall [--purge]    注销守护 + 清理；--purge 连数据目录一起清（W-11）
workbench __daemon               内部子命令：被守护配置拉起的真正入口（不进 --help）
workbench __health-wait [ms]     内部子命令：等 /healthz 就绪（托盘/安装脚本消费）
```

- **`__` 前缀隐藏**（源码拆解 §8.7）：公开命令面保兼容，内部面随改
- `start` 由 OS 守护路径调用时经 `__daemon` 进入（守护配置 `ExecStart`/`<Command>` 指向 `workbench __daemon`，稳定路径不嵌版本号，D-028）
- 退出码：`0` 正常 · `78` 配置/环境错误（OS 不徒劳重启）· `143` SIGTERM · `1` 未分类错误

## 5 配置体系（S-07）

两层分离（调研 §5.4）：`config.json` = 基础设施（运维），`settings.json` = 用户偏好（产品）。实际文件**只写覆盖项**，其余走代码默认；sample 全量带注释并**从 zod schema 生成**（不手维护）。

### 5.1 config schema（zod，节选）

```ts
const configSchema = z.object({
  network: z.object({
    port: z.number().int().default(19980),        // D-022
    host: z.literal('127.0.0.1').default('127.0.0.1'),  // 仅回环，S-12
  }).default({}),
  platform: z.object({
    publicBaseUrl: z.string().url().default('http://localhost:18000'),
    internalBaseUrl: z.string().url().optional(),   // 同机 compose 内网地址
  }).default({}),
  update: z.object({
    channel: z.enum(['stable', 'beta']).default('stable'),
    preDownload: z.boolean().default(false),       // U-04：默认不预下载
  }).default({}),
  logging: z.object({
    rotateMaxBytes: z.number().default(10 * 1024 * 1024),
    retainedFiles: z.number().int().default(5),
  }).default({}),
})
```

### 5.2 settings schema（节选）

```ts
const settingsSchema = z.object({
  locale: z.enum(['zh-CN', 'en']).default('zh-CN'),
  system: z.object({
    launchAtLogin: z.boolean().default(true),      // D-021；哨兵文件区分「用户选 false」
    tray: z.object({ enabled: z.boolean().default(true) }).default({}),
  }).default({}),
  agenthub: z.object({
    baseUrl: z.string().url().optional(),          // E-13 配置项（R-20）
    token: z.string().optional(),                  // 持久层加密存储，sample 不含
  }).default({}),
})
```

### 5.3 sample 生成

`zod-to-json-schema` + `_comment` 字段注入 -> `config.sample.json` / `settings.sample.json`（T9 验收：sample 与 schema 不一致时 CI 失败）。启动时若发现用户文件带 `_comment` 字段则忽略该字段（宽松读）。

## 6 契约文件（run/）

外部（托盘壳/脚本/任何工具）对 Service 的全部认知 = 这三个文件 + `/healthz`（C-4）。schema 均带 `schemaVersion`。

### 6.1 run/service.json（S-04，发现契约）

```ts
interface ServiceHandle {
  schemaVersion: 1
  app: 'ieidev-workbench'
  pid: number
  port: number
  host: '127.0.0.1'
  version: string            // Service 版本（用户可见版本，W-12）
  buildCommitId: string
  uid: string                // 装机稳定 ID（installation_id 同源，A 系列消费）
  instanceId: string         // 每次启动新生（UUID）
  startedAt: string          // ISO8601
}
```

单值兼容层：`run/service.pid`、`run/service.port`（供非 JSON 读者）。`run/service.lock`：启动即持有（flock/LockFileEx），防双写。

### 6.2 run/reliability.json（S-04，崩溃检测）

```ts
interface ReliabilityState { schemaVersion: 1; runId: string; startedAt: string; cleanStop: boolean }
```

启动时读到 `cleanStop === false` -> lifecycle.log 记一条「上次异常退出」；正常退出前置 `true`。

### 6.3 run/workers.json（S-05，子进程账本）

```ts
interface WorkersLedger {
  schemaVersion: 1
  workers: Array<{
    workerId: string
    sessionId: string
    pid: number
    pgid: number             // Windows: 进程组近似用 Job Object id；Unix: getpgid
    lastSeenAt: string       // 心跳式刷新；启动回收的判据
    status: 'running' | 'exited' | 'reaped'
    kind: 'base-cli' | 'build' | 'other'   // 底座 CLI 子进程（未来会话路由）/构建任务
  }>
}
```

**V0.1 的实际写入者**：员工包构建任务（packages/）与未来的底座会话进程；无任务时账本为空但文件存在。

## 7 OS 守护注册（S-03）

`guard/` 模块按平台渲染守护配置，**渲染与反解析成对**（`render()` + `parse()`，支持幂等重装与升级迁移判定）。

> ⚠️ **M0+S2 实证修正（2026-08-24）**：① 注册计划任务需**一次提权**（非提权全路径拒绝访问；提权交互须在用户终端上下文，agent 宿主弹 UAC 不可靠）；运行期零提权（`schtasks /run` 启动自己的任务不需要权限）。② **RestartOnFailure 实测不生效**（手动/触发 × 杀死/自退78 四组合零重试，配置完整在场）——Windows 守护改为**重复触发器模型**（§7.1）。③ 配置用 PowerShell `New-ScheduledTask*` cmdlet 编程构造（已验证）；若走 XML 文件必须 UTF-16。详见 [S2 报告](../../research/S2-Windows守护调度语义Spike报告-2026-08-24.md)。

### 7.1 Windows：重复触发器模型（S2 实证后定稿）

| 组件 | 配置 | 作用 |
|------|------|------|
| LogonTrigger | enabled | 登录即起（开机自启与 keepalive 同一份配置，D-021） |
| **TimeTrigger 重复** | 每 1 分钟（可配置，降噪可至 5 分钟）；RepetitionDuration 用有限时长（如 24h，到期由 LogonTrigger/每日重挂续期；`[TimeSpan]::MaxValue` 超出 XML 范围不可用） | **崩溃恢复主力**：服务死 -> 下一次触发拉回（S2 实测 43 秒恢复） |
| MultipleInstancesPolicy | IgnoreNew | 服务活着时重复触发被跳过，不产生第二实例 |
| 幂等 daemon | D-020 单实例语义 | 兜底：触发时已在运行 -> 直接退出（与 `workbench start` 幂等同构） |

必覆写的四个反直觉默认值（R-12）不变：

| 字段 | 值 | 说明 |
|------|-----|------|
| `<ExecutionTimeLimit>` | **PT0S** | 默认 72h 杀任务 |
| `<DisallowStartIfOnBatteries>` | **false** | 默认拔电源不启动 |
| `<StopIfGoingOnBatteries>` | **false** | 默认切电池即停 |
| `<StopOnIdleEnd>` / `<RestartOnIdle>` | **false** | 默认空闲即停 |
| `<Actions>` | `workbench.exe __daemon` | 稳定路径，不嵌版本号（D-028） |

**78 语义权衡（Windows 已知项）**：退 78（配置错误）的进程会被下一次触发拉起——每分钟一次瞬退，非风暴（间隔可配置拉长降噪）。Linux 侧 systemd `RestartPreventExitStatus=78` 语义正常（S3 实测含对照组）——「不徒劳重启」仅在 Linux 完整成立。

### 7.2 Linux：systemd --user unit

`~/.config/systemd/user/ieidev-workbench.service`：`Restart=always` + `RestartSec=5` + `StartLimitBurst=5/IntervalSec=60` + **`RestartPreventExitStatus=78`** + `SuccessExitStatus=0 143` + `KillMode=control-group` + `After/Wants=network-online.target` + `WantedBy=default.target` + `EnvironmentFile=-<path>`；注册后 **`loginctl enable-linger $USER`**（登出不死）。

### 7.3 macOS：launchd

`~/Library/LaunchAgents/com.ieidev.workbench.plist`：`RunAtLoad=true` + `KeepAlive=true` + `ThrottleInterval=10` + `ExitTimeOut=10`。

### 7.4 注册/注销 API

```
guard.ensureRegistered()     // start 时调用：渲染->与已注册配置比对->不一致则更新（幂等）
guard.unregister()           // uninstall 时调用
guard.status()               // 返回注册状态与配置是否漂移（status --verbose 消费）
```

注册失败**不阻塞启动**，仅 lifecycle.log 告警 + `--no-keepalive` 心智（R-11：企业策略可能拦）。

## 8 单实例语义（S-06，D-020）

| 场景 | 判定 | 行为 |
|------|------|------|
| 重复 `start` / 重复点图标 | 端口占用方 `/healthz` 返回自家 `app`+`uid` 匹配 | **幂等**：不起新进程，`portal` 打开浏览器，退出码 0 |
| 端口被第三方占 | `/healthz` 无响应或 app/uid 不符 | 退出码 **78** + 打印占用进程名（`Get-NetTCPConnection`/`lsof`/`ss`）+ 提示改端口 |
| 旧实例僵死 | service.json 在、pid 活、`/healthz` 连续 3 次失败超 30s | 清 run/ 接管（记 lifecycle.log） |

## 9 子进程账本与孤儿回收（S-05，R-16）

启动序列第 5 步遍历 `workers.json`，**三条件同时成立**才杀（整组，按 pgid）：

1. `lastSeenAt` 超过过期阈值（默认 10 分钟，即「上一个生命周期遗留」）
2. 进程仍存活（pid 探测）
3. **可执行文件路径属于本安装目录**（防误杀第三方）

命中 -> 按 pgid 杀整组 + lifecycle.log 记录（`orphan_reaped` 事件，含 workerId/pid/pgid）；少一个条件都不杀。运行期 `runtime/` 维护账本的注册/心跳刷新/注销。

Windows 进程组语义：子进程 spawn 时即加入 Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`），杀组 = 关 Job；`pgid` 字段记 Job 句柄派生 ID。

## 10 本地 HTTP API 面（S-12 + 各模块挂载）

### 10.1 安全边界（S-12）

- 仅绑 `127.0.0.1:19980`（可配置端口，不可配置 host）

## 12 磁盘 GC 与存储版本守卫（S-09/S-10）

### 12.1 storage（storage/ 模块）

- SQLite + WAL；`bun:sqlite` 仅限本目录（D-018）
- **loadExtension 用法（M0 实测）**：`new Database(path)` 后直接 `db.loadExtension(绝对路径)`；构造器选项 `{ allowExtension: true }` 在 Bun 1.3.9 Windows 报 `SQLITE_MISUSE`，勿用
- sqlite-vec 走 loadable extension：`resources/sqlite-vec/<os>-<arch>/vec0.*`，运行时 `load_extension()`（T2）；**V0.1 是否启用向量能力**：员工业务无向量需求，schema 建表但不加载（load 失败降级告警，不阻塞启动）——为 L2 记忆管线预留
- `data/storage-state.json`：`{storageSchemaVersion, lastOpenedByVersion}`；启动序列第 3 步：数据 schema 高于二进制支持 -> 拒启（78）；每次打开写 `lastOpenedByVersion`（T14）

### 12.2 磁盘 GC（启动第 6 步，C-8/W-6）

- `updates/` 内超过 7 天未应用的包 -> 删（记 `disk_gc`）
- 超额轮转日志 -> 删
- profile 总体积 > 500MB -> lifecycle.log 告警（不自动删业务数据）

## 13 检查更新（U-01~U-04，对接平台包 API）

### 13.1 流程

```
触发：启动后 30s + 每 24h + workbench update --check + 托盘菜单（TR-03）
  -> GET {platform}/api/v1/public/workbench-packages        （D-023：更新源=平台）
  -> 取与当前 os/arch 匹配的最新 published 包，semver 比对
  -> 有新版：status JSON 置 pendingUpdate + lifecycle.log 记 update_available
             + 前端 F-04 顶栏提示（版本/说明/大小/SHA-256）
  -> 用户确认下载（唯一路径，默认不预下载，省流量）
  -> 下载至 updates/ -> sha256 校验（不匹配丢弃+报错，U-02 验收）
  -> V0.1 应用方式：引导用户运行新安装包（不替换二进制，D-028 无 bootstrapper）
```

### 13.2 状态与可见性

- `workbench status` JSON 含 `pendingUpdate: {version, size, downloadedAt} | null`（三处可见之一，W-5/W-6）
- 预下载开启时（config.update.preDownload=true）：应用时机**多于一个**——用户点「立即应用」（提示跑安装包）+ 启动 GC 兜底清理；V0.1 无自动重启应用

## 14 优雅退出（S-14）

```
收到 stop/SIGTERM
  -> 置 reliability.json{cleanStop: true}
  -> 通知后台任务停（心跳定时器/更新检查；workers.json 内 running 任务按序收口，超时放弃）
  -> 关 HTTP（≤5s drain）
  -> 停止持有 service.lock，删 run/service.json + service.pid/.port
  -> 验证端口真的释放（Windows: Get-NetTCPConnection -State Listen 轮询 3s；未释放 ->
     按孤儿清理三条件处置，只碰本安装目录进程）
  -> 退出码 0
```

SIGTERM 退出码 143（systemd `SuccessExitStatus=0 143` 配套）。子进程 spawn 一律不继承监听句柄（根子上的预防，§7.5 调研）。
