## D-003 认证采用「邮箱验证码首登即注册 + JWT 双 token」🟢

- **决策**：邮箱+验证码为主要登录方式（首次登录即注册），密码为可选补充；JWT access token（约 1h）+ refresh token（约 30d，滚动轮换）；token 由工作台后端进程持有与刷新，浏览器↔工作台之间用本地 session cookie 隔离；每个工作台实例注册 device_id，token 与设备绑定，支持平台侧远程吊销。
- **理由**：交接文档 §4.4 给了"邮箱+密码 / 邮箱+验证码"两个选项，验证码路线免去密码找回/强度策略等企业内不必要的复杂度；JWT 优于 session 的点在于工作台是长驻本地服务、平台无需为每台工作台维护会话状态；device 绑定为后续审计（哪台机器上报的数据）提供锚点。
- **影响面**：文档 D 全篇；文档 B 的上传/下载鉴权。
- **备选**：纯 session（弃：平台要维护跨大量本地工作台的会话，且断线重连语义差）；OAuth2 device flow（弃：无第三方 IdP 时过度设计，但文档 D 预留企业 SSO 扩展位）。

## D-005 工作台安装载体 = CLI 一行命令为主 + Windows exe 打包 🟢

- **决策**：macOS/Linux 用 `curl … | bash` 或 `npm install -g`，Windows 提供 exe 安装包；安装后 `ieidev-workbench start` 拉起本地服务，浏览器访问 `localhost:19820`。Workshop V4 提到的"IDE 插件市场安装"定位为**接入入口**（插件里一键拉起/打开工作台），不改变工作台独立应用本质。
- **理由**：白皮书 §4.4 与 CLAUDE.md 均定调 exe/CLI；QoderWaker 参照（环境与设备页的 `curl -fsSL …/install.sh | bash`）与此一致。
- **影响面**：文档 B（底座与环境页）、文档 D（首次启动登录流）。

## D-006 创建向导五步 → 员工包文件的生成映射 🟢

- **决策**：向导五步与产物的映射固定为——
  1. **模板**：选角色模板→预填后续全部表单（模板=一份完整的预置 manifest+AGENTS.md 素材）；
  2. **身份**：→ AGENTS.md（persona 五段式渲染：identity/principles/capabilities/usage_modes/constraints）+ manifest `agent:`/`persona:` 段；
  3. **能力**：→ manifest `skills:`/`mcp:` 段；从 AgentHub（Keyhub）拉取的 skill **复制进包**（skills/ 目录，锁定版本，包自包含）；MCP 连接器写 mcp.json；
  4. **约束**：→ manifest `constraints:` 段；预置红线规则库中"声明式可编译"的规则编译为 hooks/hooks.json（路径C 底座硬拦截），全部规则同时注册进 CQO（路径A 底座无关拦截）——双保险；tier-map/token 配额走路径 B（flow-driver 派发时查）；
  5. **流程+治理**：runbook → 渲染进 AGENTS.md 尾段（流程档）；node-table → 生成 orchestration/<id>.node-table.yml 骨架（编排档，可后续在 workflow 编辑器细化）；治理 → 仅写 manifest `governance:` 段（运行时不生效，上架/审批/审计时由平台消费）。
- **理由**：与扩展配置文档 v0.1 的"配置/开发分界"和三条落地路径（A: CQO / B: flow-driver / C: 底座原生）逐条对齐；skill 复制进包（而非引用）保证"三条产出路径同构 + 包可 git 管理 + 离线可安装"。
- **影响面**：文档 A 核心章节；文档 B 的落位映射输入。
- **备选**：skill 以引用形式留在包外由工作台运行时解析（弃：破坏包自包含性，离线/手写路径不同构）。

## D-013 安装作用域两级：员工驻地（默认）× 项目工作区，身份互斥、能力共存 🟢

- **决策**：安装目标 = 底座 × 作用域。作用域两种——**员工驻地**（工作台管理的专属目录 `homes/<employee_id>/`，对话会话以此为 cwd）与**项目工作区**（用户项目目录，员工"进驻项目"）。同一 (底座×工作区) 同时只有一名**当值员工**（身份文件 CLAUDE.md/AGENTS.md 是单一身份源，互斥）；skills/hooks/mcp 按员工命名空间目录并存（切换当值不增删能力文件）。当值切换时旧身份文件移到停靠区。
- **理由**：底座的身份加载机制决定一个目录只能有一个"我是谁"；QoderWaker 的 Waker 也是按设备+工作目录派发。驻地目录解决"不在任何项目里也能对话"；命名空间并存避免切换员工时反复重装能力文件。
- **影响面**：文档 B §2.2/§4.6；文档 C 对话界面选工作目录交互。
- **备选**：全局安装单员工（弃：一台机器只能有一个员工，与多员工产品形态冲突）；per-session CLI 注入身份（弃：白皮书 §5.3 已论证否决）。

## D-014 落位后端 v0.1 统一用 file（裸文件落位），plugin 后端留作 CC/CB 后续优化 🟢

- **决策**：安装执行器抽象为"落位计划（源→目标→动作）+ 落位后端"。v0.1 所有底座统一 **file 后端**（copy/convert/merge + 事务 + 校验和）；1.0 实证过的 plugin 后端（CC/CB 的 marketplace add + plugin install）保留为后续优化项（B-Q2）。
- **理由**：员工包核心是"身份+能力"，身份文件（CLAUDE.md）本就在插件机制之外，插件机制只覆盖 skills/hooks/commands 一半问题；单一后端让首版安装/卸载/漂移/当值切换共用同一套 placements 数据模型；plugin 后端的收益（底座自管缓存与卸载）可后续替换 file 后端的一个子集而不动数据模型。
- **影响面**：文档 B §4.2/§4.5/§4.7。
- **备选**：CC/CB 走 plugin、其他走 file 的双后端（弃：首版两套卸载/漂移逻辑，复杂度翻倍）。

## D-015 employee_id 语义分层：manifest 三元组含域后缀，工作台本地层一律用纯 id 🟢

- **决策**：manifest 身份三元组的 `employee_id` 保留白皮书 §5.2 语义（`<id>@<组织节点>`，组织节点默认取所属部门），仅用于平台身份与 AgentCard 注册；工作台本地的 API 参数、安装清单文件名（`installs/<id>@<base>.json`）、任务模型字段一律取 **manifest.id（纯 id）**。
- **理由**：评审（跨文档镜头）发现三份文档对 employee_id 用法分裂——若本地层也用带域全名，文件名会出现双 @ 且所有 API 示例不成立；白皮书三元组语义不可推翻，故做分层而非改语义。
- **影响面**：文档 A §4.3 employee_id 行、文档 B §4.3 命名约定注记、文档 C §4.2 注记。
- **备选**：全链路统一带域全名（弃：本地层冗长且与所有示例冲突）；废弃三元组（弃：违反白皮书）。

## D-016 使用深度映射修正：+编排（node-table）= 使用深度 L2，跨员工接力（使用深度 L3）归 goal/Team 层 🟢

- **决策**：向导「使用深度」选项 +编排 对应 node-table 编排档 = **使用深度 L2**；requires.level 推导为 裸用→L0、+方法论/+流程→L1、+编排→L2；使用深度 L3（跨员工接力）是 goal/群组绑定 workflow 时由工作台校验的能力门槛，**不由单员工包声明**。
