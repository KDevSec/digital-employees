## 1 定位与范围

### 1.1 定位

员工新建是工作台三条员工获取路径之一（创建向导生成 / 市场下载 / 手写 manifest【修订：手写改为外部zip包导入】，三者产出**完全同构**，白皮书 §5.3）。创建向导把"数字员工 = 智能体底座 + 扩展配置"的五大类别（身份/能力/约束/流程/治理）翻译成五步表单，最终产出一个**中立 canonical 布局的员工包**（UPP v0.2 §2），可 git 管理、可安装到任意已适配底座、可上传 AgentHub（Keyhub）上架。

### 1.2 范围内

1. 创建向导完整流程（五步表单 + 右侧产出物预览 + 草稿机制）
2. 员工包生成逻辑（向导数据 → manifest.yml / AGENTS.md / skills/ / hooks/ / mcp.json / orchestration/ 的构建规则）
3. 内置角色模板定义（dev-engineer / req-architect 全量，test-engineer / reviewer / researcher 差异，Custom）
4. 编辑已有员工（复用向导，版本递增）【修订：待细化】
5. 生成完成后与安装、详情页的衔接（衔接点引用配套文档，不重复设计）

### 1.3 不做什么

- ❌ 安装流程本体、安装报告 schema —— 归《员工安装与底座适配设计》
- ❌ 详情页各 tab 的字段与交互 —— 归《员工运行与展示设计》（本文只引用 D-002 的 10 tab 名）
- ❌ manifest 的 JSON Schema 正式化 —— 交接文档 §5.1 下一阶段任务，本文给"工作字段表"
- ❌ skill 市场的上架审核侧 —— 平台侧能力，本文只消费"搜索/下载"两个契约（定义归文档 B）
- ❌ 群组创建 —— 不在本轮范围（Q-010）

## 2 用户旅程

### 2.1 主旅程：从模板到上岗（预计 3-5 分钟）

```
我的员工（列表页）
  └─ 点「＋ 新建员工」
       └─ 员工创建页（全屏子页，非模态——原型 wb-create 形态）
            Step 1 选择角色模板 ──── 点「使用模板」预填全表单
            Step 2 身份 ─────────── 改岗位名/ID/职责描述/勾选工作原则/使用深度
            Step 3 能力 ─────────── 勾选 skills（AgentHub 搜索 + 模板默认）+ MCP 接入
            Step 4 约束 ─────────── 勾选权限红线 + 模型档位 + Token 配额
            Step 5 流程+治理 ────── 选 runbook/node-table + 治理分级/可见范围/审计
            （右侧全程实时预览 manifest + 目录树，schema 校验通过才允许生成）
            └─ 点「生成员工包骨架」
                 └─ 生成完成态：展示包目录 + 三个出口
                      ① 「安装到底座并注册」→ 底座选择 → 安装（文档 B）→ 详情页
                      ② 「仅保存到本地」→ 列表页新增"未安装"卡片  【修订：这个改成仅保存到角色模版，不再列表新增未安装的卡片，太冗余了】
                      ③ 「上传到 AgentHub」→ 治理分级审批流（文档 D §权限）
```

### 2.2 次旅程

| 旅程                | 入口                   | 与主旅程差异                                            |
| ----------------- | -------------------- | ------------------------------------------------- |
| 从 Custom 白纸创建     | Step 1 选「Custom 自定义」 | 无预填，Step 2-5 全手工；右侧预览从空骨架开始                       |
| 编辑已有员工            | 详情页「编辑档案」按钮          | 向导以现有包数据预填；`id` 锁定不可改；保存时 `version` 按语义化递增（§3.10） |
| 草稿续作【修订：降低优先级】    | 列表页草稿卡片 / 向导内「保存草稿」  | 恢复到上次离开的步骤；草稿不产包文件                                |
| 手写包导入对照【修订：降低优先级】 | ——                   | 手写者直接按 §4 的文件规则写包；向导只是这些规则的 UI 化（三路径同构的含义）        |

### 2.3 异常旅程

| 场景                   | 行为                                                                            |
| -------------------- | ----------------------------------------------------------------------------- |
| AgentHub 不可达（离线/未登录） | Step 3 市场搜索区置灰，显示「AgentHub 不可达，仅本地 skill 可选」；模板默认 skill 若已缓存在本地模板库则不受影响；不阻塞生成 |
| 员工 ID 与本地已有员工重名      | Step 2 失焦即校验，红字报错「ID 已存在，可改为 xxx-2」；生成按钮禁用                                    |
| schema 校验失败          | 右侧预览面板顶部徽章从「schema 校验通过」变红「校验失败 n 项」，点击展开逐项定位到对应 Step 字段                      |
| 中途关闭页面               | 自动保存草稿（localStorage + 工作台数据目录双写），下次进入提示恢复                                     |
| 生成时磁盘写入失败            | 生成事务性：先写临时目录再原子改名；失败则报错并保留向导态                                                 |

## 3 信息架构与界面设计

### 3.1 页面布局（基线：原型 wb-create）

```
┌────────────────────────────────────────────────────────────────────┐
│ ← 员工创建                    ● localhost:19820 · 工作台运行中  [↑上传到 AgentHub] │
├──────────────────────────────────────────────┬─────────────────────┤
│ ▎1 · 选择角色模板                              │  产出物预览          │
│   [开发工程师✓][需求架构师][测试工程师]          │  ┌───────────────┐  │
│   [评审专家][调研员][Custom]                   │  │ schema 校验通过 │  │
│                                              │  │ manifest.yml   │  │
│ ▎2 · 配置向导 —— 基于「开发工程师」模板          │  │ (YAML 实时渲染) │  │
│   ①模板─②身份─③能力─④约束─⑤流程+治理 (步骤条)   │  └───────────────┘  │
│   [当前步骤表单区]                             │  将生成的目录结构     │
│                                              │  frontend-dev/      │
│   [生成员工包骨架] [保存草稿] [上一步]           │  ├ manifest.yml …   │
│                                              │  [安装到底座并注册] │
└──────────────────────────────────────────────┴─────────────────────┘
```

- 顶栏：返回箭头 + 页名 + 工作台运行状态徽章 + 「上传到 AgentHub」（生成前禁用）。
- 主列（约 2/3 宽）：区块 1 模板卡片区；区块 2 步骤条 + 当前步骤表单。
- 右栏（约 1/3 宽，sticky）：产出物预览面板（§3.8）+ 目录树 + 主行动按钮。
- 与 QoderWaker 差异说明：QoderWaker 新建 Waker 是轻模态（角色/名称/头像/简介四项）；我们的员工包字段量大得多，采用全屏子页 + 五步向导（原型 wb-create 已是此形态）。**原型偏差记录**：无。

### 3.2 Step 1 · 选择角色模板

| 元素                                 | 说明                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 模板卡片 ×6 【修订：0.1版本先内置需求架构师、开发工程师即可】 | 开发工程师 dev-engineer / 需求架构师 req-architect / 测试工程师 test-engineer / 评审专家 reviewer / 调研员 researcher / Custom 自定义 |
| 卡片字段                               | 图标字（开/需/测/评/调/＋）、岗位名、kind 徽章（flow-owner / callee）、一句话职责、模板 id、「使用模板 →」按钮                                     |
| 选中态                                | 右上角 ✓，边框高亮；同时右侧预览立即渲染该模板的完整 manifest                                                                         |
| 「使用模板」                             | 预填 Step 2-5 全部表单后自动跳到 Step 2；再次点其他模板会弹确认「切换模板将重置已修改的字段」                                                      |
| Custom                             | 文案"从空白骨架开始，自行定义职责、能力与流程，完全自由的员工定义"，点「开始 →」进入空表单                                                              |

模板内容本体见 §4.9 内置角色模板库。

### 3.3 Step 2 · 身份 —— 员工是谁【修订：参考QoderWaker的docs/references/QoderWaker/qoderwake-role-template.zip，也需要调研openclaw、Hermes、Claudecode等是如何定义Agent的身份的，这决定了后续的安装】

| 字段    | 控件                                                                                    |  必填  | 校验                                                                                            | 写入目标                                               |
| ----- | ------------------------------------------------------------------------------------- | :--: | --------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 岗位名称  | 文本框（如"前端开发工程师"）                                                                       |   ✅  | 1-30 字符                                                                                       | manifest `display` + AGENTS.md 标题                  |
| 员工 ID | 文本框（如 frontend-dev）                                                                   |   ✅  | `^[a-z][a-z0-9-]{1,31}$`；本地唯一（失焦校验）；编辑模式锁定                                                    | manifest `id`；包目录名                                 |
| 所属部门  | 下拉（从平台组织架构拉取；离线时手填）                                                                   |   ⬜  | ——                                                                                            | manifest `agent.department`                        |
| 职责描述  | 多行文本（模板预填，可改）                                                                         |   ✅  | 10-500 字符                                                                                     | manifest `persona.identity` + AGENTS.md「我是谁」段      |
| 工作原则  | 多选 chip + 「＋自定义」（如"增量交付，小步迭代""证据驱动验证""无障碍优先"）                                         |   ⬜  | 自定义项 ≤40 字符                                                                                   | manifest `persona.principles[]` + AGENTS.md「我的原则」段 |
| 使用深度  | 多选（裸用（直接对话）/ +方法论（skill 调用序列）/ +流程（runbook 流程档）/ +编排（node-table 编排档·独立会话链，对应使用深度 L2）） | ✅ ≥1 | 勾选「+编排」时 Step 5 的 node-table 变必填。注：跨员工接力（使用深度 L3）由 goal 在 Team/群组层编排（白皮书 §3.4/§4.2），不是单员工包的选项 | manifest `persona.usage_modes[]`                   |
| 头像    | 上传（PNG/JPG ≤2MB，参照 QoderWaker）或选内置图标字                                                 |   ⬜  | ——                                                                                            | 包内 `assets/avatar.png` + manifest `avatar`         |

联动规则：

- `persona.capabilities` 不在本步手填——由 Step 3 勾选的 skills 自动汇总生成（扩展配置 v0.1 §2.1"能力配置自动汇总"）。
- `persona.constraints`（软约束，给 agent 自己读的自然语言）由 Step 4 的红线勾选自动汇总，可在 Step 4 内附加自定义描述。

### 3.4 Step 3 · 能力 —— 员工会什么

**区块 1：能力 Skills**

| 元素                     | 说明                                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 模板默认 skill chips       | 已勾选态展示（如 component-arch / responsive / a11y-audit / perf-tuning），可取消勾选                                                                                                           |
| 「从 AgentHub 添加」        | 打开搜索浮层：搜索框 + 结果列表（skill 名/版本/评分/下载量/兼容底座/一句话描述）+「添加」按钮。调 `GET /api/agenthub/skills?q=`（契约见文档 B §5）【修订：注意拉取skill包时，如果只想拉取superpowers里的brainstorming的skill，如何实现呢，这个需要考虑，对于易用性特别关键】 |
| 「本地新建 skill」【修订：降低优先级】 | 进入 skill 编辑器（§3.4.1）                                                                                                                                                             |
| 每个已选 skill 行           | 名称 @ 版本（版本下拉可切换）· 来源徽章（agenthub / local / 模板内置）· 移除                                                                                                                              |

**区块 2：MCP 接入【修订：降低优先级】**

| 字段         | 控件                                                             | 写入目标                        |
| ---------- | -------------------------------------------------------------- | --------------------------- |
| 知识库连接器     | 多选（从 AgentHub 连接器目录 + 手填 endpoint），每项含 access: read/read-write | manifest `mcp[]` + mcp.json |
| 外部工具 / 数据源 | 同上（如 GitHub API、Jira）                                          | 同上                          |

#### 3.4.1 skill 编辑器（最小流程）【修订：降低优先级】

新建本地 skill 时不离开向导，右滑抽屉：

1. 填 `name`（`^[a-z][a-z0-9-]+$`，自动加工作台配置的 skill 前缀）、`description`（触发场景一句话）、正文 markdown（何时用/怎么做/边界）。
2. 保存 → 写入包内 `skills/<name>/SKILL.md`（生成规则 §4.5），source 标 `local`。
3. 后续可在详情页「技能」tab 继续维护（文档 C）。

### 3.5 Step 4 · 约束 —— 员工不能干什么【修订：降低优先级】

**区块 1：权限红线**（预置规则库多选 + 自定义，规则库全表见 §4.6.1）

- 勾选交互：chip 多选，勾中显示蓝色✓；每条 hover 显示"检查方式 + 干预动作 + 落地路径（CQO / 底座 hook 双保险 或 仅 CQO）"。
- 「＋自定义红线」：自然语言描述（如"禁止访问财务系统 API"），标注为 `custom` 类型——仅走 CQO 语义匹配路径，不编译底座 hook（§4.6.1 规则库 custom 行）。

**区块 2：模型档位**（tier-map，按节点类型分档）

| 档位      | 默认模型         | 适用       |
| ------- | ------------ | -------- |
| 设计 / 评审 | Opus         | 设计、评审类节点 |
| 编码 / 执行 | Sonnet       | 编码+执行节点  |
| 轻量查询    | Haiku        | 轻量查询     |
| 长上下文聚合  | Sonnet \[1M] | 跨文档聚合    |

- 交互为三卡片单选（原型形态"Opus 设计+评审节点 / Sonnet 编码+执行节点 / Haiku 轻量查询节点"）+「高级」展开逐档自定义。
- 写入 manifest `constraints.model_tiers`（语义档位，**不写死模型 ID**——安装时由底座 shim 按底座 tier-map 解析，1.0 的"5 档语义 tier 映射"经验，见 recon §2.2）。

**区块 3：Token 配额**

| 字段    | 控件          | 默认（模板可覆盖） | 写入                                 |
| ----- | ----------- | --------- | ---------------------------------- |
| 单任务上限 | 数值框（如 500K） | 模板值       | `constraints.token_quota.per_task` |
| 月度上限  | 数值框（如 20M）  | 模板值       | `constraints.token_quota.monthly`  |

配额执行属运行时（路径 B：flow-driver 派发前查），本步只声明。

### 3.6 Step 5 · 流程 + 治理【修订：降低优先级】

**区块 1：流程形态**（单选卡片）

| 形态             | 说明文案                                                            | 后续                                      |
| -------------- | --------------------------------------------------------------- | --------------------------------------- |
| runbook 流程档    | "agent 自跟的 skill 调用序列，同一会话完成"                                   | 展开 runbook 步骤编辑器（§3.6.1）                |
| node-table 编排档 | "flow-driver 驱动的独立会话链（使用深度 L2）；跨员工接力由 goal 在 Team 层编排（使用深度 L3）" | 生成骨架 node-table，提示「生成后到 workflow 编辑器细化」 |

- 使用深度勾了「+流程」→ runbook 必填；勾了「+编排」→ node-table 必填；两者可同时存在（runbook 为轻量日常，node-table 为完整 SOP）。
- kind 推导：有 node-table → manifest `kind: flow-owner`；模板 reviewer 类（被发函调用、无自有 flow）→ `kind: callee`，本区块替换为 dispatch-table 说明（callee 不选流程形态，见 §4.9 reviewer 模板）。

#### 3.6.1 runbook 步骤编辑器

```
┌ TDD 开发流程                            ＋ 添加步骤 ┐
│ ① 理解需求与变更范围   skill:[无(纯对话)▼] 自检:[确认理解无误] │
│ ② 编写失败测试        skill:[unit-test▼]  自检:[红灯]       │
│ ③ 最小实现使测试通过   skill:[code-impl▼]  自检:[绿灯]       │
│ ④ 重构优化           skill:[code-impl▼]  自检:[测试全绿]    │
└（拖拽排序 · 行内删除）                                      ┘
```

- skill 下拉只能选 Step 3 已勾选的 skill（保证 runbook 引用闭合）；自检为一句话文本。

**区块 2：治理**

| 字段      | 控件                                                             | 默认联动                         | 写入                           |
| ------- | -------------------------------------------------------------- | ---------------------------- | ---------------------------- |
| 治理分级    | 四卡片单选：治理分级 L1 公司级 / L2 部门级 / L3 团队级 / L4 个人级（各卡片注审批/可见/审计三行说明） | 选卡后自动预填下面两项的推荐值（白皮书 §3.6 表）  | `governance.level`           |
| 可见范围    | 下拉：仅自己 / 团队内 / 部门内 / 全公司                                       | 随分级推荐，可改小不可改大（改大需走升级审批，提示文案） | `governance.visibility`      |
| 审计级别    | 下拉：全量记录 / 仅异常记录 / 可关闭                                          | 随分级推荐；治理分级 L1/L2 锁定"全量记录"    | `governance.audit`           |
| 生命周期负责人 | 文本（默认当前登录邮箱）                                                   | ——                           | `governance.lifecycle_owner` |

- 权限校验：当前登录用户的角色决定可选的治理分级上限（个人开发者最高可建治理分级 L4/L3；部门管理员可建 L2——矩阵见文档 D §3.3）。超出权限的卡片置灰并注明"需部门管理员权限"。

### 3.7 右侧产出物预览面板

| 区块              | 行为                                                                                                                                                                                                                                     |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 4.4 AGENTS.md 五段式渲染模板

AGENTS.md 是**唯一指令源**（UPP §2 要点 1），由身份/能力/约束/流程四步共同渲染。模板（`{{ }}` 为插值）：

```markdown
# {{display}}（{{id}}）

## 我是谁
{{persona.identity}}
所属：{{agent.department}} · {{agent.role}} · v{{version}}

## 我的原则
{{#each persona.principles}}- {{this}}
{{/each}}

## 我的能力
{{#each persona.capabilities}}- {{this}}
{{/each}}
（技能清单：{{#each skills}}{{name}}@{{version}} {{/each}}——按需加载对应 SKILL.md）

## 我的边界（软约束）
{{#each persona.constraints}}- {{this}}
{{/each}}
> 硬约束由工作台 CQO 与底座 hook 双重执行，越界操作会被阻断。

## 我的工作方式
使用深度：{{persona.usage_modes | join(" / ")}}
{{#if runbook}}
### {{runbook.name}}（runbook 流程档）
{{#each runbook.steps}}{{step}}. {{action}}{{#if skill}}（调用 skill：{{skill}}）{{/if}} —— 自检：{{self_check}}
{{/each}}{{/if}}
{{#if orchestration.node_table}}
### 编排档
完整 SOP 由 node-table（{{orchestration.node_table}}）定义，由工作台 flow-driver 驱动；直接对话时不必自跑该流程。
{{/if}}
```

1. 纯 markdown、无 HTML；标题层级固定，便于 CC shim 转 CLAUDE.md 时零损转换（文档 B §落位）。
2. 治理字段**不渲染**进 AGENTS.md（治理不是给 agent 读的，扩展配置 §6.3）。
3. 完整 dev-engineer 渲染示例见附录 A。

### 4.8 node-table 骨架生成【修订：降低优先级】

选「+编排」后按模板生成最小骨架（格式沿用 1.0 实证 schema，recon §2.5）：

```yaml
# {{display}} SOP —— 由创建向导生成的骨架，请在 workflow 编辑器中细化
flow: {{id}}-flow
delivery_node: n2-deliver
max_retries: 3
terminal_fail: n-fail
nodes:
  - {id: n0-start,   name: 任务理解,  kind: action,   next: [n1-work]}
  - {id: n1-work,    name: 主体执行,  kind: action,   next: [n2-deliver]}
  - {id: n2-deliver, name: 交付确认,  kind: gate,     gate: g-deliver, next: [n3-done, n1-work]}
  - {id: n3-done,    name: 完成,      kind: terminal, next: []}
  - {id: n-fail,     name: 回流溢出终止, kind: terminal, next: []}
gate_specs:
  g-deliver: {kind: review, on_pass: n3-done, on_reflow: n1-work, reviewer: self}
```

- 内置模板（dev-engineer 等）不用骨架，而是带**完整预置 node-table**（§4.9）。
- 节点 `kind` 三值 + `gate_specs` 三类（decision/review/acceptance）与 1.0 保持兼容，workflow 编辑器（文档 C）按此 schema 读写。
