## 总体结论

**需修订后合并。** 结构骨架（八类 manifest / 六段式 AGENTS / hooks 编译契约 / 个人表形态）健康且与上游大体对齐，但「schema v0.2 ↔ 7 份物化物料」存在两处必挂级互斥（🔴），加上 1.0 编排语义在 skill 体内的残留、blocked 上报通道凭空使用、个人表 reviewer:self 与 2.0 契约语义升级的冲突，须在合并前处置；不涉架构返工，均为一轮可修的量级。

## 问题清单

### 🔴 阻断合并

**1. 全部 7 份 manifest 的 skills 条目缺 `template_id`，过不了 v0.2 自家 schema**
- 锚点：`shared-protocol详细设计-v0.2.md` §3.2（template 分支 `template_id: z.string()` 必填）vs 7 份 manifest（skills 条目均仅 `{name, version, source_type: template}`）
- 问题：discriminatedUnion 命中 template 分支后必因 template_id 缺失校验失败；zod 真源接入 CI 即全线红。
- 建议：schema 将 template_id 改 `.optional()`（模板自证场景自指无意义，E-12 重建时注入更合理）；或物料补齐。

**2. SKILL.md frontmatter 的 `.strict()` 驳回 5 份物料实际携带的溯源键**
- 锚点：schema §3.1（strict 仅 name/description）vs 5 份 SKILL.md（带 `vendored_from:`）、frontend-design（带 `license:`）
- 问题：E-02 校验接入即拒；且 vendored_from/license 是 MIT vendoring 溯源要求，不是噪声。
- 建议：schema 增 `vendored_from/license: optional`；不要删物料的溯源键。

### 🟡 合并前最好修

**3. dev 个人表 `reviewer: self` 与编排契约的 2.0 语义升级冲突（self 在 2.0 无执行体）**——建议契约补注「个人表允许 reviewer: self = 驻留员工自评闸不 spawn」并由 I0-4 收录；不能靠默契。
**4. sec-compliance AGENTS.md「engine_advance 报 blocked」超出引擎 API 面**（§9.1 advance 无 blocked/status 参数）——改为不依赖未定义通道的表述，或上游补通道后对齐。
**5. 设计 §4 渲染定稿只有执行者三件套，3/7 物料的第六段（评审位回函三件套 record_gate 系）无法由它产出**——§4 增评审位变体条款。
**6. writing-plans SKILL.md 残留 1.0 主从编排指令**（「主控派 fresh subagent（推荐）」）——违反 CLAUDE.md §2 决策 1，删改为 2.0 语境。
**7. 两处跨包 skill 引用**（brainstorming→writing-plans、kdev-gen-proto→frontend-design，被引 skill 不在本员工包）——改条件式引用或自含模式。
**8. kdev-gen 七件套体内 1.0 V4x.1 流程资产引用未清理且文件不随行**（nodes-data/、准入脚本、veto 编号、迭代档案坐标）——至少在 skills-remaining 如实列账并修正设计 §6.2 完成口径。
**9. 4 份 superpowers 系 MIT vendored skill 未随行 LICENSE，vendored_from 指向悬空**——各补 licenses/superpowers-LICENSE。
**10. sec 三员 manifest 声明的 skill 包内不存在**（声明-实物不符）——暂摘除 skills 条目加注释，或设计加注占位白名单；倾向前者。
**11. 设计文档两口径：预置物化占位 operator `local@devzero` 过不了自家 schema 的 email 校验**——统一 `demo@devzero.local`。
**12. kind 判据不可判：sec-design/sec-code 与 reviewer-expert 同形态不同 kind**——补可检验判据（能否裸用独立完成全部职责）并复核边界员工。
