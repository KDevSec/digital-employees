## 1. 项目一句话

**把一支 AI 研发团队从"一个全家桶插件"升级为"工作台（运行层）+ 员工包 + 管控平台"三层分离的全新架构。**

当前处于架构设计阶段，白皮书已迭代到 v0.7，核心架构决策已定调。需要进一步调研若干技术难点，然后进入 MVP 开发。

## 3. 架构概览（给接手同事的速览）

```
┌──────────────────────────────────────────────────────────────┐
│                    管控平台（远端 Web）                        │
│  员工市场(AgentHub) │ 运营驾驶舱 │ 跨开发者运行可见 │ 成本 │ 审计 │
│                         ⇅ OTLP / HTTP                         │
├──────────────────────────────────────────────────────────────┤
│  工作台（本地 · 与底座一起运行）                                │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────┐ │
│  │ 交互前端（六大模块）│  │ 运行时（七大能力） │  │ 四层适配     │ │
│  │ · 我的员工        │  │ · 编排引擎        │  │ MCP(工具)   │ │
│  │ · 我的群组        │  │ · 编排驱动        │  │ Hooks(hook) │ │
│  │ · workflow 编排   │  │ · 员工注册发现    │  │ AGENTS.md   │ │
│  │ · 任务看板        │  │ · 工程记忆        │  │ MemoryProxy │ │
│  │ · 底座与环境管理  │  │ · 合规监督        │  │  (记忆注入) │ │
│  │ · 对话界面        │  │ · 本地观测        │  └──────────────┘ │
│  └──────────────────┘  └──────────────────┘                    │
├──────────────────────────────────────────────────────────────┤
│  员工包（独立交付 · 可独立安装/卸载/升级）                      │
│  AGENTS.md + skills/ + hooks/ + mcp.json + orchestration/     │
└──────────────────────────────────────────────────────────────┘
```

**三个不变式**：
1. 一份资产，多底座上岗——员工定义不绑定任何底座
2. 编排引擎是通用底座——不感知具体员工
3. 工程记忆跨员工共享——记忆是运行层能力

**四级使用模型**：
- L0 裸 Agent：直接派发，零依赖
- L1 +Skill：注入方法论
- L2 +SOP：node-table + flow-driver + 引擎
- L3 +跨员工编排：goal 多员工接力

## 4. 待深度调研的难点（按优先级排列）

### 🔴 P0：阻塞 MVP 开发

#### 4.1 CodeBuddy hook 机制真机验证

**问题**：CodeBuddy 基于 CC SDK 构建，预期兼容 CC hooks 规范，但未真机验证。
**影响**：如果 CodeBuddy 不兼容 CC hooks，M2（UPP CodeBuddy 适配）的 hook 层需要重新设计。
**需要做**：
- 在 CodeBuddy 真机环境中放置 hooks.json，触发 PreToolUse/PostToolUse 等事件
- 验证 stdin/stdout JSON 协议是否与 CC 一致
- 验证退出码 0/1/2 语义
- 产出验证报告

#### 4.2 AgentHub API 文档

**问题**：AgentHub 是已有的数字资产平台，但 API 文档未获取。
**影响**：M4（AgentHub skill 拉取）无法开工。
**需要做**：
- 获取 AgentHub 的 skill 列表/搜索/详情/下载 API 文档
- 确认认证方式（token/OAuth）
- 确认 skill 包格式（是否支持 SKILL.md 标准格式）
- 产出 API 对接文档

#### 4.3 manifest + skill schema 正式化

**问题**：manifest schema 和 skill schema 目前只有白皮书中的草案字段，未正式化为 JSON Schema 或 TypeScript 类型。
**影响**：M1（shared-protocol）是所有模块的前置依赖。
**需要做**：
- 将 manifest schema 正式化为 JSON Schema 或 TypeScript 类型定义
- 定义 skill schema（SKILL.md frontmatter 字段 + 约束）
- 定义身份三元组（employee_id / base_identity / operator_id）的格式规范
- 定义 provides/requires 能力声明的枚举值
- 产出 `packages/shared/` 的初始代码

### 🟡 P1：影响 L2+ 设计但不阻塞 MVP

#### 4.4 handoff 协议设计

**问题**：跨员工编排需要 handoff 协议，目前只有 4 种消息类型（delivery_handoff / review_request / review_verdict / human_gate）的概要，未设计具体 schema。
**借鉴源**：FIPA ACL（schema 槽位）+ OpenAI Swarm（handoff 原语）+ LangGraph（checkpointer）+ Matrix 房间模式 + Google A2A（远期适配器）
**需要做**：
- 设计 handoff-message.yml v0.1 schema
- 定义消息路由规则（谁收、谁处理、谁可见）
- 设计 flow-state.json 格式
- 产出 `packages/shared/` 的 handoff schema

#### 4.5 provides/requires 能力路由算法

**问题**：当前 1.0 用硬编码 dispatch_table 做员工路由。2.0 要用 provides/requires 声明式替代，但路由算法未设计。
**需要做**：
- 设计能力匹配算法（provides ⊇ requires 的判定逻辑）
- 设计能力冲突检测（多个员工提供同一能力时的选择策略）
- 设计能力降级路径（某能力不可用时如何降级）
- 产出算法设计文档

#### 4.6 记忆方案：TencentDB SDK 集成方案

**问题**：已决定 TencentDB SDK 为主 + MemOS 设计借鉴，但具体集成方案未设计。
**TencentDB 关键信息**（源码实测）：
- TdaiCore 是 host-neutral facade，只依赖 HostAdapter + LLMRunner 抽象接口
- 我们可以写自己的 EmployeeHostAdapter（4 个方法）
- L2 用 LLM + 文件工具自主管理 .md——与文件基底兼容
- MemoryProxy 已有 CC/CB 集成路径（ANTHROPIC_BASE_URL / OPENAI_BASE_URL 劫持）
**需要做**：
- 设计 EmployeeHostAdapter 的 4 个方法实现
- 设计 L0-L3 蒸馏管线与文件基底的对接方式
- 设计 Skill 提取如何增强我们的 skill_store
- 设计 MemoryProxy 与四层适配的集成方式
- 产出集成方案设计文档

#### 4.7 OTLP 统一事件源设计

**问题**：events.jsonl 用 OTLP span 格式，但具体 span 结构、字段映射未设计。
**需要做**：
- 定义 events.jsonl 的 OTLP span schema（trace_id / parent_span_id / 属性映射）
- 定义关键 span 类型（agent.execution / tool.call / gate.evaluate / human.approval）
- 定义双消费管线的接口（HUD 服务读 → OTLP 推送 / step-recorder 读 → 记忆）
- 产出 OTLP 事件源设计文档

#### 4.8 员工包安装机制（UPP 安装面实现）

**问题**：已确定安装=文件位置映射，但具体 shim 实现未设计。
**需要做**：
- 设计安装流程（扫描底座 → 能力探测 → 文件落位 → 协商报告）
- 设计卸载流程（清理 + 残留检测）
- 设计版本升级流程（diff 安装 vs 全量替换）
- 设计跨底座版本漂移检测
- 产出 UPP 安装面实现设计文档

### 🟢 P2：远期但值得提前调研

#### 4.9 A2A relay 设计

**问题**：管控平台作为 A2A relay 的具体设计（NAT 穿透、消息路由、降级策略）。
**需要做**：调研 A2A 协议规范 → 设计 relay 架构 → 产出设计文档。

#### 4.10 Orkas 借鉴点落地

**问题**：Orkas 有三个值得借鉴的设计，但未做具体落地设计。
**借鉴点**：
- visibility slicing（isVisibleTo 规则：from==me ∨ to∋me ∨ mentions∋me）
- context budget 算术派生（从模型真实 contextWindow 派生，而非写死）
- 多信号反思触发（error_recovery 0.8 + user_correction 0.9 + complexity 0.5 + known_weakness 0.7 + skill_ineffective 0.85 加权）
**需要做**：评估各借鉴点在 2.0 架构中的适用性 → 产出落地设计。

#### 4.11 跨底座版本漂移矩阵

**问题**：同一员工安装到多个底座，版本不一致时如何检测和对齐。
**需要做**：设计漂移检测算法 → 设计一键对齐流程 → 产出设计文档。
