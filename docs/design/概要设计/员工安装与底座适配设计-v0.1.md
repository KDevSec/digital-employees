## 1 定位与范围

### 1.1 定位

**员工包必须安装到底座，否则底座不知道"我是谁"**（白皮书 §5.3，不可推翻）。安装的本质 = **文件位置映射**：把中立 canonical 布局的员工包文件，经每底座薄 shim 转换/落位到该底座期望的位置。安装是四层适配中前三层（MCP / Hooks / AGENTS.md）的物理基础；安装完成后底座自行加载运行，工作台不驻留底座进程（安装 ≠ 运行时依赖）。

### 1.2 范围内

1. 安装流程端到端设计（三入口 → 能力协商 → 落位预览 → 执行 → 安装报告）
2. 底座落位映射：**CodeBuddy / Qoder / Claude Code 写透**（D-007），opencode / Cursor 引用 UPP §6.3 矩阵。**2026-08-23 V0.1 收敛（D-029）：实现 = CodeBuddy CLI + Qoder CLI**，Claude Code -> V0.2；Qoder 落位细节以真机验证（Q-006/B-Q3）为准
3. 底座管理界面（「底座与环境」页，D-001 更名自原型"多宿主"）
4. 安装报告（schema + UI + 降级项文案）
5. 卸载流程（反向清理 + 残留检测 + 卸载报告）
6. 升级安装与版本漂移检测/一键对齐
7. AgentHub（Keyhub）REST 对接契约 + 现状缺口表（D-010）

### 1.3 不做什么

- ❌ MemoryProxy 部署与记忆注入管线 —— 白皮书 §6.2/§9，使用深度 L2+ 阶段任务（本文只在能力协商中给它留 optional 位）
- ❌ 员工包内容的生成规则 —— 文档 A §4
- ❌ 运行状态监控与任务派发 —— 文档 C
- ❌ CC Hooks 各底座实现细节的真机验证本身 —— UPP §8 计划，本文标注验证依赖点

## 2 用户旅程

### 2.1 安装三入口

```
入口①  创建向导生成完成态 →「安装到底座并注册」
入口②  员工市场（管控平台）→「安装」→ 下载已过审签名包 → 进入同一安装向导
入口③  列表页「安装员工」→ 选择本地包目录/tarball（手写路径）→ 校验包结构 → 进入同一安装向导
```

三入口汇合后的统一序列：

```
[0] 包完整性校验（结构/manifest 解析/签名验签——入口②必验，①③提示"本地包未签名"）
[1] 注册到工作台花名册（roster，§4.4）——此刻员工"存在"但"未上岗"
[2] 选择安装目标：底座（可多选）× 作用域（员工驻地/项目工作区，§2.2）
[3] 能力协商（每个目标独立跑，UPP §6.2 算法 → §4.1）
[4] 落位预览：逐文件「源 → 目标 → 动作」清单 + 可达使用深度 + 降级项 + 告警（红黄绿）
[5] 用户确认 → 事务执行（§4.5）→ 逐目标生成安装报告（§4.3）
[6] 回填 manifest.base_identity；上报 AgentCard 注册（平台可达时，异步不阻塞）
[7] 完成态：跳详情页（入口①）或列表页卡片更新底座徽章
```

### 2.2 安装作用域（新增决策 D-013）

| 作用域 | 落位根 | 适用 | 说明 |
|--------|--------|------|------|
| **员工驻地**（默认） | 工作台管理的专属目录 `~/.ieidev-workbench/homes/<employee_id>/` | 直接对话、非项目型任务 | 工作台为每员工建驻地目录，身份文件落此；对话会话以驻地为 cwd 启动底座 |
| **项目工作区** | 用户指定的项目目录 `<workspace>/` | 项目内干活（对话时选工作目录 / flow 任务绑仓库） | 员工"进驻项目"；同一 (底座×工作区) **同时只能有一名当值员工**（身份文件是单一身份源），换人=切换当值（§4.6） |

**身份互斥、能力共存**：AGENTS.md/CLAUDE.md 等身份文件一对一互斥；skills/hooks/mcp 按员工命名空间目录并存，切换当值员工不反复增删能力文件。

### 2.3 卸载旅程

```
详情页「员工包」tab / 列表页卡片 ⋯ 菜单 →「卸载」
  → 选择范围：单底座卸载 / 全部底座卸载 / 卸载并从花名册移除
  → 运行中任务保护检查（flow-state 有 active → 阻止，提示先停任务；可强制但需二次确认）
  → 预览清理清单（按安装报告 placements 反向 + 残留扫描结果）
  → 执行：先解注册（花名册/AgentCard）→ 撤销 merge 类落位 → 删除 copy 类落位 → 扫尾
  → 卸载报告（清理项/跳过项/检出的手工改动）
```

顺序原则（1.0 实证）：**先清引用再删文件**——避免底座 settings 残留断链命令。

### 2.4 升级与漂移对齐旅程

- 升级：市场有新版 / 本地重新生成新版 → 卡片与详情页出现「升级到 vX.Y.Z」→ 升级 = 同目标重装事务（先备份现安装清单 → 新版落位 → 校验 → 删旧版残余），失败自动回滚旧版。
- 漂移：同一员工装在多底座、版本不一致 → 底座与环境页矩阵高亮 → 「一键对齐」= 以选定基准版本（默认最高已过审版本）对落后目标逐个执行升级事务，串行执行、逐个出报告。

## 4 数据模型与核心算法

### 4.1 能力协商（安装时执行，UPP §6.2 细化为可实现形态）

**输入 1：manifest 的 requires/optional**（文档 A §4.3）。requires.capabilities 由向导按下表自动推导：

| 员工包特征 | 推导出的 requires.capabilities |
|-----------|------------------------------|
| 总是 | `agent-def`、`fs-access` |
| skills/ 非空 | `skill-def` |
| runbook 或 node-table | `bash-exec`、`slash-command` |
| node-table 存在 | `subagent-dispatch`（使用深度 L2 门槛） |
| （不由单员工包触发）跨员工编排是工作台 goal/Team 场景 | `goal-command`（使用深度 L3 门槛）只在群组绑定 workflow 时由工作台校验底座，不进单员工 requires |
| hooks/hooks.json 非空 | optional：`event:PreToolUse` 等逐事件列出 |
| mcp.json 非空 | optional：`mcp` |

**输入 2：底座 capability-profile**（`adapters/<base>/capability-profile.yml`，UPP §6.1 格式），关键字段：`open_standards.{agents_md|agent_skills|cc_hooks|mcp}: native|convert|unsupported`、`provides[]`、`unsupported[]`、`base_version_tested`。**探测修正**：安装时以实际探测结果修正 profile 静态声明（B-7"shim 不盲信原生"）——探测不到的能力按 unsupported 处理并记入报告告警。

**算法（伪代码）**

```
negotiate(manifest, profile, probe):
  effective = merge(profile, probe)                 # 探测结果覆盖静态声明
  missing_required = manifest.requires.capabilities
      - (effective.provides ∪ {std 能力 | open_standards[std] ∈ {native, convert}})
  if missing_required ≠ ∅: return 不可安装(missing_required)

  reachable = L0
  if skill-def 可用: reachable = L1
  if {slash-command, bash-exec, fs-access, subagent-dispatch} ⊆ 可用: reachable = L2
  if goal-command 可用: reachable = L3
  reachable = min(reachable, manifest.requires.level)      # 与设计使用深度取小

  placements = 落位计划(manifest.standards, effective.open_standards, scope)   # §4.2
  degraded = [ 降级映射(opt) for opt in manifest.optional if opt ∉ 可用 ]       # UPP §7.2 目录
  warnings = []
  if 任一 blocking hook 事件缺失: warnings += CQO_LA_UNAVAILABLE（显式 WARN，禁止静默）
  if effective.base_version ≠ profile.base_version_tested: warnings += VERSION_DRIFT
  return { reachable, placements, degraded, warnings }
```

### 4.2 落位映射表（核心；scope 记号：`{home}`=员工驻地或项目工作区根）

**通用原则**（吸收 1.0 经验）：
1. **隔离优先**：凡可用命名空间目录（skills/hooks 子目录、插件机制）必用，绝不覆盖用户已有资产；检出非本员工产物一律走冲突流程（备份 `<name>.bak-<ts>` 后才可覆盖）。
2. **幂等**：重复安装同版本 = 校验和比对后跳过（报告标 unchanged）。
3. **两种落位后端**（新增决策 D-014）：`plugin`（复用底座插件机制，1.0 对 CC/CB 实证路线）与 `file`（裸文件落位）。**v0.1 统一采用 file 后端**——原因：员工包是"身份+能力"而非通用插件，身份文件（CLAUDE.md）本就在插件机制之外；单一后端降低首版复杂度；plugin 后端保留为 CC/CB 的后续优化项（B-Q2）。

#### 4.2.4 AGENTS.md → CLAUDE.md / CODEBUDDY.md 转换规则

4. spec 分歧适配位：预留 transform 钩子（如 CC 不支持的 AGENTS.md 特性出现时在此处理），当前为空。

### 4.5 安装事务性

```
① 生成落位计划 → ② 冲突预检（全部落点）→ ③ 写事务日志（计划+每步意图）
→ ④ 逐项执行：copy/convert 先写临时文件再原子 rename；merge 先备份原文件
→ ⑤ 全部成功 → 写安装报告 + 更新花名册/当值登记
→ ✗ 任一失败 → 按事务日志逆序回滚（rename 回退/恢复备份/删除已拷目录）→ 报告 result=rolled-back
```

幂等：重装同版本时逐项比对 checksum，一致则跳过（1.0"幂等可重跑"）。

### 4.6 当值切换（同一 base×workspace 换员工）

```
切换当值(new_employee):
  旧身份文件（带 _ieidev 溯源注释）→ 移回停靠区 installs/parked/<old>@<base>/
  新员工身份文件落位（convert/copy）
  skills/hooks/mcp：命名空间目录并存，无需动
  更新 duty.json；events.jsonl 记 employee.duty_switch span
```

UI：对话界面选工作目录时若目标工作区当值非当前员工 → 提示"该目录当值员工为 X，切换为 Y？"。

### 4.7 卸载数据流

```
输入：安装报告 placements + 残留扫描
① 保护检查：flow-state active？→ 阻止/强制
② 解注册：AgentCard 注销（平台可达时）→ roster 状态改 uninstalling
③ merge 类：按 merge_marker 精确摘除本员工条目（settings.json/mcp.json），无法解析时报"需手工处理"并给 diff
④ copy/convert 类：checksum 一致 → 删除；不一致（用户改过）→ 默认保留 + 报告列"检出手工改动，已保留：<路径>"，可勾选强删
⑤ 残留扫描：按命名空间约定 glob（.{claude,codebuddy,qoder}/**/ieidev-*、*_ieidev 标记、溯源注释文件）→ 列孤儿文件供确认清理
⑥ 卸载报告：cleaned[] / kept[] / manual[]；roster 移除或标"未安装"
```

## 7 边界情况与降级

| 情况 | 行为 |
|------|------|
| 底座未连接就安装 | 目标选择置灰；roster 可先注册（"待安装"态） |
