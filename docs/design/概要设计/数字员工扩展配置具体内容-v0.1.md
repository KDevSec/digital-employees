## 1. 总览：五大类别与配置/开发分界

```
数字员工 = 智能体底座 + 扩展配置

扩展配置
├── 一、身份    🟢 纯配置
├── 二、能力    🟡 配置引用 + 可能需要开发（skill/MCP server）
├── 三、约束    🟡 大部分配置 + 复杂场景需开发
├── 四、流程    🔴 配置 + 开发混合，开发占比最高
└── 五、治理    🟢 纯配置
```

| 维度 | 配置 | 需开发（写 prompt） | 需开发（写代码） |
|------|:----:|:------------------:|:----------------:|
| 身份 | 100% | — | — |
| 能力 | 60%（引用已有） | 新建 skill（`.md` 提示词） | 新建 MCP server |
| 约束 | 70%（声明式规则） | — | 复杂红线 Hook 脚本 |
| 流程 | 30%（runbook/node-table 骨架） | 新建 skill（间接） | Hook 脚本 + Command 实现 |
| 治理 | 100% | — | — |

## 2. 一、身份

### 2.1 字段清单

| 字段 | 类型 | 说明 | 来源 |
|------|------|------|------|
| `agent.name` | string | 员工 ID，唯一标识 | 创建向导 → 手填 |
| `agent.version` | semver | 语义版本号 | 创建向导 → 自动生成 0.1.0 |
| `agent.department` | string | 所属部门 | 创建向导 → 下拉选择 |
| `agent.role` | string | 岗位名称 | 创建向导 → 手填或模板预填 |
| `persona.identity` | text | 主人设身份描述（自然语言） | 创建向导 → 多行文本 |
| `persona.principles` | list | 工作原则列表 | 创建向导 → 多选勾选 + 自定义 |
| `persona.capabilities` | list | 能力描述（自然语言摘要） | 能力配置自动汇总 |
| `persona.usage_modes` | enum[] | 使用深度：裸用 / +方法论 / +流程 / +编排 | 创建向导 → 多选 |
| `persona.constraints` | list | 软约束描述（给 agent 自己读） | 约束配置自动汇总 |

### 2.2 落地路径

```
agent.* + persona.*  →  工作台渲染为 persona 系统提示词 → 注入到每次 agent 会话
```

**全部是底座无关的配置**。manifest 里的身份字段被工作台渲染为一段结构化的系统提示词前缀，附加到每次 agent 调用的 system prompt 中。换底座不影响——提示词注入是工作台运行时做的，不依赖底座特性。

### 2.3 示例

```yaml
agent:
  name: dev-engineer
  version: 1.0.0
  department: 技术研发部
  role: 开发工程师

persona:
  identity: 你是一名资深开发工程师，擅长 Python / TypeScript，遵循 TDD 流程
  principles:
    - 每次改动后必须跑全量测试
    - 代码风格严格遵循团队规范
    - 优先使用现有工具和库，避免重复造轮子
  capabilities: [代码实现与重构, 单元测试编写与执行, Git 分支管理]
  usage_modes: [裸用, +方法论, +流程, +编排]
  constraints: [禁止操作生产环境, 禁止修改 DB schema 未经审批, Token 上限 50K]
```

## 3. 二、能力

### 3.1 字段清单

| 字段 | 类型 | 说明 | 配置 or 开发 |
|------|------|------|:------------:|
| `skills[].name` | string | 能力模块名称 | 配置引用 |
| `skills[].version` | semver | 能力模块版本 | 配置引用 |
| `skills[].source` | enum | 来源：管控平台技能市场 / 本地开发 | 配置 |
| `mcp[].type` | enum | 连接器类型：knowledge-base / tool / datasource | 配置引用 |
| `mcp[].name` | string | 连接器名称 | 配置引用 |
| `mcp[].access` | enum | 访问级别：read / read-write | 配置 |
| `mcp[].endpoint` | url | MCP server 地址（如已部署） | 配置 |

### 3.2 技能市场 → 能力引入流程

```
管控平台 技能市场（AgentHub Skills）
    │
    ├── 浏览已上架 skill（含版本、评分、兼容底座、使用示例）
    ├── 浏览已上架 MCP 连接器（知识库 / 工具 / 数据源）
    │
    ▼
工作台 员工创建向导 Step 3（能力）
    │
    ├── 从技能市场搜索并勾选需要的 skill
    ├── 从技能市场搜索并勾选需要的 MCP 连接器
    │
    ▼
manifest.yml 写入 skills: / mcp: 声明
    │
    ▼
安装时 UPP 适配器
    ├── skill 引用 → 工作台通用能力库加载对应 skill 文件
    ├── MCP 连接器 → 安装 MCP server 依赖 + 配置连接参数
    └── 底座注册 → 底座感知到可用能力（按底座类型翻译）
```

### 3.3 何时需要开发

| 场景 | 动作 | 产出物 |
|------|------|--------|
| 技能市场已有此 skill | 勾选引用即可 | 零开发 |
| 需要新 skill | 创建向导 → 进入 skill 编辑器（写 `.md` 提示词文件） | `agents/<name>.md` |
| 技能市场已有此 MCP 连接器 | 勾选引用 + 填 endpoint | 零开发 |
| 需要新 MCP server | 开发 MCP server（Python/TS 实现协议） | `mcp/<name>/` 目录 |

### 3.4 示例

```yaml
skills:
  - {name: code-impl, version: 1.2.0, source: agenthub}
  - {name: unit-test, version: 1.0.0, source: agenthub}
  - {name: git-ops, version: 0.9.0, source: local}

mcp:
  - {type: knowledge-base, name: 代码规范知识库, access: read, endpoint: http://kb.internal/code-standards}
  - {type: knowledge-base, name: 业务领域知识库, access: read, endpoint: http://kb.internal/domain}
  - {type: tool, name: Git API, access: read-write, endpoint: http://git.internal/api}
```

## 4. 三、约束

### 4.1 字段清单

| 字段 | 类型 | 落地路径 | 配置 or 开发 |
|------|------|----------|:------------:|
| `constraints.red_lines` | list | 路径A: CQO 合规监督 + 路径C: 底座 Hook | 配置（简单）/ 开发（复杂） |
| `constraints.model_tier` | map | 路径B: flow-driver 派发时选模型 | 配置 |
| `constraints.token_quota.per_task` | number | 路径A: 工作台运行时累计 → 超配额拒绝 | 配置 |
| `constraints.token_quota.per_day` | number | 路径A: 同上 | 配置 |
| `constraints.host_restrictions` | list | 路径B: flow-driver 派发前检查底座 | 配置 |

### 4.2 三条落地路径详解

```
            UI 配置（创建向导 Step 4）
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   ┌─────────┐  ┌──────────┐  ┌──────────────┐
   │ 路径 A   │  │  路径 B   │  │    路径 C     │
   │ CQO 合规 │  │ flow-    │  │  UPP 适配器   │
   │ 监督     │  │ driver   │  │  → 底座原生   │
   └────┬────┘  └────┬─────┘  └──────┬───────┘
        │            │              │
        ▼            ▼              ▼
   工作台运行时   编排引擎派发    底座 hook/权限
   拦截 agent   选模型/查配额   硬拦截（双保险）
   操作 → 阻断
```

**路径A：CQO 合规监督（底座无关）**

- 工作台运行时内置的规则引擎
- agent 每次操作前，CQO 匹配红线规则
- 命中 → 阻断并告警 / 升级人工闸
- 不依赖底座，换底座照样生效

**路径B：flow-driver 调度（底座无关）**

- flow-driver 派发子 agent 时读取 tier-map → 选模型
- 累计 token 消耗 → 超配额拒绝派发
- 检查底座是否在 host_restrictions 白名单内

**路径C：UPP 适配器 → 底座原生（底座相关）**

- 安装时，UPP 适配器将红线声明翻译为底座原生 hook 脚本
- 写入底座 hook 目录（如 `.claude/hooks/`）
- **双保险**：CQO 拦截 + 底座硬拦截

### 4.3 权限红线规则库

创建向导提供预置规则库，用户勾选 + 可自定义：

| 规则 ID | 规则描述 | 检查方式 | 干预动作 |
|---------|---------|---------|---------|
| `no-push-to-main` | 禁止直接 push 到 main 分支 | git 操作检测 | 阻断 + 提示 |
| `high-risk-via-gate` | 高风险操作走人工闸 | 操作类型匹配（部署/DB 变更/配置变更） | 升级 gate_pause |
| `no-ieidev-state` | 不改动 .ieidev/ 状态目录 | 路径匹配 | 阻断 |
| `no-external-request` | 禁止外网请求 | 网络调用检测 | 阻断 |
| `no-production-access` | 禁止操作生产环境 | 目标环境匹配 | 阻断 |
| `no-db-schema` | 禁止修改数据库 schema | 操作类型匹配 | 阻断 |
| `custom` | 自定义（自然语言描述） | 语义匹配 | 告警 / 阻断 |

### 4.4 示例

```yaml
constraints:
  red_lines:
    - no-push-to-main
    - high-risk-via-gate
    - no-ieidev-state
    - 禁止写入 /etc/ /opt/production/
    - 禁止调用 deploy-to-prod
    - 禁止访问财务系统 API
  model_tier:
    design: claude-opus-5
    implement: claude-sonnet-5
    query: claude-haiku-4-5
  token_quota:
    per_task: 50000
    per_day: 500000
  host_restrictions:
    - Claude Code
    - opencode
```

## 5. 四、流程

### 5.1 字段清单

| 字段 | 类型 | 落地路径 | 配置 or 开发 |
|------|------|----------|:------------:|
| `runbook.name` | string | persona 注入 | 配置 |
| `runbook.steps[]` | list | persona 注入 | 配置 |
| `runbook.steps[].skill` | string | 引用已有 skill | 配置引用 |
| `node-table` | file ref | flow-driver 编排 | 配置（节点图 YAML） |
| `hooks[]` | list | UPP 适配器 → 底座 hook 目录 | **需要开发** |
| `commands[]` | list | UPP 适配器 → 底座命令注册 | **需要开发** |

### 5.2 runbook（流程档）

**落地方式**：渲染为 persona 系统提示词的一部分，agent 在同一会话内按步骤序列执行。

**UI 配置**：步骤编辑器（添加/删除/排序步骤），每步绑定 skill + 设置自检条件。

**底座无关**：runbook 是纯描述性结构，注入到 persona 提示词中，不依赖任何底座特性。

```
runbook 编辑器（创建向导 Step 5）

┌─────────────────────────────────────────────────────┐
│  TDD 开发流程                          ＋ 添加步骤    │
│                                                     │
│  ① 理解需求与变更范围                                 │
│     skill: [无（纯对话）      ▼]  自检: [确认理解无误] │
│                                                     │
│  ② 编写失败测试                                      │
│     skill: [unit-test ▼]           自检: [红灯]      │
│                                                     │
│  ③ 最小实现使测试通过                                │
│     skill: [code-impl ▼]           自检: [绿灯]      │
│                                                     │
│  ④ 重构优化                                         │
│     skill: [code-impl ▼]           自检: [测试全绿]   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 5.3 node-table（编排档）

**落地方式**：flow-driver 读取 YAML → 驱动独立会话链 → gate 判定流转。

**UI 配置**：Canvas/Script 双视图编辑器，拖拽节点 + 连线 + 配置 gate 条件。

**底座无关**：node-table 是编排引擎的输入，flow-driver 是工作台运行时的一部分。

详见原型图 [workbench.html](prototype/workbench.html) P2 workflow 编排。

### 5.4 Hook（底座相关，需开发）

**落地方式**：UPP 适配器将 Hook 声明 → 翻译为底座原生 hook 脚本 → 写入底座 hook 目录。

**UI 配置**：Hook 配置表单 + 代码编辑器。

```
Hook 配置（创建向导 Step 5 高级）

┌─────────────────────────────────────────────────────┐
│  Hook 名称: [check-commit-author              ]      │
│  触发事件: [git pre-commit              ▼]           │
│  目标底座: [Claude Code ▼] [opencode ▼]              │
│                                                     │
│  脚本:                                               │
│  ┌─────────────────────────────────────────────┐    │
│  │ #!/bin/bash                                  │    │
│  │ # 检查 commit author 符合署名规范              │    │
│  │ author=$(git log -1 --format='%an %ae')      │    │
│  │ if [[ ! "$author" =~ ^(ly|ly-AI) ]]; then    │    │
│  │   echo "ERROR: 署名不符合规范"                 │    │
│  │   exit 1                                     │    │
│  │ fi                                           │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  底座模板:  [Claude Code hook ▼]  自动翻译            │
│  说明: 从底座模板库选择，自动处理路径/参数/退出码约定    │
└─────────────────────────────────────────────────────┘
```

### 5.5 Command（底座相关，需开发）

**落地方式**：UPP 适配器将 Command 声明 → 翻译为底座命令 → 注册为底座可调用命令。

**UI 配置**：命令定义表单 + 代码编辑器。

```
Command 配置（创建向导 Step 5 高级）

┌─────────────────────────────────────────────────────┐
│  命令名: [deploy-check                        ]      │
│  描述:   [部署前检查（测试+安全扫描+审批状态）  ]      │
│  目标底座: [Claude Code ▼] [opencode ▼]              │
│                                                     │
│  实现:                                               │
│  ┌─────────────────────────────────────────────┐    │
│  │ #!/usr/bin/env python3                       │    │
│  │ import subprocess, sys                       │    │
│  │ # 1. 跑全量测试                               │    │
│  │ # 2. 安全扫描                                 │    │
│  │ # 3. 检查审批状态                             │    │
│  │ # 返回 0=通过, 非0=拦截                       │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  底座模板:  [Claude Code slash command ▼]            │
│  说明: Claude Code 注册为 /deploy-check 斜杠命令      │
└─────────────────────────────────────────────────────┘
```

### 5.6 示例

```yaml
# runbook（底座无关）
runbook:
  name: TDD 开发流程
  steps:
    - {step: 1, action: 理解需求与变更范围, self_check: 确认理解无误}
    - {step: 2, action: 编写失败测试, skill: unit-test, self_check: 红灯}
    - {step: 3, action: 最小实现使测试通过, skill: code-impl, self_check: 绿灯}
    - {step: 4, action: 重构优化, skill: code-impl, self_check: 测试全绿 + 质量达标}

# node-table（底座无关，引用独立文件）
node_table: orchestration/dev-flow.node-table.yml

# hooks（底座相关，需开发）
hooks:
  - name: check-commit-author
    trigger: git-pre-commit
    script: hooks/check-author.sh
    targets: [Claude Code, opencode]
  - name: validate-manifest
    trigger: pre-install
    script: hooks/validate-manifest.py
    targets: [Claude Code, opencode, CodeBuddy]

# commands（底座相关，需开发）
commands:
  - name: deploy-check
    description: 部署前检查（测试+安全扫描+审批状态）
    script: commands/deploy-check.py
    register_as:
      Claude Code: slash-command
      opencode: custom-command
```

## 6. 五、治理

### 6.1 字段清单

| 字段 | 类型 | 说明 | 来源 |
|------|------|------|------|
| `governance.level` | enum | L1 公司级 / L2 部门级 / L3 团队级 / L4 个人级 | 创建向导 → 单选 |
| `governance.approval` | enum | 公司审批 / 部门审批 / 团队自审 / 无审批 | 随 level 自动推荐 |
| `governance.visibility` | enum | 仅自己 / 团队内 / 部门内 / 全公司 | 创建向导 → 下拉 |
| `governance.audit` | enum | 全量记录 / 仅异常记录 / 可关闭 | 创建向导 → 下拉 |
| `governance.lifecycle_owner` | string | 生命周期负责人 | 创建向导 → 手填 |

### 6.2 治理分级与字段默认值

| 级别 | 审批 | 可见范围 | 审计 | 典型场景 |
|------|------|---------|------|---------|
| **L1 公司级** | 公司审批 | 全公司 | 全量记录 | 跨领域通用模板（如"Git 操作规范"） |
| **L2 部门级** | 部门审批 | 部门内 | 全量记录 | 部门通用岗位模板（如"前端开发工程师"） |
| **L3 团队级** | 团队自审 | 团队内 | 仅异常记录 | 团队内复用模板 |
| **L4 个人级** | 无审批 | 仅自己 | 可关闭 | 个人自定义，鼓励试错 |

### 6.3 落地路径

```
governance.*  →  管控平台（远端）
                  ├── 审批流：员工上传到 AgentHub → 按 level 路由审批
                  ├── 可见性：管控平台员工市场按 visibility 过滤
                  ├── 审计：工作台上报 OTLP → 管控平台按 audit 级别存储
                  └── 生命周期：管控平台按 lifecycle_owner 管理升级/废弃
```

**全部是配置**。治理字段不在工作台运行时生效，而是**上报到管控平台**，由管控平台执行审批流、可见性过滤、审计存储。

### 6.4 示例

```yaml
governance:
  level: L2
  approval: 部门审批
  visibility: 部门内
  audit: 全量记录
  lifecycle_owner: 技术研发部
```

## 7. 附录：UPP 适配器翻译表

### 7.1 约束 → 底座翻译

| manifest 声明 | Claude Code | opencode | CodeBuddy |
|:---|:---|:---|:---|
| `red_lines: no-push-to-main` | `.claude/hooks/pre-commit` bash 脚本 | `.opencode/hooks/pre-commit` | CodeBuddy 权限规则 |
| `red_lines: high-risk-via-gate` | 工作台 gate_pause（底座无关） | 同左 | 同左 |
| `model_tier: design: opus` | `--model claude-opus-5` | `--model opus` | `model: claude-opus-5` |
| `token_quota: per_task: 50000` | 工作台运行时累计（底座无关） | 同左 | 同左 |

### 7.2 Hook → 底座翻译
