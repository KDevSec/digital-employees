## 1 一条链路（谁干什么）

```
上架：管理员/员工属主 → 上传 zip → 平台校验（§4）→ blob 保存 + 索引（§3）
分发：终端请求 → 平台返回 zip + sha256（§5）
消费：终端校验 → 解包 → schema 校验 → 落员工库 ~/.devzero/employees/ → 可安装（终端侧已就绪，零改动）
```

平台侧职责边界：**保存、索引、分发**（§2~§5）。解包落库与安装归终端侧（§6，我方已实现）。

## 2 分发包格式（zip 容器规范）

### 2.1 包结构

```
<employee-id>-<version>.zip
└── <employee-id>/                  # ★ 单根目录 = manifest.id（zip-slip 天然约束 + 解包干净）
    ├── manifest.yml                # 八类 v0.2（元数据 10 项/八件套 1+7/管理面 3 段）——唯一元数据真源
    ├── AGENTS.md                   # 身份指令（六段式渲染产物）
    ├── skills/<slug>/              # skill 素材（SKILL.md + 副文件，与 manifest.skills 清单一致）
    ├── hooks/                      # hooks.json（编译产物）+ redlines/（脚本本体）
    ├── orchestration/              # 仅 flow-owner 员工（个人 SOP 表）
    ├── commands/  knowledge/       # 可选（有则带，空目录可省）
```

### 2.2 打包规则（上架时平台侧校验，MUST 级）

| 规则 | 说明 |
|---|---|
| 单根目录 | zip 顶层**只有一个**目录且名 = manifest.id——多根/顶层散文件一律拒收 |
| 文本编码 | 一律 UTF-8 无 BOM（GBK 文件名/内容是已知坑，终端侧已按此假设解包） |
| 路径安全 | 条目路径不得含 `..`/绝对路径/盘符前缀（zip-slip 防护，解包侧亦有二次校验） |
| 禁含运行时物 | `.venv/`、`node_modules/`、`.git/`、`*.log`、点开头文件一律不得入包（例：sec-code 员工的 Python `.venv` 由终端装到员工 home，不进包——既定规则） |
| 大小上限 | 建议 ≤ 50MB/包（skill 素材为主；超出走人工审核通道） |

## 3 服务端保存模型

**blob 原样保存 + manifest 派生索引**——平台不拆包改写、不维护第二份元数据：

| 层 | 内容 |
|---|---|
| blob 存储 | zip 字节流原样（存储键建议：`employees/<id>/<version>.zip` 或内容寻址） |
| 索引行（DB） | 上传时从 manifest.yml 解析派生：`id / display / brief / avatar / version / upp_version / kind / requires.level / tier / skills[]（name+version 摘要）/ operator / 上传者 / 上传时间 / sha256 / size_bytes` |
| 版本语义 | 同 id 多 version 并存；市场列表默认展示最新 semver，历史版本可下；**同 (id, version) 重复上传 = 拒绝（不可变，改内容必须 bump version）** |

> 索引是派生物不是真源：市场卡片/检索全部字段以索引为准，但索引的来源永远是从包内 manifest 解析——平台侧不提供「改元数据」的编辑面（改 = 重新上架新版本）。

## 4 上架校验清单（平台侧把关，按序执行，任一失败拒收并返回结构化错误）

1. **zip 结构**：§2.2 全部规则（单根/编码/路径安全/禁含物/大小）
2. **manifest schema 校验**：`manifest.yml` 必须通过 **shared-protocol v0.2 的 zod schema**（八类结构、跨字段校验：`+编排` → level=L2 且个人表必填；kind=callee 禁 orchestration；skills name 不重复；connectors stdio→command 必填、http→url 必填等）
   - 实现提示：schema 真源是 TS 包 `workbench/shared-protocol/`（零运行时依赖，除 zod）。平台 backend 是 Python/FastAPI——两个选项：①平台内用 Pydantic 复刻一份同构 schema（**必须**与 TS 真源同步演进，建议 CI 里用 TS 包跑双方 fixture 对照测试防漂移）；②上架校验走一个轻量 TS 校验服务。**推荐 ①+对照测试**（运维简单），漂移防护是硬要求
3. **三方互证**：manifest.skills ↔ `skills/` 目录实物一致；声明 `compiled: true` 的红线 → `hooks/hooks.json` 必须存在
4. **sha256 计算**：校验通过后计算 zip 整体 sha256 入索引

## 5 分发 API 面（终端 → 平台，REST）

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/market/employees` | GET | 列表（索引查询；分页 + 按 display/id/kind/level 检索；含最新版本摘要） |
| `/api/market/employees/{id}` | GET | 详情（指定 id 的全部版本列表 + 当前最新版完整索引行） |
| `/api/market/employees/{id}/download` | GET | 下载 zip（`?version=` 缺省最新；`Content-Type: application/zip`；**响应头 `X-Package-Sha256` 携带 sha256**，终端做完整性校验） |

鉴权与部署边界沿用平台既有体系（平台 V0.1 的认证/网关模式，平台团队自行对接）；具体路径前缀/版本号风格按平台 API 惯例调整，**契约不变量只有三个**：zip 按 §2 格式、sha256 响应头、manifest 是包内唯一元数据源。

## 6 终端侧消费链路（我方已就绪，此处仅供平台理解全链）

下载 zip → sha256 校验 → 解包（zip-slip/GBK 二次防护）→ manifestSchema 校验（终端侧 shared-protocol 直用，与平台校验同一真源）→ 落员工库 `~/.devzero/employees/<id>/` → **安装零登记**（安装域实时查员工库，任何新落库员工即刻可装到 CC/CB/Qoder 三底座）。同 id 员工已存在时按员工库快照语义提示（升级 = 新 version 落库并存）。

## 7 兼容与演进

- `manifest.upp_version`（当前 `2.1`）是格式版本判据：终端遇到不认识的 upp_version → 明确报「包格式版本不支持」而非静默失败
- 本契约 v0.1 的演进（如加签名/审核状态流/依赖声明）走版本化修订；**不破坏 zip 容器与 manifest 真源两条不变量**
- 员工包内结构规范由 shared-protocol 独立演进（八类 schema 迭代），平台侧只需跟随 schema 校验规则更新——这就是 §4 选项 ① 对照测试的意义

## 8 坑位备忘（终端侧已踩过的，平台侧可提前防）

| 坑 | 防法 |
|---|---|
| zip 内 GBK 文件名/内容乱码 | 上架即拒非 UTF-8（§2.2）；下载侧按 UTF-8 解 |
| zip-slip 路径穿越 | 双侧都校验（平台 §4、终端 §6） |
| 大 zip 解压炸弹 | 平台侧限 50MB；终端侧解压前校验条目数与总大小上限 |
| `.venv` 类运行时物混入 | §2.2 禁含物清单 |
| skill 素材版权 | 上架人工审核通道关注 `vendored_from`/`license` 字段（manifest skill 条目已带） |
