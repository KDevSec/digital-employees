## §1 从 1.0 到 2.0

### 1.1 一句话

**把一支 AI 研发团队从"一个全家桶插件"升级为"工作台（运行层）+ 员工包 + 管控平台"三层分离的全新架构。**

### 1.2 1.0 的成就与局限

1.0 版本验证了核心命题：5 角色数字员工集群端到端交付、三层编排引擎（R1 状态机 / R2 节点图 / R3 gate）、四底座全量适配、工程记忆底座、2814 自动化测试全绿。

但 1.0 是**单体架构**——所有东西绑在一个插件里，员工不能独立安装/卸载，编排能力和员工能力混在同一层，观测是事后产物。

### 1.3 2.0 的核心主张

2.0 是**全新架构**，不是 1.0 的增量改进：

| 维度 | 1.0 | 2.0 |
|------|-----|-----|
| 架构 | 单体插件 | 三层分离（工作台 + 员工包 + 管控平台） |
| 员工形态 | 多 Agent 主从结构 | **单 Agent + 多 Skill** |
| 员工独立安装 | ❌ 散落 4 个目录 | ✅ 独立包 |
| 编排引擎 | 和员工能力混在一起 | 通用底座 |
| 观测 | 事后产物 | OTLP 统一事件源 |
| 多底座 | 自研中性协议 | 开放标准薄封装（CC hooks 事实标准） |
| 管控平台 | 无 | 远端 Web |
| 记忆 | 文件基底（人工归纳） | 文件基底 + TencentDB SDK 增强（自动蒸馏） |

> 1.0 的产品名、代码路径、skill 名等旧品牌已从正文移除。1.0 → 2.0 的命名迁移见附录 A。

```
└──────────────────────────────────────────────────────────────┘
```

### 2.2 三个不变式

1. **一份资产，多底座上岗**：员工定义不绑定任何底座，通过四层适配在多底座上运行
2. **编排引擎是通用底座**：不感知具体员工，只提供状态机 + 节点图 + gate 判定
3. **工程记忆跨员工共享**：记忆是运行层能力，所有员工共用

### 2.3 三层职责边界

| 层 | 负责 | 不负责 |
|----|------|--------|
| **工作台** | 编排引擎/编排驱动/员工注册/通用能力/合规监督/多底座适配/工程记忆 + 交互前端 + 员工安装上下传 + 本地观测 | 不含具体员工定义、不含员工专属 skill/node-table |
| **员工包** | AGENTS.md / skills / node-table / hooks / mcp.json / 评审标准 | 不含编排引擎/编排驱动/跨员工调度 |
| **管控平台** | 员工市场 / 跨开发者运行可见 / 成本 / 审计 / 运营 / 远端观测 | 不干预员工运行时 |

## §3 数字员工

### 3.1 定义

**数字员工 = 智能体底座 + 扩展配置**，作为人的分身，只具备决策之外的执行能力。

### 3.2 单 Agent + 多 Skill 形态

2.0 员工 = **一个 Agent**（AGENTS.md 定义完整身份）+ **多个 Skill**（SKILL.md，按需加载）。

- Skill 调用时开独立会话（subagent dispatch），避免上下文污染
- **编排对象无关性**：引擎不区分 node-table 中的节点是 skill 还是员工——支持单员工 skill 链、多员工接力、混合编排
- 不再有"能力 agent .md"子文件（1.0 多 Agent 主从结构已废弃）

### 3.3 五大类别

| 类别 | 回答 | 包含内容 |
|------|------|---------|
| **身份** | 员工是谁 | AGENTS.md（主 Agent 定义）、岗位名、角色、部门、版本 |
| **能力** | 员工会什么 | Skill（可跨员工复用、独立版本管理）、MCP 连接器 |
| **约束** | 员工不能干什么 | 权限红线、模型档位、Token 配额、安全规范 |
| **流程** | 员工怎么干活 | runbook（流程档）、node-table（编排档）、Hook、Command |
| **治理** | 谁管、谁能看 | 审批要求、可见范围、审计级别、生命周期管理 |

### 3.4 渐进增强：四级使用模型

| Level | 叠加 | 依赖 | 适用 |
|-------|------|------|------|
| **L0 裸 Agent** | 主 Agent 直接派发 | 0（底座自带 Agent 派发） | 单次任务 |
| **L1 +Skill** | 注入方法论 | 员工包 skill 文件 | 专业任务 |
| **L2 +SOP** | node-table + flow-driver + 引擎 | 编排引擎 | 完整流程 |
| **L3 +跨员工编排** | goal 多员工接力 | 引擎 + flow-driver + goal | 端到端交付链 |

**关键**：L0/L1 不需要编排引擎——单个员工直接被底座加载执行。

### 3.5 Team 定义

| 形态 | 说明 |
|------|------|
| **群组** | 人的协作空间：拉多个员工进组，绑定 workflow 模板，@ 员工发起任务 |
| **编排 Team** | flow-driver 按 node-table 自动接力，人只在人工闸停靠确认 |

### 3.6 治理分级 L1-L4

| 级别 | 审批 | 可见范围 | 审计 |
|------|------|---------|------|
| L1 公司级 | 公司审批 | 全公司 | 全量 |
| L2 部门级 | 部门审批 | 部门内 | 全量 |
| L3 团队级 | 团队自审 | 团队内 | 仅异常 |
| L4 个人级 | 无审批 | 仅自己 | 可关闭 |

### 4.3 OTLP 统一事件源

引擎只写一次 events.jsonl（**OTLP span 格式**），双消费：

```
events.jsonl（OTLP span 格式）
  ├── HUD 服务读 → 推 OTLP → Honeycomb（观测管线）
  └── step-recorder 读 → 抽 key_facts → 写记忆（记忆管线）
```

- `trace_id` 贯穿 + `parent_span_id` 因果链 + OTel GenAI 标准属性
- **不破坏文件基底**：仍然是 JSONL 文件，人类可 cat / grep / jq

- `npm install @digital-employee/workbench` 或 IDE 插件市场安装
- 启动后访问 `localhost:19820` 进入交互前端

### 5.3 安装与分发

**员工包必须安装到智能体底座，否则底座不知道"我是谁"。**

每个底座的 Agent 启动时，必须有一个"我是谁"的身份源——CC 读 CLAUDE.md，CB 读 CODEBUDDY.md，opencode/Cursor 读 AGENTS.md。这是底座的原生加载机制，不可绕过。

```
安装的本质 = 文件位置映射（每底座一个薄 shim 做路径转换）

员工包源（中立 canonical）         安装后（底座认识的位置）
──────────────────────────────────────────────────────────
AGENTS.md         →  CC: CLAUDE.md（薄 shim 改名）
                     CB: CODEBUDDY.md
                     Qoder: AGENTS.md（原生读取）
                     Cursor: AGENTS.md（原生读取）
                     opencode: AGENTS.md（原生读取）
skills/SKILL.md   →  底座 skill 目录
hooks/hooks.json  →  底座 hooks 配置目录
mcp.json          →  底座 MCP 配置目录
```

**为什么不能不安装？** 不安装只有两条路，都有根本缺陷：

| 方案 | 做法 | 问题 |
|------|------|------|
| CLI 注入 | `claude --system-prompt "$(cat AGENTS.md)"` | ① 绕过了底座的指令加载机制，不确定所有底座都支持 CLI 注入；② MCP/hooks 连接器无法通过 CLI 参数注册；③ 每次启动都要拼参数，脆弱 |
| API 注入 | MemoryProxy 层注入 AGENTS.md 到 system prompt | ① 只能注入指令，管不了 MCP 工具注册和 hooks 拦截；② 这是"假扮"员工，不是"是"员工——底座不知道自己加载了员工身份 |

**安装不是运行时依赖**：安装后，底座自己加载、自己运行，工作台不需要驻留在底座进程里。这就是 L0/L1 的完整形态——安装一次，底座就是员工，用户直接对话。

**四层适配的物理基础**：MemoryProxy（第四层）只能注入记忆，不能替代前三层（MCP 工具注册 + Hooks 拦截 + AGENTS.md 身份加载）。安装是前三层得以生效的前提——没有安装，四层适配缺了三层。

```
获取（⬇）：管控平台下载 / 创建向导生成 / 手写 — 三路径完全同构
发布（⬆）：工作台 → AgentHub 审核 → 管控平台上架 → 各团队下载
```

## §6 多底座适配（四层正交）

### 6.1 四层适配架构

> v0.7 决策：适配形态从"待定"改为已决策。调研结论——不存在单一适配形态覆盖全部能力面，四层正交不冲突。
>
> **物理基础**：四层适配的前提是**员工包已安装到底座**（§5.3）。前三层（MCP + Hooks + AGENTS.md）依赖底座原生加载机制，只有安装后底座才能"认识"这些文件；MemoryProxy 作为第四层只负责记忆注入，不能替代前三层的工具注册和 hook 拦截。

| 层 | 开放标准 | 管什么 | 底座原生支持 | shim 工作量 |
|----|---------|--------|------------|-----------|
| **工具层** | MCP（mcp.json） | Agent 怎么调工具 | CC/CB/Qoder/Cursor/opencode 全原生 | 零（格式标准一致，仅文件位置不同） |
| **Hook 层** | CC Hooks（hooks.json） | 工具调用拦截 + 会话生命周期 | CC/Cursor 原生；opencode 概念等价需 shim | CC/Cursor 零；opencode 需翻译层 |
| **指令层** | AGENTS.md | Agent 身份 + 指令 | opencode/Codex/Cursor 原生读 | CC 需转 CLAUDE.md（薄 shim） |
| **记忆注入层** | MemoryProxy | LLM 请求前注入记忆/上下文 | 任何支持 ANTHROPIC_BASE_URL 的底座 | 零（API 劫持，不修改底座） |

### 6.2 MemoryProxy（第四层适配）

> 源码实证：[TencentDB vs MemOS 对比 §5](TencentDB-vs-MemOS深度对比-源码级-2026-08-13.md)

MemoryProxy 是 **API base URL 劫持代理**——不修改底座，只劫持 LLM API 请求注入记忆：

```
Claude Code → ANTHROPIC_BASE_URL=http://proxy:8096/claude-code/ → MemoryProxy → 真实 LLM API
CodeBuddy   → OPENAI_BASE_URL=http://proxy:8096/codebuddy/     → MemoryProxy → 真实 LLM API

MemoryProxy 每轮做：
  1. 解析请求 → 提取用户消息
  2. 召回 L1 记忆 → 注入到用户消息前（prependContext，每轮变化）
  3. 注入 L2/L3 记忆 + Skill 列表 → 系统提示（appendSystemContext，prompt cache 命中）
  4. 转发到真实 LLM API
  5. 响应 tap → 提取 usage → 写 L0 → 触发 L1 蒸馏 → 触发 Skill 提取
```

**关键设计**：session 稳定内容用 `session_init` 缓存策略（prewarm 一次，保留 prompt cache）；每轮变化内容用 `none` 策略（只注入用户消息，不碰系统提示 cache 前缀）。

**适用场景**：无 hook 底座的记忆注入补充；或任何需要记忆增强的底座。不覆盖 hook 层拦截（CQO L-a 仍需底座 hooks）。

### 6.3 CC hooks 是事实标准

- **Cursor 官方兼容 CC hooks**："matches Claude Code behavior for compatibility"
- CC hooks 事件名 + stdin/stdout JSON + 退出码 0/1/2 是跨底座标准

### 6.4 底座梯队

| 梯队 | 底座 | 工具层 | Hook 层 | 指令层 | MemoryProxy |
|------|------|--------|--------|--------|-------------|
| P0 | Claude Code | ✅ 零 | ✅ 零 | 需转 CLAUDE.md | ✅（ANTHROPIC_BASE_URL） |
| P0 | CodeBuddy | ✅ 零 | 大概率兼容（基于 CC SDK） | 需验证 | ✅（OPENAI_BASE_URL） |
| P0 | Qoder | ✅ 零 | ✅ 原生 CC Hooks | 需验证 | ✅ |
| P1 | Cursor | ✅ 零 | ✅ 官方兼容 | ✅ 原生 | ✅ |
| P1 | opencode | ✅ 零 | 需 shim（命名转换） | ✅ 原生 | ✅ |

> CodeBuddy 的 hook 兼容性需真机验证（基于 CC SDK，预期兼容）。

## §7 管控平台（远端）

> 参照原型 [management.html](prototype/management.html)

### 7.1 五阶段主线

```
① 定义 → ② 运行 → ③ 发现 → ④ 协同 → ⑤ 效能
```

### 7.2 五大模块

| 模块 | 职责 |
|------|------|
| **员工市场** | AgentHub 审核 + 包托管 + 下载 API + 签名校验 |
| **运行可见** | 跨开发者状态聚合 + active flow 追踪 |
| **成本中心** | Token 消耗追踪 + 按员工/任务/团队归集 |
| **审计中心** | 工具调用审计 + 两档脱敏 |
| **运营驾驶舱** | DAU + gate 通过率 + CQO 告警 + 趋势图 |

### 7.3 衔接点

- 工作台 → 平台：员工上架 / 运行数据上报（OTLP 不可关闭）/ AgentCard 注册
- 平台 → 工作台：员工下载安装

### 7.4 A2A Relay（Phase 3）

管控平台在 A2A 通信层 = "公网 relay + 治理层"——NAT 后双方 A2A 直连不可能时做中继。

## §8 通信架构

### 8.1 五层通信

```
Layer 0：同机器 → 文件 handoff（零网络）
Layer 1：同网络 → A2A 直连（P2P，工作台互发 Agent Card）
Layer 2：跨网络 NAT 后 → 管控平台 relay
Layer 3：外部 Agent 接入 → A2A 适配器
Layer 4：跨组织联邦 → Matrix federation
```

### 8.2 关键原则

1. 消息格式始终是 handoff-message.yml——无论哪层，schema 不变
2. A2A 不在员工层，在工作台层——员工是配置文件，工作台是运行进程
3. 管控平台从"消息 broker"降级为"relay + 治理"

### 8.3 handoff 协议（4 种消息类型）

| 类型 | 说明 |
|------|------|
| `delivery_handoff` | 员工 A → 员工 B（交付接力） |
| `review_request` | gate 发函评审员工 |
| `review_verdict` | 评审员工回函 |
| `human_gate` | 人工闸停靠 |

借鉴源（多源混合，非兼容）：FIPA ACL（schema 槽位）+ OpenAI Swarm（handoff 原语）+ LangGraph（checkpointer）+ Matrix 房间模式 + Google A2A（远期适配器）。

### 9.2 为什么选 TencentDB 为主 + MemOS 为辅

> 源码级对比：[TencentDB vs MemOS 深度对比](TencentDB-vs-MemOS深度对比-源码级-2026-08-13.md)

| 维度 | TencentDB | MemOS | 选择 |
|------|-----------|-------|------|
| 语言 | TypeScript | Python + TypeScript | **TencentDB**——与工作台 TS 一致 |
| L0-L3 管线 | ✅ 四层全实现（源码实证） | ✅ 三层 + 奖励 + 反馈 | TencentDB 管线更实用；MemOS 奖励/反馈更先进 |
| Claude Code 集成 | ✅ MemoryProxy（API 劫持） | ❌ 无 | **TencentDB** |
| OTLP | ✅ 原生（@opentelemetry/*） | 未确认 | **TencentDB** |
| 奖励系统 | ❌ | ✅ R_human + V_t 反向传播 | **MemOS 借鉴** |
| 反馈修正 | ❌ | ✅ 分类器+修正器 | **MemOS 借鉴** |
| Skill 验证器 | ❌ | ✅ tool coverage + resonance | **MemOS 借鉴** |
| 纯文件后端 | ❌ 强依赖 SQLite | ❌ 强依赖 SQLite | 都不能替代文件基底 |

### 9.3 TencentDB Agent Memory 源码实证

> 源码位置：`references/tencentdb-agent-memory/`

**基本信息**（源码直读，非 WebFetch）：

| 维度 | 实证 |
|------|------|
| 包名 | `@tencentdb-agent-memory/memory-tencentdb-v2` v2.0.0-beta.1 |
| License | MIT |
| 语言 | TypeScript（Node.js >= 22.16） |
| 存储 | SQLite + sqlite-vec（本地）；TencentDB VectorDB（可选云）；Redis/ClickHouse/MongoDB（可选） |
| OTLP | ✅ 原生（package.json 依赖 @opentelemetry/*） |
| 本地部署 | ✅ Docker 三容器（memory-core + memory-hub + proxy），SQLite-only 模式不需要 Redis/ClickHouse |

**L0-L3 管线**（源码文件实证）：

| 层 | 源码文件 | 职责 |
|----|---------|------|
| L0 | `MemoryCore/src/core/conversation/l0-recorder.ts` | 原始对话记录 |
| L1 | `MemoryCore/src/core/prompts/l1-extraction.ts` + `l1-dedup.ts` | 原子事实提取 + 去重 |
| L2 | `MemoryCore/src/core/prompts/scene-extraction.ts` + `scene/` | 场景知识（LLM 用文件工具自主管理 .md） |
| L3 | `MemoryCore/src/core/prompts/persona-generation.ts` + `persona/` | 用户画像 |
| Skill | `MemoryCore/src/core/skill/`（skill-core/extractor/versioning/store） | 从对话提取可复用工作流 |

**核心 facade**：`MemoryCore/src/core/tdai-core.ts` — TdaiCore 是 host-neutral facade，只依赖 `HostAdapter` + `LLMRunner` 抽象接口。我们可以写自己的 HostAdapter 来集成。

**SDK**（源码实证）：
- TypeScript SDK：`@tencentdb-agent-memory/memory-sdk-ts-v2`，105 个 API 端点
- Python SDK：`tencentdb-agent-memory-sdk-python`，同步+异步
- 可不经过 MemoryProxy 直接用 SDK 集成

**MemoryProxy**（源码实证）：
- Hono HTTP 服务器，劫持 ANTHROPIC_BASE_URL / OPENAI_BASE_URL
- CC 配置：`ANTHROPIC_BASE_URL=http://proxy:8096/claude-code/<spaceId>`
- CB 配置：`OPENAI_BASE_URL=http://proxy:8096/codebuddy/<spaceId>`
- 每轮：召回 L1 → 注入用户消息前；注入 L2/L3 + Skill → 系统提示；转发；响应 tap → 写 L0 → 触发蒸馏

### 9.4 MemOS 借鉴点

> 源码位置：`references/MemOS/`

| 借鉴点 | MemOS 源码 | 我们的轻量实现 |
|--------|-----------|--------------|
| priority 衰减 | `apps/memos-local-plugin/core/reward/` | Step frontmatter 派生 priority 字段（纯计算零依赖） |
| R_human 三轴评分 | `apps/memos-local-plugin/core/reward/` | Step 评分维度增强 |
| gain 评估 | `apps/memos-local-plugin/core/memory/l2/` | Step self_eval_score 归一化 |
| skill 验证器 | `apps/memos-local-plugin/core/skill/` | skill_store 质量门 |
| feedback 修正 | `apps/memos-local-plugin/core/feedback/` | F-NNN 反馈落地追踪 |

**不采用**：SQLite/Neo4j/Qdrant（破坏文件基底）、Python 双语言（工作台是 TS）、LLM 全自动归纳（人工归纳为底线）。

### 9.5 OTLP 统一事件源

events.jsonl 用 OTLP span 格式（§4.3），记忆和观测共享同一事件源。TencentDB 原生支持 OTLP（package.json 含 @opentelemetry/*），印证方向正确。
