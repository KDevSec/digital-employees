## 2 冲突与对齐建议（新建员工侧，按建议裁决优先级排）

> 编号 DC-01~09（demo-collab 专用前缀，不与 PR-/R- 撞号）。每条：demo 事实 → 2.0 现状 → 建议。

### DC-01 🔴｜Command 类进不进 schema/向导——demo 已把它变成领导见过的一等公民

- **demo**：Command 是 8 类扩展之一（候选 /daily-report、/handoff、/self-review），预览树有 `commands/` 目录；1.0 真实包结构（UPP §2 源布局）也有 `commands/`（flow-driver.md 等 slash commands）。
- **2.0**：manifest schema 无 `commands` 字段；[员工新建设计 §4.1](概要设计/员工新建设计-v0.1.md) 生成管线 ①-⑧ 无 commands 步骤——即 PR-004 指出的「UPP v2 骨架字段未落」。
- **建议**：a) schema 补 `commands`（对齐 UPP 骨架，向导 V0.1 不做 UI，包结构预留——内置 team 预置包可自带）；b) 完全不做留 V0.2；c) 向导加五轻式 chip 区。**推荐 a**：成本一个字段，消除与 UPP/demo 双重脱钩。

### DC-02 🔴｜MCP 连接器必须有 sse/url 型——demo 卡面带传输徽章

- **demo**：MCP_CATALOG 7 个 server，其中「内部数据平台」「工单系统」是 **sse 传输**，卡面渲染传输徽章。
- **2.0**：[shared-protocol §2.2](详细设计/shared-protocol详细设计-v0.1.md) connectors 只有 `{name, command, env, access}`——无 url 型、无 args（= 预审 PR-005）；而 [员工新建设计 §4.7](概要设计/员工新建设计-v0.1.md) 的 mcp.json 生成模板本来就支持 url 型（kb-design-system）。
- **建议**：PR-005 从 🟡 升 🔴。connectors 改 `{name, type: 'stdio'|'http', command?, args?, url?, env: record, access}`——PR-005 的选项 a，demo 事实加重了它。

### DC-03 🔴｜skill 三来源 + 版本徽章是演示高光，schema 枚举必须装得下

- **demo**：skills[].source ∈ `{local, asset}`，资产平台拉取项带**版本号徽章**，走场第 5 步明写「来源徽章（**高光**）」。
- **2.0**：skillEntrySchema 仅 `agenthub | local`（= 预审 PR-001：模板内置来源无位）；「数字资产平台」即 AgentHub（D-033 实证 API）。
- **建议**：PR-001 维持 🔴 且裁决方向明确——**加第三来源支**（template 或等效），并统一命名「AgentHub」；demo 的 asset 卡字段（下载量/分类）真 API 没有，I3 演示素材按真 API 字段降级或向 AgentHub 提需求。

### DC-04 🔴｜avatar / 一句话简述：领导见过的卡面必备字段

- **demo**：`avatar` + `brief`（一句话职责）是创建表单字段、工牌卡与员工详情页身份头字段。
- **2.0**：schema 无 `avatar`、无 brief 对应字段（persona.identity 缺失 = 预审 PR-002）；[员工业务 §3](详细设计/员工业务与前端详细设计-v0.1.md) 卡片「头像/图标字」「简介截 2 行」已在消费。
- **建议**：PR-002 维持 🔴，裁决方向收敛为**补最小字段集**（identity / capabilities / department / avatar / engine_version）；demo 事实是「领导见过」的背书，不建议走「砍 UI 展示项」路线。

### DC-05 🟡→🔴｜档位 UI：领导已定调「全隐」，2.0 设计还保留档位交互

- **demo v2**：界面全隐档位、后台静默落默认档、「一切界面不再出现档位字样」——这是**领导修改建议**的直接落实。
- **2.0**：[员工新建设计 §3.5](概要设计/员工新建设计-v0.1.md) 三卡片单选 + 高级自定义；[员工业务 §4.1](详细设计/员工业务与前端详细设计-v0.1.md) Step 4 降优先级「折叠展示可展开微调」；详情页 tab⑨ 渲 tier-map。
- **建议**：2.0 跟进 v2 定调——Step 4 去掉档位区块（schema `tier_map` 字段保留、模板默认值静默落账）、tab⑨ tier-map 渲染降级为只读声明或并入治理卡。此条与预审 PR-006（tier_map 命名统一）可同批裁决。**性质**：产品口径冲突（领导定调 vs 设计保留），非技术问题。

### DC-06 🟡｜身份文件形态：demo 预览 `employee.yml + persona.md` vs 2.0 `manifest.yml + AGENTS.md`

- **demo**：预览树渲 employee.yml / persona.md 两文件——1.0 lab 的简化形态，与 1.0 真实体系（staff.yml + agents/*.md）也不同构。
- **2.0**：manifest.yml + AGENTS.md（唯一身份源，D-006 五段式）。
- **建议**：2.0 不改（manifest+AGENTS.md 是白皮书不变式）；**演示素材侧对齐**——内置 team 演示（I3）的预览/走场话术用 2.0 形态，避免领导形成 employee.yml 心智。落 I3 演示脚本任务清单。

### DC-07 🟡｜底座选择时机：demo 创建期多选 vs 2.0 安装期选底座×作用域

- **demo**：创建表单含底座多选（hosts），保存后安装弹层预勾选；多 deployment 并存（一员工多底座多工位），无「同一底座同目录单一当值」约束。
- **2.0**：生成（底座无关，白皮书不变式「一份资产多底座上岗」）→ B 系列安装向导选底座×作用域 + D-013 当值互斥。
- **建议**：**维持 2.0 模型**（demo 是演示简化，把底座前移到创建期会固化「员工绑底座」心智，违背三层分离）；对齐动作只在演示话术——生成完成态的出口①「安装到底座」承接 demo 的「保存即安装」节奏感。不改设计。

### DC-08 🟡｜Tools / 知识库 / Hook 三轻类与 2.0 概念模型的错位

- **Tools**（代码执行沙箱/网页检索/文件读写/图表渲染）：2.0 里这是**底座能力**（requires.capabilities 的 bash-exec/fs-access 等），不是员工包内容——概念错位，2.0 不跟进 schema，向导也不展示（能力协商自动推导）。
- **知识库**（团队 Wiki/产品手册引用）：2.0 定位为连接器子集（员工业务 tab⑦ 空态「并入 tab⑧ 展示」）；白皮书包结构有 `knowledge/` 目录但 schema 无声明。**建议**：维持 2.0 口径，I3 演示话术说明；若要包内知识库随包分发再走 Q 决策（V0.2+）。
- **Hook 四候选中两个是正向功能 hook**（会话结束自动归档/产物落盘校验），2.0 红线编译规则只生成**禁止类**（[员工新建设计 §4.6.1](概要设计/员工新建设计-v0.1.md) 规则库全是「禁止/阻断」）。hooks.json 是 CC 标准格式装得下，缺的是编译规则与规则库条目。**建议**：V0.1 维持红线子集，正向 hook 记 V0.2 扩展项（挂员工新建设计开放问题即可）。

### DC-09 ⚪｜命名统一：三个名字一个东西

- demo「**数字资产平台**」/ 2.0「**AgentHub**」/ 白皮书管控平台模块「**员工市场**」。D-033 已实证 CLI API、E-13 全部按 AgentHub 落地。**建议**：对外口径统一 **AgentHub**（员工市场 = AgentHub 的平台侧门户，白皮书已有此关系）；demo 话术在 I3 演示脚本里对齐。
