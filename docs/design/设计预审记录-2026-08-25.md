## 1 预审范围与方法

- **范围**：三份 M2 详细设计全文逐节精读；对照上表基准文档做交叉核验；抽查仓库现状（`workbench/` 目录、服务本体 §10 端点表、docs/README 索引）验证文档引用的代码路径与结构假设。
- **触发语境**：路线图 I0-3 任务「M2 三份详细设计评审 🟡→🟢」。本预审是其先行机械输入——覆盖/一致性/可编码性由 agent 机械核出，裁决权全部留用户。
- **不做**：架构重构建议（只在问题内提）；UI 细节还原度核对；Keyhub 对接契约正确性（以 D-033 实证为准）；服务本体/托盘壳两份详细设计（不在预审对象内，仅作引用核对，其自身问题列入 §6 跨文档提醒）。

## 2 总体结论

三份文档的**底子是好的**：真机验证（D-034）回填细致且证据链完整；开放问题全部带临时立场；「花名册=派生视图」「roster.json 不设」「contract 消歧」等修订方向正确且两份文档间自洽。

核心风险集中在两处：

1. **schema 的三个死锁/缺口**（PR-001/002/003）——均属「上游字段表 → schema」翻译时静默丢失或含糊，且每个都恰好卡在冻结基线的验收标准上（E-11 模板默认 skill 无合法来源值、E-12 生成包过不了 base_identity 必填校验、E-10 花名册简介无数据源）。schema 是契约冻结四件套之首（D-038），这些必须在冻结前解决，否则冻结了一个无法表达主验收路径的契约。
2. **D-036/037 拉前裁决未回灌**（PR-007/008）——员工业务详细设计成稿于 2026-08-23（拉前裁决 2026-08-25 之前），「无引擎/看板隐藏/统计占位」整组口径已被推翻。路线图把功能点清单回写安排在 I3（治理链声明，合理），但**员工业务详细设计等不到 I3**——它是 I0-5（Web 壳补全）与 I1 L1 线的直接依据，I0-5 做 F-02 导航骨架当天就会遇到「看板入口按哪版口径做」的问题。

覆盖轴结论：E-01/E-02/E-03 验收标准均有承接（§2.3 校验语义 / §7 测试表逐条对应）；但 E-02 功能点描述的「skill 清单结构（名称/版本/**来源**/参数）」中「参数」无对应设计（Agent Skills 标准本无参数概念，若按标准裁掉应显式声明，列 ⚪ 归入 PR-002 的取舍表一并澄清）。

### 🔴 PR-001｜skillEntrySchema 缺 `template` 来源支——E-11 主验收路径产不出合法 manifest

- **锚点**：[shared-protocol详细设计-v0.1.md:182-198](详细设计/shared-protocol详细设计-v0.1.md#L182-L198)（§3.2 discriminatedUnion 仅 `agenthub` / `local` 两支）。
- **为什么是问题**：`source_type` 枚举没有「模板内置」。但 E-11 的验收路径是「模板预填后**一路下一步**可生成」——dev-engineer / req-architect 模板自带默认 skills 素材（[员工业务 §5.2](详细设计/员工业务与前端详细设计-v0.1.md#L152-L154)），管线 ④ 明确有「模板内置 -> templates/ 拷贝」分支（[员工业务 §5.1:141-142](详细设计/员工业务与前端详细设计-v0.1.md#L141-L142)），上游向导的来源徽章是三态「agenthub / local / 模板内置」（[员工新建设计 §3.4](概要设计/员工新建设计-v0.1.md#L143-L146)）。生成器只能二选一：写非法值（校验拒绝）或撒谎标 `local`（丢失「重建包时从 templates/ 拷贝」的语义，且来源徽章三态塌成两态）。冻结基线 E-11 验收与 schema 直接冲突。
- **建议裁决选项**：a) discriminatedUnion 增加 `template` 支（`{source_type:'template', template_id}`）——语义最干净；b) 模板 skill 统一标 `local` + `origin: 'builtin:<template_id>'`——改动最小但弱化来源语义，需同步修订员工业务的来源徽章设计。

### 🔴 PR-002｜schema 丢字段群——花名册/详情页多个 UI 字段无数据源

- **锚点**：[shared-protocol详细设计-v0.1.md:62-152](详细设计/shared-protocol详细设计-v0.1.md#L62-L152)（§2.2 schema 全文）vs [员工新建设计 §4.3 字段表](概要设计/员工新建设计-v0.1.md#L306-L346)（canonical 手写版）。

  | `persona.capabilities[]`（能力短语） | 详情页 tab① 档案卡「擅长」栏（员工业务 §8）；五段式第三段渲染 |
  | `agent.department`（所属部门） | Step 2 表单字段 + `employee_id = <id>@<部门>` 的域后缀来源（员工业务 §5.1 ③）；E-Q4 已裁决「部门可改、不联动 employee_id」——没有独立字段则该裁决无法实现 |

  花名册是**派生视图**（扫描 manifest.yml 聚合，员工业务 §1）——manifest 里没有的字段，花名册永远拿不到。「简介」「擅长」等 UI 已写进员工业务设计，数据源在 schema 层被裁掉了，链条断在中段。

### 🔴 PR-003｜base_identity 必填死锁——生成时无值可填，安装器又不回填

- **锚点**：[shared-protocol详细设计-v0.1.md:75](详细设计/shared-protocol详细设计-v0.1.md#L75)（`base_identity: z.string().min(1)` 必填）· [员工业务 §5.1:144](详细设计/员工业务与前端详细设计-v0.1.md#L144)（管线 ③ 只写 employee_id / operator_id）· [底座适配 §4:115-122](详细设计/员工安装与底座适配详细设计-v0.1.md#L115-L122)（安装执行六步无回填环节）· [员工新建设计 §4.3](概要设计/员工新建设计-v0.1.md#L321-L322)（「安装时由文档 B 流程回填」）。
- **为什么是问题**：三方各执一环拼成死锁——schema 说必填；生成管线（员工业务）没写它；安装器（底座适配）把上游「安装时回填」的步骤丢了。生成时员工还没安装、不知道会装哪个底座，无值可填 → E-12 验收「产出包过 shared-protocol 校验」不可能通过。上游设计本身还有第二层含糊：base_identity 是单值字段（如 `claude-code@lyadmin-mac`），多底座安装时装了 CB + Qoder 记谁？且「回填」= 安装器改写 canonical 员工包目录的 manifest（员工包是 git 可管理的 canonical 源，安装副作用改源文件本身就需要裁决）。
- **建议裁决选项**：a) schema 改 optional，底座归属事实由安装报告承载（推荐——报告已有 base 字段，天然多底座）；b) 生成时写占位值（如 `unassigned`），安装时回填并定义多底座覆盖策略；c) 恢复上游回填语义并补齐：回填时机、多底座策略、git 管理冲突的处理。

### 🟡 PR-005｜connectors 表达力不足以生成 mcp.json

- **锚点**：[shared-protocol详细设计-v0.1.md:107-112](详细设计/shared-protocol详细设计-v0.1.md#L107-L112)（`{name, command, env: string[], access}`）· [员工新建设计 §4.7](概要设计/员工新建设计-v0.1.md#L456-L469)（mcp.json 两形态：进程型 `{command, args, env:KV}` / url 型 `{url, access}`）。
- **为什么是问题**：三处不足——① 无 `args`：模板默认连接器 command 是完整命令串（`npx -y @modelcontextprotocol/server-github`），mcp.json 标准结构是 `command + args[]` 分离，拆分规则未定义；② 无 url 型：dev-engineer 模板默认 MCP「代码规范知识库(read)」是 url 型连接器，schema 装不下；③ `env: string[]` vs mcp.json 的 `env: {KEY: VALUE}` KV map，转换规则未定义。D-037 模式一「员工包 mcp.json 挂引擎工具」也走此 schema（见 PR-010），同一掣肘。
- **建议裁决选项**：a) connectors 改 `{name, type: 'stdio'|'http', command?, args?, url?, env: record<string,string>, access}`；b) V0.1 只支持 stdio 型并在 schema 注释声明（同步修订模板素材表的知识库连接器）。

### 🟡 PR-007｜employee_id 域后缀正则与中文部门名冲突

### 🟡 PR-008｜capability 词表无权威定义——schema 与 negotiator 各自硬编码必漂移

- **锚点**：[shared-protocol详细设计-v0.1.md:134-139](详细设计/shared-protocol详细设计-v0.1.md#L134-L139)（requires.capabilities 自由字符串）· [底座适配 §2.2:65](详细设计/员工安装与底座适配详细设计-v0.1.md#L65)（L1/L2 判定词表）· [UPP §6.1](概要设计/UPP通用插件协议规范-v0.3-开放标准薄封装.md#L257-L279)（profile provides/unsupported）。
- **为什么是问题**：`agent-def / skill-def / slash-command / bash-exec / fs-access / subagent-dispatch / event:*` 这套词表散在 UPP §5/§6、上游设计 §4.1 推导表、底座适配 §2.2 三处，全是自由字符串。schema 自称「全链路单一真相源」却不持有词表——schema 校验侧（合法值集合）与 negotiator 匹配侧（profile 提供集合）各自硬编码，I1 双线（L1 schema / L2 negotiator）并行开发时必然漂移。这正是 D-038 契约冻结要防的病。
- **建议裁决选项**：a) shared-protocol 导出 `CAPABILITY_VOCABULARY` 常量（或 zod enum + 前缀规则 `event:*`），profile 与 negotiator 一律 import；b) 词表归 UPP 文档定义、schema 只引用——需在 UPP 补权威清单节。

### ⚪ PR-009｜standards.hooks 的 default 注入使「必填」校验形同虚设
