## 3. 架构概览

```
┌──────────────────────────────────────────────────────────────┐
│                    管控平台（远端 Web）                        │
│  员工市场(AgentHub/Keyhub) │ 运营驾驶舱 │ 成本 │ 审计        │
│                         ⇅ OTLP / HTTP（邮箱登录认证）          │
├──────────────────────────────────────────────────────────────┤
│  工作台（本地 · exe/CLI 安装 · Web 访问 · 参照 QoderWaker）    │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────┐ │
│  │ 交互前端（六大模块）│  │ 运行时（七大能力） │  │ 四层适配     │ │
│  │ · 我的员工        │  │ · 编排引擎        │  │ MCP(工具)   │ │
│  │ · 我的群组        │  │ · 编排驱动        │  │ Hooks(hook) │ │
│  │ · workflow 编排   │  │ · 员工注册发现    │  │ AGENTS.md   │ │
│  │ · 任务看板        │  │ · 工程记忆        │  │ MemoryProxy │ │
│  │ · 底座与环境管理  │  │ · 合规监督        │  │  (记忆注入) │ │
│  │ · 对话界面        │  │ · 本地观测        │  └──────────────┘ │
│  └──────────────────┘  └──────────────────┘                    │
├──────────────────────────────────────────────────────────────┤
│  员工包（独立交付 · 可独立安装/卸载/升级）                      │
│  AGENTS.md + skills/ + hooks/ + mcp.json + orchestration/     │
└──────────────────────────────────────────────────────────────┘
```

**关键区分**：
- **工作台** = 独立应用（exe/CLI 安装 → 启动本地 Web 服务 → 浏览器访问），不嵌入任何底座
- **员工包** = 安装到智能体底座（CC/CB/Qoder 等），底座加载后成为该员工
- **管控平台** = 远端 Web，通过邮箱登录认证

## 4. 当前阶段任务：按原型图完成设计（不着急开发）

原型图已按 QoderWaker 的 UI 形态完成（`docs/prototype/` 3 页 HTML），接下来的工作按以下顺序推进设计：

### 4.1 员工新建（创建向导）

**参照**：原型图 workbench.html + QoderWaker 截图 `新建Waker.png` / `员工详情.png`

**需要设计**：
- 员工创建向导的完整流程（角色模板选择 → 身份配置 → 能力选择 → 约束配置 → 生成）
- 员工包生成逻辑（AGENTS.md + skills + manifest.yml 的构建规则）
- 内置角色模板定义（dev-engineer / req-architect，各包含哪些默认 skill）
- 员工详情页的多 tab 结构（首页/项目/任务/记忆/技能/知识库/连接器/权限）

### 4.2 员工安装（多智能体底座适配）

**优先级**：先适配 **CodeBuddy** 和 **Qoder**（两者 CC hooks 已验证兼容，1.0 已有适配经验可参考）

**参照**：原型图 workbench.html + QoderWaker 截图 `环境与设备.png`、`本地运行.png`

**需要设计**：
- 安装流程：员工包 → 四层适配器 → 底座文件落位（AGENTS.md 转 CLAUDE.md / CODEBUDDY.md 等）
- 底座管理界面：底座卡片（在场/版本/已装员工数）、版本漂移检测、一键对齐
- 安装报告：可达 Level 判定、降级项清单、告警
- 卸载流程：清理 + 残留检测

**1.0 参考**：agents-team 1.0（https://github.com/KDevSec/agents-team）已适配过 CodeBuddy 和 Qoder，可以参考其适配方式和 hooks 配置文件，但 2.0 是全新架构，**不一定完全照搬**。

**AgentHub 集成**：Keyhub（https://github.com/KDevSec/Keyhub）是已有的数字资产平台，创建向导中 skill 可从 Keyhub 拉取。需要设计 Keyhub API 对接方式。

### 4.3 员工运行和展示

**参照**：原型图 workbench.html + QoderWaker 截图 `员工详情.png`、`对话界面.png`

**需要设计**：
- 员工列表页（卡片 grid：头像 + 岗位名 + 底座标签 + 运行状态）
- 员工详情页（多 tab 的具体字段和交互）
- 对话界面（与员工直接对话 + 任务建议卡片）
- 员工状态监控（在线/离线/在跑任务数）

### 4.4 登录和认证

**与管控平台之间的登录**，使用**邮箱登录**方式。

**需要设计**：
- 工作台 ↔ 管控平台的认证流程（邮箱 + 密码 / 邮箱 + 验证码）
- Token 管理（JWT 或 session）
- 权限分级（L1 公司级 / L2 部门级 / L3 团队级 / L4 个人级，与员工治理分级对齐）

## 5. 后续待调研（设计阶段之后）

以下事项不阻塞当前设计工作，可在设计完成后逐步推进：

### 5.1 manifest + skill schema 正式化

将白皮书中的草案字段正式化为 JSON Schema 或 TypeScript 类型定义。定义身份三元组格式、provides/requires 能力枚举值。

### 5.2 handoff 协议设计

4 种消息类型（delivery_handoff / review_request / review_verdict / human_gate）的具体 schema 设计。借鉴：FIPA ACL + OpenAI Swarm + LangGraph + Google A2A。

### 5.3 记忆方案：TencentDB SDK 集成

写 EmployeeHostAdapter 接入 TdaiCore（4 个方法），设计 L0-L3 蒸馏管线与文件基底的对接方式。

### 5.4 OTLP 统一事件源设计

events.jsonl 的 span schema、关键 span 类型（agent.execution / tool.call / gate.evaluate / human.approval）、双消费管线接口。
