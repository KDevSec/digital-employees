治理分级 L1–L4

级别维度准入要求审批可见范围审计
L1公司级最高，跨领域通用模板公司审批全公司全量记录
L2部门级部门通用岗位模板部门审批部门内全量记录
L3团队级团队内复用团队自审团队内仅异常记录
L4个人级个人自定义，鼓励试错无审批仅自己可关闭

治理分级（L1–L4）与使用深度（裸用 / +方法论 / +流程 / +编排）完全正交——治理分级定「能不能用」，使用深度定「用多深」，两个维度自由组合。

标准模板示例（代码形态）

以"开发工程师"为例，展示按定义公式产出的标准模板。实际模板由创建向导自动生成，与手写规范完全同构。UI 形态见原型图。

▶ 收起 YAML 模板（开发工程师 · L2 部门级） 
# ===== 数字员工标准模板示例：开发工程师 =====
# 智能体底座：Claude Code / opencode / CodeBuddy / Qoder（多底座适配）

# === 一、身份 ===
agent:
  name: dev-engineer
  version: 1.0.0
  department: 技术研发部
  role: 开发工程师

persona:          # 主人设（五段式岗位说明书）
  identity: 你是一名资深开发工程师，擅长 Python / TypeScript，遵循 TDD 流程
  principles:
    - 每次改动后必须跑全量测试
    - 代码风格严格遵循团队规范
    - 优先使用现有工具和库，避免重复造轮子
  capabilities: [代码实现与重构, 单元测试编写与执行, Git 分支管理]
  usage_modes: [裸用, +方法论, +流程, +编排]
  constraints: [禁止操作生产环境, 禁止修改DB schema未经审批, Token上限50K]

# === 二、能力 ===
skills:
  - {name: code-impl, version: 1.2.0}
  - {name: unit-test, version: 1.0.0}
  - {name: git-ops, version: 0.9.0}
mcp:
  - {type: knowledge-base, name: 代码规范知识库, access: read}
  - {type: knowledge-base, name: 业务领域知识库, access: read}
  - {type: tool, name: Git API, access: read-write}

# === 三、约束 ===
constraints:
  red_lines: [禁止写入 /etc/ /opt/production/, 禁止调用 deploy-to-prod, 禁止访问财务系统]
  model_tier: claude-sonnet-5
  token_quota: {per_task: 50000, per_day: 500000}
  host_restrictions: [Claude Code, opencode]

# === 四、流程 ===
runbook:
  name: TDD 开发流程
  steps:
    - {step:1, action: 理解需求与变更范围, self_check: 确认理解无误}
    - {step:2, action: 编写失败测试, skill: unit-test, self_check: 红灯}
    - {step:3, action: 最小实现使测试通过, skill: code-impl, self_check: 绿灯}
    - {step:4, action: 重构优化, skill: code-impl, self_check: 测试全绿+质量达标}

# === 五、治理 ===
governance:
  level: L2
  approval: 部门审批
  visibility: 部门内
  audit: 全量记录
  lifecycle_owner: 技术研发部

二

数字员工 Team 定义

数字员工 Team = 多个数字员工 + 流程编排。通过编排引擎驱动多员工协作，完成单人无法独立交付的复杂任务。

两种 Team 形态

👥 群组

人的协作空间：人把多个员工拉进一个组，绑定 workflow 模板（必选），在组里 @ 员工发起任务、按组聚合看任务。

协作空间必选 workflow

⚙️ 编排 Team

流程化协作：由 flow-driver 按 node-table 自动接力（需求 → 开发 → 测试 → 评审），人只在人工闸停靠确认。

自动接力人工闸

编排引擎的两种节点执行模式

inline
同一会话内连续执行 agent 按 runbook 依次调用 skill
上下文连续，适合轻量任务链
process
每个节点独立会话 flow-driver 管理状态 + gate 判定
上下文隔离，可并行、可重试、可跨底座

编排对象无关性

编排引擎不区分节点是 skill 还是员工——对引擎来说，每个节点就是"要执行的东西 + 输入 + 输出 + gate 条件"。

🔗 单员工 skill 链

flow-driver 编排 skills，每个 skill 独立会话，避免上下文污染

🤝 多员工接力

flow-driver 编排员工，每个员工独立会话，gate 在员工间做质量门

🔀 混合编排

同一 node-table 中既有 skill 节点也有员工节点

五大模块

① 定义——员工怎么被定义

员工管理：组合基座 + MCP + 记忆 + 知识库 + 工具 + 指令文件，定义出"数字员工是谁"，支持版本与模板

AgentHub 集成：从技能市场拉取 Agents.md / Skill.md，注入数字员工，补全"会什么"

② 运行——员工怎么跑起来

部署引擎：把员工定义打包成"员工包"，提交运行环境拉起实例，自动登记员工身份

运行环境：K8s 容器化，支持 Pro 模式（独立隔离）和 Lite 模式（共享资源池）

③ 发现——员工怎么被找到

目录发现服务：数字员工的"通讯录"——上岗即登记（注册/注销/心跳/能力画像），统一维护"在岗名单"

Search Agent：按能力检索匹配的员工，按匹配度排序推荐

④ 协同——多员工怎么一起干活

模式 A · 固定工作流：DAG 执行引擎按流程驱动，人工审批节点强制把关、不可跳过

模式 B · LLM 动态编排：Orchestrator 自主拆解任务、挑选员工、并行执行并汇总

⑤ 效能——员工干得怎么样

监控与可观测性：汇总 Trace/指标/日志，做统计、链路追踪、异常告警、协作拓扑

评估引擎：基于成功率、Token 消耗、耗时、SLA 达成率综合评估——不合格下架，合格继续在岗，效能参与后续任务匹配

O（目标）：构建面向研发体系的数字员工套件与管控平台，制定数字员工统一标准与 L1–L4 分级体系，实现各领域数字员工的纳管、度量与治理，把质量与安全合规要求固化进数字员工套件，打造具有浪潮信息 DNA、可规模化推广的数字员工体系。

以下协同要求不是一次性收材料，而是要共同支撑 9–12 月从 V0.5 到 V1.0 的连续交付。

使用方式：每个章节先看「会上主要讲」，这是本次 Workshop 的主线；后面的「补充支撑」只在需要解释或被追问时展开。

整体诉求

我们对各组最核心的诉求只有一句话：横向组的产出，请以「可被数字员工装配」的形式交付；纵向组提供真实场景，并使用套件做出数字员工、在平台上跑起来。

🧰 数字员工套件负责

把岗位、流程、知识、工具、安全和质量要求装配成数字员工。

🏛️ 管控平台负责

数字员工的上架、分发、运行监控、度量评价、成本和权限审计。

各组的标准如果只停留在文档里，仍然依赖人主动遵守；装配进数字员工后，才能成为默认执行、可追溯、可度量的能力。

对各横向组的要求

1对质量组的要求 L1-L4 标准共创

请质量组提供两类基础材料：一是 L1 级岗位说明的原始版本；二是协调垂直领域提供岗位说明、作业手册、操作指导、模板和验收规则，用于 L2/L3 等更高等级数字员工的定义。首批可从系统软件、技术研发、硬件研发/BMC 等领域开始。
补充支撑
  • 将 IPD、敏捷、瀑布等研发流程拆解为可配置的流程节点，明确输入、输出和准出标准
  • 共同定义数字员工的岗位职责、能力要求、交付物标准和质量验收规则
  • V0.3 中材料仍以 L1–L3 表述；正式分级口径按已定稿 OKR 统一为 L1–L4
  • 质量要求最好能够结构化，便于装配进套件，并由平台自动执行和留痕
现场最好确认：接口人、首批材料范围、提供时间，以及 L1–L4 标准的共创安排。

2对安全合规组的要求 9 月随 V0.5 上线

9 月随 V0.5 上线首批安全能力。请安全合规组提供现有安全规范等原始材料，将其 AI 化为 Spec、Skill、工具和原则要求，并协同完成数字员工安全行为规范与模板的定义和开发。
补充支撑
  • 明确数字员工能够访问哪些代码库、数据和网络资源
  • 明确数据外流规则、敏感操作清单和必须记录的审计事件
  • 明确数字员工、Skill 和工具上架前的安全扫描与准入要求
  • 安全规则应尽量内置到套件中，实现「出厂即合规」，而不是运行后再补检查
现场最好确认：安全接口人、V0.5 安全最小要求清单、规则和模板的交付及联调时间。

3对知识管理组的要求 统一知识接口和权限

请知识管理组与我们统一知识接口和权限，重点明确不同场景下「数字员工权限」与「知识权限」的交叉关系。
补充支撑
  • 为数字员工提供统一的知识入口或检索接口，使其能够按岗位和场景挂载相应知识
  • 明确哪些知识可由哪一级、哪一岗位的数字员工访问，并与安全权限体系打通
  • 建立双向机制：数字员工既消费知识，也能把运行经验和问题记录回流到知识库
  • 各领域知识工程师可作为相应数字员工的知识对接和维护人员
现场最好确认：接口负责人、权限模型负责人、首个联调场景和时间节点。

4对工具链管理组的要求 四件事

重点解决四件事：新旧平台工具融合、CI/CD 等端到端链路打通、Skill/Agent/数字员工兼容、AgentHub 对接。
补充支撑
  • 建立统一的工具注册和调用标准，可采用 MCP 或统一工具网关等方式，避免逐个点对点集成
  • 工具凭证、权限和配额统一托管，数字员工不直接持有裸凭证
  • 明确数字员工在本地 IDE、云端和其他运行环境中的适配规范与责任边界
  • 套件尽量做到一次标准化、多个运行端复用，兼容问题统一归口处理
现场最好确认：首批接入工具、AgentHub/CI/CD 接口人、联调时间及兼容规范维护方。

5对基建组、度量绩效组和预算组的要求 选、用、育、留、备、退

一是明确数字员工运行的观测、监控和度量指标；二是在度量绩效组指导和评审下，由套件与平台团队提炼数字员工评价选用机制，并上线智能体评测能力；三是逐步覆盖数字员工的「选、用、育、留、备、退」。
补充支撑
  • 基建组：提供数字员工运行环境、模型算力、网络和网关链路，支持本地、研发专网、沙箱或云端等运行形态
  • 度量绩效组：指导任务成功率、返工率、质量、效率和资源消耗等指标定义；平台负责采集和提供数据
  • 预算组：共同明确模型/Token、算力和工具等成本口径，逐步核算到单个数字员工、团队和使用部门
  • 评价选用和成本核算最终都需要以平台的实际运行数据为依据
现场最好确认：各组接口人、首批指标集、评测方法、成本口径和数据对接时间。

6对纵向领域组的要求 1 个典型场景实跑

每个领域至少选择 1 个典型场景，使用数字员工套件制作本领域的数字员工，并在管控平台上实际跑起来，验证整体方案可行性。
补充支撑
  • 每个垂直小组指定 1 名数字员工需求接口人
  • 提出本领域最痛的 1–2 个岗位场景，并选其中 1 个优先验证
  • 提供岗位 SOP、输入输出、所需知识和工具、验收标准等材料
  • 数字员工上架后，领域组作为第一批用户，承担试用、反馈和定级评审
  • 条件成熟时，可选择 BIOS Debug、CVE 修复等跨节点流程，验证多个数字员工的团队协同
现场最好确认：首批场景、接口人、材料提供时间和首个数字员工试跑时间。

7服务器及其他资源需求 联调验证环境

请提供 1 台可稳定使用的 M7 / Gen8 服务器，并接入研发专网，用于数字员工套件、管控平台及首批场景的联调验证。
补充支撑
  • 需要进一步确认服务器具体配置、归属、到位时间和运维责任人
  • 模型算力需求、供给方式和配额目前仍需结合首批场景确认
  • 相关入口还包括本地 IDE、云端协同、AgentHub、管控平台，并需明确对 InAgent、EPAI 等平台的集成方式
  • V0.3 中列出的协同人员为：李勇、霍文、周广跃、唐超、俊昌；叶笑夕、刘斌；龙飞、海渔
现场最好确认：服务器和算力负责人、资源到位时间，以及上述协同人员的角色和投入方式。

现场收口

今天不要求把所有方案一次讨论完，但希望每个相关组至少确认三件事：接口人是谁、首批交付物是什么、什么时间能够提供。如果存在人员、服务器、算力、权限或平台集成阻塞，也请一并提出，由项目组形成清单统一协调。
