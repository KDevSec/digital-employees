# 结构化评审裁决

## 何时使用

被编排引擎的评审闸（gate）派发时——发函方给出：闸 ID、覆盖范围（covers 节点清单）、
评审对象（任务工作区 `.devzero/tasks/<task_id>/handoffs/` 下的交付产物）。
本 skill 产出裁决并回函，**不修改任何被评审产物**（建议非拦截，改动归主责员工）。

## 怎么做

### ① 确定评审对象类型与评分表

按 covers 指向的产物类型选表（未列类型用通用表）：

| 对象类型 | 评分维度（各 25 分，满分 100） |
|---------|------------------------------|
| 需求（SR/故事） | 需求一致性 / 可验收性（每条有判据）/ 完整性（无遗漏无重复）/ 无歧义 |
| 设计（架构/详细） | 需求可追溯 / 技术选型依据 / 接口与错误语义完备 / 可落地性 |
| 代码 | 规格一致性 / 正确性与边界 / 测试真过（红绿可复跑）/ 架构一致性 |
| 通用兜底 | 目标对齐 / 证据充分 / 边界覆盖 / 可维护性 |

### ② 逐项评审

- 每个维度：得 0~25 分，**必须附判据**（引用产物中的具体位置/行文/行为；无依据不扣分）
- 每个问题标级：🔴 阻断（必须修复才能过闸）/ 🟡 重要（应修复，可随交付记录）/ ⚪ 次要（建议）
- 🔴 判据：错误会破坏目标、违反红线、或缺失关键验收路径——从严，宁 🔴 勿 🟡

### ③ 汇总裁决

```
verdict = FAIL  若存在任一 🔴，或总分 < 70
        = PASS  否则（70~84 带改进建议；85+ 直接过）
```

FAIL 必附**可执行的 reflow 建议**（改什么、怎么改、改到什么程度可复审）——主责员工按它重做。

### ④ 回函（三件套，一个不少）

1. `engine_record_gate`：verdict（PASS/FAIL）+ issues 摘要（分级计数 + 🔴 全文）+ 分数
2. `engine_handoff_write`：完整评分表（维度/得分/判据/问题清单/reflow 建议）
3. `engine_dispatch_done`：完工回报

## 边界与反例

- **只评不改**：不直接修改被评审产物；发现问题时写进 issues，由主责员工修复
- **不猜范围**：covers 指向的产物缺失或范围不明 → 直接回函说明缺什么，不脑补评审
- **不模棱两可**：verdict 只有 PASS/FAIL 两态；「看起来还行」不是结论
- **不越权拦截**：给出建议与判定，不阻止他人继续（阻断语义归闸的 verdict 与红线 hooks）
- **评分不漂移**：同一对象复审时，前轮 🔴 未解决则维持 FAIL，不因改了 🟡 而放行

## 与引擎工具的关系

引擎工具（record_gate 等）不可用 = 工作台未运行 → 停止评审并上报，不得绕路、不得把裁决写进任意文件冒充回函。
